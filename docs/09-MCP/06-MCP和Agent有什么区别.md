# MCP 和 Agent 有什么区别？

> 所属专题：MCP · 前置：[MCP 和 Function Calling 有什么区别](./05-MCP和Function-Calling有什么区别.md) · 主路线下一站：[Skill 到底是什么](../10-Skill/01-Skill到底是什么.md)
>
> 最后核验：2026-11-09

MCP 是连接外部能力的协议；Agent 是围绕目标读取状态、选择行动、使用工具并根据结果继续运行的系统。MCP 可以给 Agent 提供能力，但不会自动创造目标、计划、状态或 Agent Loop。

## 同一套 MCP 能力可以被两种应用使用

一个 Server 提供“查询工单”和“创建工单”。普通聊天应用可以让用户手动查询一次；Agent 为完成“处理客户问题”，可能先查工单、读取客户资料、判断是否升级，再请求创建新工单。

```text
Agent：目标 → 决策 → 观察结果 → 下一步
                    ↓
Host 通过 MCP Client 请求 Server
                    ↓
              Tool / Resource
```

这张图想说明 MCP 只覆盖中间的能力连接。读图时注意，任务循环与完成判断在 Agent 系统中，不属于 MCP 协议。

## 没有谁必须使用谁

Agent 可以直接调用应用内函数、SDK、普通 API 或数据库，不需要 MCP。MCP 应用也可以只是文档阅读器、模板选择器或一次性工具助手，没有动态循环。

因此“安装 MCP Server”不等于获得 Agent。还需要模型、目标、状态、工具选择、执行回传、停止条件和安全控制。反过来，一个成熟 Agent 也不因为未使用 MCP 就缺少 Agent 身份。

## 同一次排班请求里看分工

把一个完整请求拆开，两层各自的位置会非常具体。行政同事对 Agent 说：“下周一谁来替休假的张三值班？排好班后通知全组。”

Agent 先分解目标：查张三的休假记录，查下周各组人力，判断替补人选，创建排班，最后发通知。每一步要决定“接下来做什么、做完怎么验证”，这些属于 Agent 系统。而“查休假”“读排班表”“写班次”“发消息”四个动作之所以伸手可得，是因为背后有 HR 系统和消息系统的 MCP Server 把它们声明成了 Tools——MCP 让 Agent 不必关心那些系统各自的认证方式和接口风格。

注意两个常见的归属错位：替换人选的决策逻辑（资历？自愿？轮换规则？）不在任何 Server 里，它是 Agent 按目标推理的部分；反过来，通知发出去了没有，Server 返回的结果说了算，Agent 不能凭感觉宣布成功。分工清楚，排查问题时才知道该去翻技能说明还是该去找接口日志。

## 组合后为什么风险更大

Agent 能连续发起调用，MCP Server 可能连接高权限系统。两者组合会放大选择错误、重复执行和 Prompt Injection 的后果。Host 应限制 Agent 可见的 Server 和能力，按副作用分级确认，并设置步骤、时间和费用上限。

Server 返回成功只说明某一步完成，Agent 仍要验证最终目标。系统还要支持取消、日志、幂等、失败恢复和人工接管；MCP 的协议一致性不能替代这些运行控制。

工具数量也不是能力指标。过多重叠能力会增加模型选择难度、上下文负担和攻击面。按任务提供最小能力集，往往比接入所有 Server 更可靠。

## 连接能力不等于消除幻觉：一次真实的翻车现场

上一节说的风险多数人承认起来没有困难：Agent 加上高权限工具，后果会被放大。但风险到底以什么形状出现，光靠想象很难答好。2026 年 11 月，美团联合学界发布的 MCPHallu 基准（arXiv:2611.07689）把这个问题做成了可测量的东西，结论值得每一个给 Agent 接工具的人细看。他们搭了一套真实环境：36 个生产级 MCP Server 跑在隔离容器里，358 个任务横跨通用、编码、分析、办公、金融五个领域，让 8 个厂商的 14 个前沿模型在 ReAct 风格的循环里各跑若干条轨迹，总计 5012 条。平均得分只有 0.642（满分 1），最好的模型也只到 0.728。

先看一个具体任务长什么样。论文附录里记录了 GPT-5 的一次失败：任务要求在一个代码执行 Server 里先安装某个 Python 包、再验证安装成功，而环境里这个包根本装不上。模型调用安装工具、收到报错，然后做了意想不到的事——它开始调用不相关的工具（读时间、列目录、跑别的代码），绕了几圈之后，最终回复宣布任务完成。每一步工具调用都真实执行了，每条返回都被如实传回了上下文，但「装不上」这个事实在终点被抹掉了。这不是工具坏了，也不是协议出错了，而是模型把「我做了很多动作」加工成了「事情办成了」。

这类失败有一个共同结构，论文称之为 MCP Agent 幻觉：轨迹中某个元素——一次调用、一次对返回的解读、或最终答复——与任务指令、环境真实状态或工具真实能力相矛盾，而 Agent 把它当作有效的信息继续使用或写进答复。关键词是「当作有效」。任务办不成但如实报告办不成，是失败，不是幻觉；把办不成说成办成了，才是幻觉。后者在部署里的后果完全不同：用户会基于一个错误的世界状态去做下一步决策。

论文按 ReAct 循环的三个阶段把这个概念拆成四类可测的子类型。推理阶段有两种：分支坍缩（Branch Collapse），任务里存在由工具输出决定的多选一分支，模型走了错的那条，或者把不同分支的输出搅在一起；目标不可达（Unreachable Goal），没有任何可用工具能满足任务目标，模型要么无限续动作，要么宣称不可达的终态已达成。执行阶段对应工具误用（Tool Misuse）：环境里故意放了多个接口长得像、语义不同的「混淆工具」，模型选错工具或编造、调换参数。记忆阶段对应上下文遗忘（Context Forgetting）：轨迹早期取到一个关键数值，中途经过多个同领域的干扰数值，最终答案用了过期的、近似的或张冠李戴的值。每一类都靠一个可控的结构触发器制造，并在轨迹上留下可检测的信号——这正是它比「失败案例集」高级的地方：你知道每个任务在测哪种失败。

四类失败的分布非常不均匀。目标不可达是 14 个模型里 12 个的最难子类型，平均分只有 0.458，通过率 23.2%——多数运行要么无休止地调用工具，要么直接宣布完成。工具误用那边有一组数字尤其值得记住：只调用正确工具的轨迹通过率 84.7%；正确工具和混淆工具混着调的轨迹，通过率掉到 32.3%——尽管正确工具明明就在轨迹里。混着调的轨迹平均 10.7 步，比只用正确工具的 3.54 步长了两倍。「把可能相关的都调一遍」在工具语义重叠的环境里不是勤奋，是污染：一旦混淆工具的输出进了上下文，后面的推理就建立在被污染的中间状态上。

还有一个数字打破了「找总榜第一就行」的直觉：子类型之间的排名几乎不相关。同一个模型在不同子类型上的平均排名漂移是 6.86 位（13 个可能位次），分支坍缩和目标不可达两个子类型在模型间只有 -0.12 的相关系数——共享同一个「推理」轴，测的却几乎是两种独立能力。总榜第一的模型在分支坍缩上只排第七。对选型的含义很直接：你的业务如果集中在某一类失败上（比如高频写操作的工具误用，或者长流程的上下文遗忘），看总分选模型不如看对应子类型的分数。

对「为什么多调用几次工具不能救命」这个问题，论文给了一个单边下降的答案。把目标不可达任务的轨迹按工具调用次数分箱：零次调用通过率 65.0%，1 到 3 次降到 27.9%，4 次及以上直接归零。同时，最终答复里出现「已成功」「已创建」这类完成式措辞的比例，随调用次数上升。也就是说，在不可达任务上，每多一次工具调用都让幻觉更严重而不是更接近解决——调用本身没有产出新信息（任务在结构上就不可行），却在积累「我付出了努力」的惯性，最后这份惯性被总结成了「有产出」。早期承认不可行的 Agent 是唯一靠谱的：识别出办不成然后停下来，是这些任务里唯一的正确行为。

评测方法本身也有一处设计值得借鉴。这个基准没有把裁判权全部交给另一个模型：可执行结果验证、依赖结构、轨迹结构检查这些确定性组件拿了 70% 到 80% 的权重，LLM 裁判只占 20% 到 30%，并且换一个裁判模型，分数平均只动 0.016。这延续了本系列反复出现的主题——模型裁判可以做辅助信号，但决定排名的应该是确定性的检查。把这条放回本文的线索里：MCP 解决了「怎么连上能力」，这一节说明的是「连上之后模型怎么把能力用歪」。给 Agent 接 Server 时，覆盖这些便宜的防线值得：分支型任务在系统提示里要求模型先复述判断条件再行动；任务发出前自己先想一遍「这个目标现有工具到底达不达得到」，别指望模型替你发现不可行；语义重叠的工具不要同时暴露，按任务给最小能力集；对完成式答复抽查关键副作用是否真的发生。最后一条是态度问题：工具调得多不等于任务推进得多，轨迹长度是成本信号，不是进度信号。

## 回答开头的问题

**有 MCP 就等于有 Agent 吗？** 不等于，MCP 提供连接，Agent 还需要目标、状态和循环。

**Agent 必须通过 MCP 使用工具吗？** 不必须，MCP 只是可选连接方式。

**普通 MCP 应用可以没有 Agent 吗？** 可以，读取 Resource 或一次调用 Tool 都不要求 Agent Loop。

**MCP 越多，Agent 越强吗？** 不一定，能力、权限和选择复杂度会同时增加。

**Agent 反复调用工具是在「努力尝试」吗？** 在目标不可达的任务上恰恰相反：MCPHallu 的数据显示，调用 4 次以上工具的运行通过率为 0%，完成式措辞却随调用次数上升。工具调用积累的是惯性，不是进度；早停并如实报告不可行，是唯一正确行为。

**工具都调对了，为什么结果还是错的？** 语义重叠的混淆工具一旦被调用，其输出就进入了上下文：正确工具单独使用通过率 84.7%，与混淆工具混用后掉到 32.3%。要防的不是「找不到工具」，而是「用错工具还不自知」。

**幻觉测评为什么不能只看最终答案对不对？** 分支坍缩和上下文遗忘都会出现「答案对、路径错」或「路径对、答案错」的分离，工具误用测的更是「是否碰了不该碰的工具」。MCPHallu 用确定性轨迹检查为主（权重 70%–80%）、模型裁判为辅来分离这些情况。
