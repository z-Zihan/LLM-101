# 思维树、思维链和 ReAct 有什么区别？

> 所属专题：[推理能力](./03-推理能力是什么.md) · [Agent 规划](../07-Agent/04-Agent如何规划和恢复.md)
>
> 扩展路线：本篇比较三种推理时编排方式，不把它们当成模型架构或可靠性认证。

一个公开项目已经有思维链机制，开发者仍提出：它不足以比较多条候选路径，希望加入思维树。另一条真实问题则问，ReAct 的“思考 → 行动 → 观察”为什么比一次性计划更适合某些任务，又会带来什么代价？

这几种方法看起来都在“让模型多想一会儿”，实际解决的卡点不同：思维链给一条路径更多中间位置，思维树显式保留并筛选多条路径，ReAct 让路径在执行过程中读取外部环境。名字里都有 Thought，不表示它们展示了模型内部计算的真实录像。

## 一条路线、几条岔路和现实反馈

假设要安排三项维修工作，规则是：断电后才能换线，换线完成才能通电测试；另外还要在两个供应方案里选择一个。

思维链（Chain of Thought，CoT）通常沿一条文本轨迹展开：

```text
读规则 → 选择供应方案 A → 安排断电 → 换线 → 通电测试
```

若开头误判了方案 A，后面的步骤可能在同一路径上继续变得很完整。模型可以重新生成另一条思维链，但单次 CoT 本身没有规定怎样保存候选、比较分支和回退。

思维树（Tree of Thoughts，ToT）把中间状态当成可搜索节点：

```text
当前维修状态
  ├─ 方案 A → 评估：交付快、库存风险高
  │            ├─ 先断电……
  │            └─ 先备件……
  └─ 方案 B → 评估：交付慢、库存确定
               ├─ 调整窗口……
               └─ 改用临时方案……
```

系统生成若干候选“思路单元”，评估哪些状态值得继续，再按广度优先、深度优先、束搜索等策略展开或回退。节点可以是短方案、局面摘要或部分解，不必是一长段自然语言内心独白。

ReAct 则在推理文本与外部行动之间循环：

```text
判断缺少库存信息
  ↓ Action：查询库存系统
Observation：方案 A 缺货
  ↓ 根据新事实调整
Action：查询方案 B 到货时间
```

读图时注意，Observation 不是模型凭空继续写的设定，而应来自工具或环境的实际返回。ReAct 的优势来自“先做低成本探查，再用结果修正下一步”；若工具结果错误或不可信，它也可能把错误带进后续循环。

## 四种常见方法放在一起看

| 方法 | 保留什么 | 怎样选择下一步 | 适合的卡点 | 主要代价 |
|---|---|---|---|---|
| CoT | 一条中间文本轨迹 | 沿当前生成继续 | 需要分步展开的单路径问题 | 早期错误会一路传递 |
| 多样本投票 | 多条完整回答 | 最后投票或打分 | 答案可聚合、路径差异有价值 | 多次调用，仍缺少中途回退 |
| ToT | 多个部分状态和分支 | 生成、评估、搜索、剪枝 | 需要比较候选并可判断中间状态 | 分支成本高，评估器也会错 |
| ReAct | 决策、行动与真实观察 | 根据环境反馈滚动决定 | 搜索、排障、工具使用 | 循环、权限、延迟与状态漂移 |

多样本投票常被叫作自洽性（Self-Consistency）：生成多条推理路径，再聚合最终答案。它和 ToT 都会尝试多条路径，但 ToT 在中间状态就进行评估与搜索，不必等每条路径走到底。

这张表不是互斥产品分类。一个 Agent 可以用 ReAct 读取环境，在某个高影响决策点用 ToT 比较三种方案，再把选中方案交给固定 Workflow 执行。

## 思维树不是一句更复杂的 Prompt

只在 Prompt 里写“请用 Tree of Thoughts 思考”，模型可能输出树状文字，但不一定真的实现了可控搜索。完整 ToT 流程至少要回答四个工程问题：

1. **状态是什么**：当前已经确定的约束、部分解和未决项怎样表示；
2. **怎样扩展**：每个状态生成几种下一步，候选是否去重；
3. **怎样评估**：由模型打分、规则验证、单元测试还是环境模拟判断；
4. **怎样搜索和停止**：保留多少分支，何时回退，预算耗尽或无解时怎么办。

若没有独立状态，所谓“树”可能只是把整段聊天复制很多份。若没有可用评估，系统只是花更多 Token 生成更多同样不可靠的候选。ToT 论文中的任务之所以适合搜索，是因为中间状态至少能被启发式评估；现实开放问题常没有这么清楚的评分函数。

## 什么时候多路径搜索值得

ToT 更适合同时满足几项条件的任务：选择会显著改变后续空间；错误路径可以在中途识别；允许回退；额外调用成本低于选错的代价。例如组合谜题、受约束排程、候选设计比较和部分代码搜索。

一个事实问答、一次格式转换或已有确定步骤的审批流程，通常不需要思维树。多分支不仅更慢，还可能增加互相重复的错误和选择偏差。可预测步骤应优先写成普通程序或[工作流](../07-Agent/05-Workflow和Agent有什么区别.md)，不要把搜索包装成“更智能”。

分支数乘深度会迅速扩大调用量。生产系统通常使用束宽、最大深度、时间和费用上限，只保留少量高分状态；还要检测多个分支是否只是换词重复。成本报告应统计所有生成与评估调用，不能只展示最后一条路径。

## 评估器为什么是核心风险

思维树需要决定“哪条路值得继续”。若让同一个模型同时提出方案和给自己打分，它可能偏爱表达流畅、与首个想法相似或符合错误假设的分支。换一个模型打分也不自动可靠，只是改变了误差来源。

能执行的检查通常更强：数学题用计算器或约束求解器，代码用测试，排程用规则校验，检索任务检查来源是否真实存在。开放写作没有唯一正确答案时，可以先明确受众、事实、长度和禁区，再评价是否满足这些可观察条件。

评估器还要防止“看见答案后泄漏”。如果用测试集答案直接挑选分支，得到的是在该测试上的搜索效果，不能无条件外推到新任务。记录候选数、预算、打分规则和尝试次数，才有可比较的评测。

## ReAct 不是 ToT 的简化版

ReAct 的重点是把行动结果带回决策。它可能始终只有一条当前轨迹，却能通过搜索、文件或 API 获得新信息。ToT 可以完全不调用工具，只在一个给定问题上探索多个候选状态。

两者组合时要格外控制副作用。探索三条“删数据方案”不能真的删三次；系统应在沙箱或模拟状态中比较，选中后再进入审批和执行。只读查询也要限制访问范围，Observation 中的网页或文件内容可能包含 Prompt Injection，不能因为它来自工具就默认可信。

Agent 真正需要保存的是目标、候选状态、工具输入输出、评分依据、审批和最终结果。对外审计可以提供“为什么选择这项动作”的简洁理由和可验证证据，不必把未经核实的长篇隐藏推理当作事实日志。

## 回答开头的问题

**CoT 和 ToT 的关键差别是什么？** CoT 通常沿一条中间文本继续；ToT 显式生成、评估和搜索多个部分状态，并允许剪枝或回退。

**多生成几条答案再投票，就是 ToT 吗？** 不完全是。多样本投票在完整路径末尾聚合；ToT 会在中间节点选择下一批要展开的分支。

**ReAct 为什么适合 Agent？** 它让工具 Observation 改变下一步，不必在未知环境中一次猜完整计划；代价是循环、权限、延迟和不可信结果都要治理。

**什么时候不该用 ToT？** 问题简单、流程固定、中间状态无法可靠评分，或分支成本高于错误代价时，不值得使用。

**树里的 Thought 是模型真实完整思考吗？** 不能这样认定。它是系统选择保存和评估的文本或结构化状态，用于后续搜索，不是内部数值计算的透明录像。
