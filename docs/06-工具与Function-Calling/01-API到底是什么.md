# API 到底是什么？

API 是网址、代码，还是一份说明书？这三个答案都碰到了一部分，却没有说完整。API（Application Programming Interface，应用程序编程接口）是一套软件之间交互的约定：允许做什么、输入长什么样、怎样认证、成功返回什么、失败怎样表达。

界面面向人，API 主要面向程序。你点击聊天产品里的“发送”，产品后端可能再调用模型 API；两者相关，却不是同一个产品层。

## 从一次天气查询看完整契约

天气应用不需要自己在每座城市装温度计。它可以向天气服务请求“上海现在的天气”，服务返回温度、天气状况和更新时间，应用再把数据展示给用户。

```text
天气应用（Client）
  ↓ 按 API 约定发送 Request
天气服务（Server）
  ↓ 查询并处理
Response：数据、状态或错误
```

这张图想说明 API 连接的是两个软件角色。读图时注意，地址只告诉请求发往哪里；请求方法、字段、认证、响应和错误规则共同构成可用接口。

常见 HTTP API 的请求可能包含 Endpoint、Method、Headers 和 Body。响应通常包含状态码、数据或错误信息。具体结构由服务文档和版本决定，不能把一家厂商的字段当成通用标准。

API 也不一定走网络。操作系统向应用暴露文件接口，代码库向开发者暴露函数，也属于 API。日常说“调用模型 API”时，多半指通过网络访问模型服务。

## 调用模型 API 时发生什么

应用把输入、模型选择和必要配置按约定发送给服务。服务完成推理并返回文本、结构化内容、工具调用请求或错误；应用再决定怎样展示、保存或继续处理。

```text
用户界面
  ↓
你的应用：权限、历史、业务规则
  ↓ 调用模型 API
模型服务：执行推理
  ↓ 返回结果
你的应用：验证并继续工作
```

这张图把“模型”和“聊天产品”拆开。读图时最重要的是中间的应用层：历史记录、Memory、文件、搜索、计费和安全策略通常不由一个裸模型 API 自动提供。

API 返回 HTTP 成功，只说明请求在接口层完成，不证明生成内容在事实或业务上正确。超时、限流和格式错误要按工程错误处理；模型幻觉、工具参数不合理则需要内容和业务验证。

## API Key 只是身份凭证的一层

API Key 常用于识别调用方，并关联权限、配额和费用。它应保存在服务端的安全配置中，不要写进公开仓库、浏览器前端或日志。

“持有 Key”也不等于可以执行任何操作。真实系统还要做用户身份验证、资源授权、参数校验、速率限制和审计。一个能调用模型的 Key，不能替代用户访问某份订单或文件的权限判断。

## API、SDK、模型和 UI 怎么分

API 是交互契约；SDK 是帮助开发者调用 API 的代码库和工具；模型负责计算；UI 是人直接操作的界面。SDK 可能替你构造请求、处理流式响应，但底层仍受 API 契约约束。

同一个模型可能通过不同产品和 API 使用，一个 API 也可能提供多个模型或其他服务。模型版本升级不必然等于 API 地址变化，API 兼容也不保证模型行为完全相同。

OpenAPI 这类规范可以机器可读地描述 HTTP API 的路径、操作、参数和响应，便于生成文档或客户端。它描述“怎样连接接口”，不决定模型是否应该调用，也不自动提供 Agent 循环。

## 生产系统还要处理哪些现实问题

网络会超时，服务会限流，返回可能不完整，重复请求还可能造成重复写入。应用要设置合理超时和重试策略，并区分可以安全重试的读取与可能产生副作用的付款、发送、删除。

接口也会演进。生产代码要关注版本、弃用通知和官方变更说明，为未知字段和明确错误保留处理路径。不要把今天观察到的限制写成永远不变的常识。

## 回答开头的问题

**API 是一个网址吗？** 网址可能是 Web API 的 Endpoint；完整 API 还包括操作、输入输出、认证、错误和版本约定。

**API 是一段代码吗？** 调用方和服务方会用代码实现接口，SDK 也提供代码封装，但 API 指的是双方约定的边界。

**调用模型 API 等于打开聊天产品吗？** 不等于。聊天产品通常还包含 UI、账号、历史、系统提示、工具和业务策略。

**API 调用成功，结果就可信了吗？** 不代表。接口成功与事实正确、权限合理、业务完成是不同层的检查。
