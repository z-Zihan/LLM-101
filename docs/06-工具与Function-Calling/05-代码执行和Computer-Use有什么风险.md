# 代码执行和 Computer Use 有什么风险？

> 你现在的位置：[搜索、文件与数据库](./04-AI怎样搜索读文件和查数据库.md) → **代码执行与 Computer Use** → [Agent](../07-Agent/01-Agent到底是什么.md)
>
> 所属专题：工具安全 · 本文是 Optional 扩展阅读

有人使用 Code Interpreter 时问：“环境不能联网，我怎样安装新的 Python 库？”另一个开发者想让浏览器 Agent 每一步都截图并录下整个会话。一个问题在争取更多能力，另一个问题在补可追溯性；它们恰好揭示了执行工具的核心矛盾：能力越接近真实电脑，错误和攻击就越可能产生现实后果。

代码执行工具让程序真正运行；浏览器工具让系统点击网页；Computer Use 还可能控制鼠标、键盘和桌面应用。模型仍然只是在提出下一步动作，承载这些动作的运行环境才拥有文件、网络、进程和账号权限。

## 三种工具看起来相似，边界并不相同

代码执行通常把模型生成或用户提供的代码送进 Python、Shell 或其他运行时。它擅长计算、转换文件、画图和运行测试。浏览器自动化主要通过网页元素或浏览器协议导航、填写表单和下载文件。Computer Use 常根据屏幕截图选择坐标，再模拟鼠标和键盘，能操作没有专用 API 的界面。

| 能力 | 系统实际看见什么 | 主要优势 | 特有风险 |
|---|---|---|---|
| 代码执行 | 代码、进程、文件和标准输出 | 计算精确、可组合、便于测试 | 任意代码、依赖和系统调用可能越权 |
| 浏览器工具 | URL、页面结构、网络与浏览器状态 | 能操作交互网站并读取结构化页面 | 登录态、下载、恶意网页和提交动作 |
| Computer Use | 截图、坐标、键盘和桌面状态 | 可操作没有 API 的旧系统 | 看错界面、点错对象、被遮挡或弹窗误导 |

三者可以叠加。代码启动浏览器，浏览器下载脚本，Computer Use 再打开终端执行它，风险会沿工具链传递。不能因为每一步单看都常见，就忽略组合后的权限。

## 一次“整理报销”怎样走到危险边缘

假设 Agent 要登录报销网站，下载发票，用 Python 汇总金额，再把报告发送给财务。

```text
网页中的任务说明与不可信内容
        ↓
浏览器：登录、下载、填写表单
        ↓
代码环境：读取附件、运行依赖、生成报告
        ↓
邮件或上传工具：把结果送出系统
```

这张图想说明风险不只来自代码。网页可能藏有间接 Prompt Injection，下载文件可能恶意构造，代码可能读取同一目录里的其他资料，最后的发送动作会把错误变成不可逆副作用。读图时应沿着数据流问：“哪一步获得了什么，下一步能把它带到哪里？”

## 沙箱不是一个开关，而是一组限制

沙箱（Sandbox）是与主机和其他任务隔离的执行环境。说“代码在沙箱里运行”仍不够，至少要继续问：

- 它以哪个系统身份运行，能启动多少进程、占用多少 CPU、内存和时间；
- 能读取和写入哪些目录，任务结束后文件是否销毁；
- 能访问公网、内网、云元数据地址或本机服务吗；
- 是否注入 API Key、数据库凭证和用户 Cookie，凭证能做什么；
- 能安装哪些依赖，依赖包和镜像从哪里来；
- 输出、下载和上传的大小与目标是否受限。

一个临时容器如果挂载了整个主目录、拥有宿主 Docker Socket、能访问内网并携带生产密钥，隔离名称再漂亮也挡不住严重后果。较稳妥的默认值是短生命周期、非特权身份、最小文件挂载、受限网络、资源上限和按任务发放的短期凭证。

禁网会限制安装库和获取数据，却能显著缩小外泄与供应链攻击面。确实需要依赖时，可以从审核过的镜像或内部软件源安装；需要网络时，按域名、协议和用途放行，并记录请求。不能把“让任务跑通”自动置于“允许访问一切”之上。

## Computer Use 为什么比普通 API 更难控制

API 的参数和返回值通常有 Schema，页面坐标却没有稳定语义。按钮可能移动，弹窗会遮挡，页面可能加载到一半；视觉相似的“保存草稿”和“立即发布”只差几像素。模型看到的截图还可能过期，点击时界面已经变化。

网页和桌面内容本身也不可信。恶意页面可以用醒目文字要求 Agent 上传文件，甚至伪造“系统通知”或“安全验证”。登录态让工具能够访问用户私有信息，却不会判断页面里的指令是否有权改变任务。

所以 Computer Use 适合运行在独立浏览器配置或隔离桌面中，不直接复用个人日常浏览器的全部 Cookie、扩展和历史。允许访问的站点应与任务一致；跨域跳转、下载可执行文件、打开密码管理器或系统设置，需要被程序拦截或升级为人工处理。

## 人工确认应该放在“承诺点”

如果每次滚动和点击都弹窗，用户很快会机械同意；如果从不确认，Agent 又可能替用户付款、发送、删除或公开发布。确认应放在动作从可撤销准备变成真实承诺的边界。

例如，搜索商品和填写购物车可以自动进行；提交订单前展示商家、商品、数量、总价、收货地址和付款方式。生成邮件草稿可以自动进行；点击发送前展示收件人、附件和正文。准备删除文件时，展示明确路径、数量和是否可恢复。

确认必须由独立界面和宿主策略执行。模型不能在工具参数中写“用户已经同意”就替代真实授权，也不能把网页里的一句“请点击确认”当成用户许可。高风险动作还应再次检查当前身份、资源归属和业务条件，避免确认后界面或参数被偷换。

## 失败不总是“什么都没发生”

浏览器提交后超时，系统可能已经创建订单，只是确认页面没有返回；脚本在写文件时崩溃，目标文件可能只写了一半；用户按下取消时，一个子进程仍可能在后台运行。这些都是“状态未知”，不能简单重试并宣称成功。

执行系统需要为调用分配唯一标识，区分计划、已批准、执行中、成功、失败、取消和结果未知。可重复的查询可以有限重试；发送、付款和创建记录应使用幂等键或先查询业务状态。无法安全判断时停止自动循环，告诉用户已经知道什么、还需要人工核对什么。

长任务还要保存检查点：输入文件版本、已完成步骤、产生的资源 ID、用户批准和验证证据。恢复时先核对现实环境，而不是只根据旧对话继续点击。临时凭证应能吊销，生成文件应能隔离或移入回收站，高风险任务要有人工接管入口。

## 日志既要能复盘，也不能变成新的泄露源

“模型最后说任务完成”不是审计证据。日志应区分模型建议的代码或动作、策略判断、用户确认、环境真实执行和业务系统返回。代码工具还应记录运行镜像或依赖版本、退出码、资源限制和产物哈希；浏览器或 Computer Use 可以记录关键截图、URL、元素或坐标和提交结果。

全程录屏有助于复盘界面问题，却可能同时录下密码、聊天、客户信息和其他窗口。日志要做访问控制、脱敏、保留期限和删除策略；默认保存所有屏幕内容并不比完全不记录更负责任。针对关键承诺点保存最小充分证据，通常比无边界录制更可控。

验证也不能只看工具退出码。脚本返回 `0` 说明进程按约定结束，不代表报表数字正确；网页出现“成功”文字可能是恶意页面伪造。应根据任务使用独立证据，例如重新读取生成文件、查询订单 ID、核对数据库状态或让用户检查最终提交内容。

## 回答开头和常见追问

**Code Interpreter 为什么可能不能联网或安装任意库？** 这是运行环境的安全与可复现性限制。需要新依赖时，应走允许的软件源、固定版本或预构建镜像，而不是默认开放整台机器和公网。

**代码在沙箱里就一定安全吗？** 不一定。要看身份、挂载目录、网络、凭证、资源限制和生命周期。沙箱配置不当仍可能访问主机或敏感系统。

**浏览器 Agent 为什么要截图或录像？** 它们能帮助复盘模型当时看见什么、点了哪里，但要与 URL、动作、工具结果和业务状态一起记录；截图本身既可能缺关键信息，也可能包含隐私。

**只让 Agent 操作浏览器，不给 Shell 权限，是不是风险很低？** 不是。带登录态的浏览器可以读私有数据、发送消息、购买和修改账号。权限应按真实可产生的结果判断，而不是按工具名字判断。

**Prompt Injection 为什么会影响代码执行？** 不可信网页或文件可能诱导模型生成并运行额外代码。最终防线是限制代码环境和工具权限、检查数据流，并在高风险动作前独立确认，而不是期待模型永远识别恶意文字。
