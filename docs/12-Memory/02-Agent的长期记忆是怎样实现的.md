# Agent 的长期记忆是怎样实现的？

> 所属专题：Memory · 前置：[聊天记录是什么](./01-聊天记录是什么.md) · 后续：[上下文压缩是什么](../11-Coding-Agent/13-上下文压缩Compaction是什么.md)

上一篇讲聊天记录时，你见过这个结论：[聊天记录](./01-聊天记录是什么.md)是产品保存的历史消息，只有被重新选入[上下文](../02-聊天Token与上下文/07-上下文和上下文窗口是什么.md)，才会影响这一次回答。那么顺着问下去：ChatGPT 说它"记住了你喜欢简洁的回答"，Claude Code 在新会话里知道你项目的构建命令，Coding Agent 断点续跑时还记得上次改到哪个文件——这些"记住"是怎么做到的？既然模型每次请求都是无状态的，跨会话的信息到底放在哪里、什么时候回来、回来多少？

> Agent 的记忆不是模型自带的能力，而是一套系统设计：把信息存起来，在合适的时机把合适的部分取回来放进上下文。存什么、怎么取、取多少，每一步都有取舍。

这一篇把这套系统拆开看。先看清"记忆"在产品里到底有几种形态，再走一遍记忆系统的完整闭环（写入、存储、检索、使用），然后看工程上的主要方案——外挂数据库、压缩沉淀、Agent 自我反思——最后看 2026 年 10 月刚出现的新路线：把记忆直接做进模型架构里。

## 先分清：你说的"记住"是哪一种

打开 ChatGPT 的设置，你会发现"记忆"其实是两个开关：一个是"保存的记忆"（Saved Memories）——你说过"我喜欢简洁回答"之后，它把这条偏好写成一条独立记录存起来；另一个是"参考聊天历史"（Reference Chat History）——它在新对话里自己去翻你的旧对话，找到相关内容再回答。两个都叫记忆，实现方式完全不同：前者是显式的、用户可以逐条编辑删除的结构化记录；后者是对历史对话的按需检索。

这个区分值得放大，因为工程上的"Agent 记忆"几乎都落在这三种形态的组合里：

- **原文留存**：聊天记录、操作日志原样保存，需要时检索取回。信息无损，但量大、噪音多。
- **结构化沉淀**：把对话里值得长期保留的信息提炼成一条条独立记录（用户偏好、项目决策、账号配置），带时间戳、可更新、可删除。ChatGPT 的 Saved Memories 就是这一种。
- **模型内状态**：把历史信息压缩成模型的内部状态（隐藏状态或参数），不依赖外部存储。

最后一种目前还是研究前沿，主流产品用的都是前两种的组合。但先别急着看实现——一个记忆系统要正确工作，得先走通一个完整的闭环。

## 记忆系统的闭环：写入、存储、检索、使用

把 Agent 的记忆系统想象成一个图书馆，四个环节缺一不可：

**写入（What to write）**：对话进行中，判断哪些信息值得长期保留。用户说"以后都用 TypeScript"——这是偏好，值得记。用户说"帮我写个排序"——这是任务，做完就可以丢。写入决策可以由规则做（比如保存 设置页里的显式内容），也可以让模型自己判断（Mem0 这类系统用 LLM 从对话中抽取候选记忆，再做去重与合并）。写错比不写更糟：一条过时的记忆会在未来无数次对话里持续误导模型。

**存储（Where to keep）**：写下来的信息放在哪。可以是一条数据库记录、一个 Markdown 文件、一个向量库条目，或者——后面会讲到的——模型参数本身。存储形态决定了后面怎么检索。

**检索（When and what to recall）**：新请求到来时，决定取哪些记忆、放进本次上下文。这是整个系统里最容易被低估的环节。检索不是"把所有记忆都塞回去"——记忆条目一多，全量注入等于把上下文窗口变成垃圾场，既贵又稀释注意力（回忆一下[上下文窗口](../02-聊天Token与上下文/07-上下文和上下文窗口是什么.md)的预算概念）。实际系统都做相关性过滤：用[向量检索](../08-RAG与知识库/03-Embedding是什么.md)按语义相似度召回，再按时间、重要性、访问频率加权排序。生成式智能体（Generative Agents，斯坦福 2023 年的小镇实验）把这套打分公式写得很清楚：相关性 × 新近度 × 重要性，三个分数加权综合。

**使用（How to use）**：取回的记忆以什么形式进入上下文。直接拼进系统提示？作为一条"系统注意事项"？还是作为检索结果片段？形式影响模型对它的"信任权重"。同时还要处理冲突：新记忆和旧记忆矛盾时，谁赢？成熟的做法是让新证据覆盖旧记录并保留更新时间，而不是让两条矛盾记忆同时在上下文里打架。

这四步里藏着记忆系统与 [RAG](../08-RAG与知识库/01-RAG到底是什么.md) 的本质关系：**记忆系统和 RAG 共用同一套"检索后注入"的机制，差别在存储内容的性质**。RAG 的语料是相对静态的知识文档；记忆系统的内容是动态的用户数据和交互历史，需要持续写入、更新、过期和删除。所以业内常说"记忆是带生命周期的 RAG"——机制同源，管理复杂度完全不同。

## 主流实现：三种工程方案

围绕上面这个闭环，工程上形成了三种主要方案。它们不互斥，实际系统常常叠加使用。

### 方案一：外挂数据库（今天的主流）

把记忆做成模型之外的存储层，最典型的是 Mem0：一个 LLM 从对话中抽取候选记忆，另一个 LLM 决定每条候选是新增、更新还是删除，存进结构化存储（可选向量库加速检索）；下次对话时按语义检索相关条目，注入上下文。在 LOCOMO 这个多会话记忆基准上，Mem0 论文报告的准确率超过了把完整对话历史全量塞进上下文的做法，同时延迟和 token 消耗低一个数量级——全量历史的成本随会话数线性增长，检索式记忆只取需要的几条。

开源生态里还有 MemOS 这类"记忆操作系统"定位的框架，把明文记忆、KV 缓存、参数化记忆统一调度管理。方向相同：记忆是系统层的资源，需要专门的管理和调度机制，就像操作系统管理内存一样。

外挂方案的好处是可控：每条记忆可查看、可编辑、可删除，出了错能定位。代价是系统复杂度——写入判断、检索排序、冲突处理都要自己搭，而且检索质量直接决定记忆质量（这继承了 RAG 的全部老问题：检索不到等于没记住）。

### 方案二：压缩与沉淀（Coding Agent 的选择）

Coding Agent 处理的是另一个极端：单次会话内动辄几十万 token 的上下文。它们的记忆策略围绕"上下文不够用"展开：

- **会话内压缩**：上下文快满时，把早期历史摘要压缩，保留关键约束和状态——这是[上下文压缩](../11-Coding-Agent/13-上下文压缩Compaction是什么.md)的主题；
- **跨会话沉淀**：把稳定信息写入项目里的持久文件。Claude Code 的 CLAUDE.md、Cursor 的 Rules、各种 AGENTS.md，本质都是"项目记忆"：构建命令、代码规范、踩过的坑，下次会话自动加载。它不靠智能检索，靠约定路径 + 全量注入——简单，但文档膨胀后同样消耗预算；
- **任务清单外置**：Agent 把执行进度写成结构化清单（todo list），压缩或中断后从清单恢复，而不是从对话历史里"回忆"。

这套方案的价值取向是"让正确的信息在压缩后幸存"。它承认上下文有限，用工程手段管理稀缺性。

### 方案三：自我反思与生成（记忆的"深加工"）

斯坦福的生成式智能体实验展示了第三种可能：Agent 不仅存原文，还定期对自己的记忆做"反思"（Reflection）——从大量底层观察中合成更高层的结论。比如 Agent 观察到用户多次提到乐队和写歌，反思后生成一条新记忆"用户在筹备出道演出"。检索时这些高层结论和底层观察一起参与排序，让 Agent 的行为既有细节又有大局观。

这个思路影响了后来几乎所有记忆系统的设计：记忆不只是存取，还需要加工层次——从原始事件到结论，从具体到抽象。反思本身也要消耗模型调用，所以工程实现里通常做成低频后台任务，而不是每次对话都做。

### 一个统一视角：分层存储

三种方案摆在一起，你会发现它们其实在回答同一个问题：**信息按什么生命周期分层**。

| 层次 | 典型载体 | 生命周期 | 类比 |
|---|---|---|---|
| 工作记忆 | 当前上下文窗口 | 单次请求 | 人的即时注意力 |
| 短期记忆 | 会话历史 + 压缩摘要 | 单次会话 | "今天聊了什么" |
| 长期记忆 | 外部存储 / 记忆文件 | 跨会话持久 | "我对这个人的了解" |
| 参数记忆 | 模型权重 | 训练时写入 | 已内化的技能与知识 |

任何记忆方案都是这几层之间的搬运策略：什么该从工作记忆降到短期，什么该沉淀为长期，什么值得写进参数。分层的价值在于生命周期和权限不同——把所有内容都做成永久记忆，过期日志和敏感信息会长期传播；全都留在临时上下文，新会话后一切归零。

## 新路线：把记忆做进模型里

前面所有方案的共同点是：记忆在模型**外面**。2026 年 10 月，MemTensor 团队发表的 MemT-1.0 给出了另一个答案——记忆基础模型（Memory Foundation Model）：让模型架构本身携带一个持久、可动态演化的记忆状态。

它的前身 Metis（2026 年 7 月）已经提出了基本思路：给基座模型内置一个"原生记忆状态"，历史信息不再是越攒越长的 token 序列，而是被压缩进模型主干的记忆状态里持续更新；模型还可以通过自身计算自主决定存什么、取什么。MemT-1.0 把这个思路做成了可用的模型家族（Nano 和 Flash 两档），两个关键技术：

**一是改造骨干网络**。标准 Transformer 的注意力是"无状态"的——每个 token 的 KV 值平等存储，历史一长，缓存就大。MemT-1.0 采用 Gated DeltaNet-2（门控增量网络），这是线性注意力方向的架构：它把历史压缩成一个固定大小的记忆矩阵，每个新 token 到来时不是"追加存储"，而是"增量更新"——有用的新信息写入，相关的旧信息被覆盖调整。压缩必然有损，这正是设计取舍：用"记不清所有细节"换"记得住关键信息且成本恒定"。

**二是扩大记忆容量**。固定大小的记忆矩阵很快成为瓶颈，MemT-1.0 引入混合存储（Mixture-of-Storage），类似 [MoE](../03-模型原理与训练/02-模型架构是什么.md) 的路由思想——多个存储模块，按需激活一部分，让记忆容量随模块数扩展而不必让每个 token 都触碰全部存储。

官方报告的数字：在 128K token 历史长度下，端到端推理加速约 1.86 倍，持久存储相比全量 KV 缓存减少约 66 倍；记忆评测上超过参数化记忆基线，与检索增强方法持平，同时通用能力基本不损失。把检索到的"程序性经验"（怎么做事的步骤）内化进记忆后，Agent 任务的成功率还有提升。

这是不是意味着外挂记忆要被淘汰了？下结论为时尚早，有三条边界要看清：

1. **规模**。MemT-1.0 的模型规模和训练数据量都远小于前沿大模型，"记忆原生"在更大规模上是否同样有效，还没有证据。
2. **有损与可控的矛盾**。架构内记忆是有损压缩，用户无法像编辑 Saved Memories 那样查看、修正模型"脑子里"记的东西。记忆错误变得不可解释、不可审计——对准确性要求高的场景，这可能是致命的。
3. **生态**。外挂方案不换模型就能用，架构方案要求你换掉整个基座。企业已有的基础设施投资决定了过渡期会非常长。

更可能的中期图景是混合：架构内记忆处理高频、即时的状态，外挂存储处理需要精确回查和审计的关键数据——就像 CPU 缓存和硬盘的关系，谁也没有取代谁。

## 常见误解与边界

**"模型记得我"= 模型变强了？** 多数时候不是。ChatGPT 记得你的偏好，是产品层的记忆系统在起作用，模型的参数可能从没变过。区分"产品记忆"和"模型能力"很重要：换一个没有记忆功能的产品，同一个模型立刻"失忆"。

**记忆等于微调吗？** 不是。[微调](../03-模型原理与训练/11-RLHF和DPO是什么.md)改参数，成本高、周期长，适合固化稳定能力；记忆是运行时信息管理，即时生效、即时可改，适合用户数据和会话历史。两者粒度也不同——微调很难精准记住"用户对花生过敏"这类具体事实，还容易伤害通用能力；这恰恰是外部记忆的舒适区。什么时候该微调、什么时候该上记忆，取决于信息是"能力"还是"事实"。

**记忆越多越好吗？** 记忆系统的失败模式恰恰常常是"记得太多"：过时记忆持续误导（用户三年前喜欢 Java，现在写 Rust 了）、错误记忆无法清除（一次误写入长期污染回答）、检索噪音稀释注意力。记忆系统需要遗忘机制和冲突消解，就像人需要忘记不重要的事。

**记忆是隐私敏感操作。** 记忆的内容是用户数据，存储位置、保留期限、删除机制都直接关联隐私责任。设计记忆系统时，"用户能看到并删除关于自己的记忆"应该是默认要求，而不是可选项。

## 回到开头的问题

现在可以回答开头那串问题了。ChatGPT 的"记住"，要么是显式的记忆条目（方案一的结构化沉淀），要么是对历史对话的检索（原文留存），两者都在模型之外，通过"检索后注入上下文"生效。Coding Agent 的跨会话记忆主要靠约定路径的记忆文件和结构化状态外置（方案二）。模型参数在大多数"记住"的场景里根本没有参与。

记忆系统的本质公式：**记忆 = 有生命周期的信息 × 检索式使用**。写入决定记什么，存储决定怎么放，检索决定何时用，使用决定多大权重——四步任何一步做错，记忆都会从资产变成负债。RAG 和记忆共享机制而分工不同：RAG 管知识，记忆管"关于这个用户/这个项目的事实"。架构内记忆（MemT-1.0）刚刚开了个头，它把"检索"这个最脆弱的环节内化成了模型计算，但可控性和规模的考卷都还没答完。

下一次 AI 对你说"我记住了"，你可以追问一句：记在了哪一层？什么时候会被取出来？以及——我能删掉它吗？
