# 聊天记录是什么？

> 你现在的位置：[Coding Agent](../11-Coding-Agent/04-Coding-Agent是什么.md) → **聊天记录**
>
> 课程导航：[上一篇：Coding Agent 是什么](../11-Coding-Agent/04-Coding-Agent是什么.md) · 第 28 / 28 篇 · 主路线结束

聊天记录或对话历史（Conversation History）是产品保存的一系列用户消息、助手回复和相关事件。

它不等于模型能在本次计算中看到的全部[上下文](../02-聊天Token与上下文/07-上下文和上下文窗口是什么.md)，也不等于模型参数里的长期记忆。

## 页面可见和模型可见不是一回事

一个聊天页面可能显示过去 200 条消息，但本次请求实际发送给模型的可能是：

```text
系统指令
 + 最近若干消息
 + 更早对话的摘要
 + 当前检索到的相关记录
```

“界面还能翻到”不保证每个字都再次进入模型上下文。

反过来也可能发生：界面只展示普通消息，模型请求里却还包含系统指令、工具结果或产品检索出的相关记录。用户看到的是产品界面，模型处理的是一次请求的输入，两者有关联，却不是同一份数据结构。

## 产品怎样使用历史？

应用可以：

- 原样发送最近消息；
- 截断过旧内容；
- 把早期对话总结后发送；
- 只检索与当前问题相关的片段；
- 把工具调用和结果也保存为事件；
- 完全不保存某些临时会话。

具体行为取决于产品设计、隐私设置和容量限制。

因此“模型忘了”至少有三种可能：旧消息没有再次进入上下文；旧消息进入了，但被摘要损失或被大量内容淹没；信息其实被正确使用，只是模型仍然推断错了。只看最终一句回答，很难判断是哪一层出了问题。

## 聊天记录、上下文与记忆的区别

```text
聊天记录：保存过的对话记录
上下文：本次模型计算实际可用的信息
记忆：系统跨会话保存并在未来取回的信息机制
```

聊天记录可以成为上下文或记忆的来源，但三者不是同义词。

比如你在三个月前说过“我更喜欢简短回答”。这句话可以一直留在聊天记录里，却从未被再次发送给模型；产品也可以把它提取为一条偏好记忆，在新会话中按需加入上下文。真正影响当前回答的是最后进入本次上下文的内容，而不是它最初存在哪个页面。

## 为什么会丢失早期细节？

- 上下文窗口有容量上限；
- 系统可能截断或总结旧消息；
- 摘要会丢失细节；
- 检索可能没有选中相关历史；
- 内容进入窗口也不保证被正确利用。

因此重要事实不应只依赖很久以前的一句聊天。

对长任务，更稳妥的做法是把关键约束写进当前可核验的计划或项目文件，并在压缩后检查它们是否仍然存在。聊天记录适合保留过程，稳定规则则需要更明确的状态载体。

## 保存聊天会训练模型吗？

不会自动发生。保存记录是产品数据状态；训练模型需要独立的数据处理和训练流程。

某些服务可能依据其政策使用部分数据改进模型，但这属于具体产品的数据政策，不能从“有历史记录”直接推出。

这里还要区分“当前对话让模型临时适应”和“训练后模型参数改变”。模型根据前文改变语气，是在使用上下文；只有独立训练流程更新了参数，才属于模型训练。两者在界面上都可能表现为“它好像学会了”，技术过程却不同。

## 隐私与控制

聊天记录可能包含个人信息、文件内容和凭证。产品需要定义保存期限、访问权限、删除能力和是否用于其他目的。用户也不应在不可信会话中发送秘密。

## 三个常见误判

### 聊天窗口里可见，模型就一定看得见

界面状态与模型请求上下文是不同层。

### 模型提到旧消息，就永久记住了

它可能只是当前上下文包含历史或摘要。

### 删除界面消息就一定删除所有副本

具体删除范围取决于产品存储、备份和政策，需要查看官方说明。

## 把边界收回来

聊天记录是产品保存的消息与事件；上下文是本次模型实际拿到的信息；记忆是跨会话保存并在未来取回信息的机制。三者可以互相提供来源，但不应混为同一个存储层。

保存记录也不自动训练模型。具体服务是否使用数据改进模型、保存多久和怎样删除，必须查看当前产品政策，不能从“页面有历史”自行推断。
