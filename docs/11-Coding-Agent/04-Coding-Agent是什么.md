Coding Agent 是面向软件项目的 Agent。它不只生成代码片段，还会读取仓库、搜索符号、编辑文件、运行测试和构建，并把真实环境结果带回下一轮决策。

关键差异不只是“模型更会写代码”，而是项目上下文、开发工具、Agent Loop 和权限边界组成了完整系统。

## 一次任务如何形成闭环

```text
读取需求与仓库规则
  ↓ 搜索相关文件、符号和历史
制定或调整步骤
  ↓ 编辑代码
运行测试、类型检查或构建
  ↓ 读取真实结果
修复、验证或明确受阻
  ↓
交付 Diff 与证据
```

这张图想说明“写完代码”只是中间步骤。读图时注意，完成必须由测试、构建、业务行为或其他证据支持，不能只靠 Agent 宣布。

## 为什么不能把仓库一次读完再修改

仓库可能远大于上下文窗口，而且开工时并不知道哪些文件真正相关。Coding Agent 使用 `rg`、`find`、符号导航和目录读取逐步缩小范围；修改后再用测试、构建和 `git diff` 获取新证据。

工具循环不是模型能力不足的补丁，而是软件任务的现实结构：代码、依赖、运行环境和当前变更都在模型参数之外。一次性读取会混入大量无关内容，后续代码或测试结果还会让早期判断过期。

每次工具调用都应有问题意识。搜索用于定位定义和引用，测试用于验证行为，Git Diff 用于检查实际改动；机械重复命令却不更新假设，只会浪费上下文。

## 为什么需要项目级上下文

同一个需求在不同仓库有不同架构、依赖、测试和约定。Agent 要读取代码、配置、文档、Git 历史和 `AGENTS.md` 等规则，不能用训练记忆猜当前项目。

大型仓库也不能全部塞入上下文。文件搜索能找到文本，符号导航还能追踪定义、引用、类型和调用关系。公开真实需求提出“像 IDE 一样的语义导航”，正因为只读原始文件会在跨文件关系中浪费上下文并漏掉依赖。

## 工具和权限同时扩大能力与风险

终端允许 Agent 运行真实测试，Git 提供 Diff、历史和可恢复边界。文件写入、命令、网络和发布权限也可能删除数据、泄露凭证或影响外部系统。

终端、Shell、命令和真实进程分别承担什么，见：[Shell 和 Command 是什么](./02-Shell和Command是什么.md)。

因此应使用沙箱和最小权限，对破坏性或外部副作用操作确认，避免把密钥写入日志。能修改仓库不代表应自动合并、推送或发布。

## 怎样判断任务真的完成

Diff 要与需求一致，相关测试、类型检查和构建通过；新增逻辑应覆盖失败路径和边界；没有意外文件、调试残留或被削弱的断言。无法验证的外部条件要明确记录，高风险变化仍需人工 Review。

Benchmark 只能测特定任务和环境，不能替代生产权限、私有依赖和发布门禁。最终应审查代码和证据，而不是只看模型名称或运行轮数。

## 设计一个 Coding Agent 要补哪些系统能力

一个可用设计通常包括：

1. 项目发现：规则、目录、语言、构建与 Git 状态；
2. 检索：文本、符号、依赖和按需文件读取；
3. 编辑：结构化 Patch、冲突检测和用户变更保护；
4. 执行：沙箱命令、超时、资源和网络限制；
5. 验证：测试、类型、构建、静态检查和业务证据；
6. 恢复：检查点、可逆 Diff、失败分类和取消；
7. 权限：读取、写入、命令、密钥、提交和发布分层授权；
8. 观测：轨迹、工具输入输出、成本和最终产物。

“Git 回滚”不能依赖破坏性清空工作区。Agent 应先识别哪些变化属于用户，优先用小 Patch、反向修改或独立分支，并在任何会覆盖数据的操作前确认目标。

## Harness 能不能自己改进自己

前面列出的系统能力合在一起，就是业界所说的 Harness：模型参数之外、决定 Agent 怎么干活的整套运行时脚手架。前几节默认它由工程师设计、发布后基本冻结；这一节讨论一个更新的问题——它能不能自己改进自己。

2026 年 10 月，这个方向的工作集中出现，可以看作一个子领域的成型标志。Harness²（arXiv:2610.14224）代表"模型冻结、只改脚手架"的路线：它把 Harness 拆成系统提示、护栏、记忆、技能、工具指引、脚本、子 Agent、中间件八个文件级组件，让一个编辑器模型针对当前任务提出两份修改——一份盯可能跨领域复现的通用缺陷（计划、工具使用、上下文管理），一份盯当前领域的知识与流程——然后把修改前后的 Agent 在同一任务、同一环境下各跑一遍，用行为对比代替评分：不看输出"对不对"，只看目标缺陷的行为有没有缓解、有没有引入退化，最后只把有证据支持的修改组合进新 Harness。

两处设计值得细看。其一，没有标准答案也能改：开放世界的任务大多没有真值和验证器，Harness² 不假装能验证正确性，只利用"只变 Harness、其他全部相同"带来的可比性。这是它敢用执行证据的原因，也是证据的边界——执行有随机性，模型判断有共同偏差，行为对比只能支持"这个改动缓解了那个缺陷"，不保证任务做对，更不保证改动能迁移到别的任务。其二，改进过程本身也被沉淀：每个任务结束后，系统回顾整个改进记录，把"什么改动、在什么条件下、产生了什么后果"写成经验条目存入改进库；下一个任务仍从通用 Harness 出发，但提案和组合会参考库里的组件与教训，而不是整体继承上一个任务的特化配置。这就是两层递归：第一层改当前任务的 Harness，第二层改"以后怎么改 Harness"。消融实验中去掉经验库、去掉两路分工提案、去掉证据组合都会掉分；在 JobBench 上攒出的库搬到 WorkBuddy-Bench 仍然有效。结果上，一步改进就让 GLM-5 和 Gemini 3.5 Flash 在三个职业基准上全部上涨（最高 +11.5 分），递归预算加大还能继续涨；弱模型配上改进后的 Harness 甚至能反超强模型配原始 Harness。另一个反直觉的细节：编辑器不需要是更强的模型，多个模型用自己改自己，全部基准都有提升。

同一窗口还有两条互补路线，合起来看更完整。Self-HPO（arXiv:2610.22791）指出只改一边是次优的：Harness 调优针对的是旧模型的失败模式，而策略训练又受限于固定 Harness 产出的轨迹，于是它让两者交替进化——策略模型先分析自己的失败并提出 Harness 候选，再用强化学习在选定 Harness 下更新策略，训练中暴露的难题反过来构成下一轮 Harness 搜索的目标；Qwen3.5-35B-A3B 的平均解决率从 57.8% 提到 64.8%，增益还能带到分布外任务。Self-Evolving Agent Harness（arXiv:2610.18813）则退后一步做形式化：把 Harness 自进化定义为"被接受的修改跨运行持久生效"的反馈过程，区分解释态修改（提示、记忆）与代码级修改（工具、控制逻辑），用进化搜索刻画整个过程，并给出泛化界与修改准入规则，强调可靠部署需要持续验证和独立的安全护栏——当修改能跨运行持久生效，信任、权限与问责就成了工程问题，而不只是提示词写法问题。

对自建 Agent 的开发者，当下值得搬的不是完整递归框架，而是三个便宜的做法：把 Harness 拆成可独立修改的组件文件（这是所有路线的前提）；让改动依据行为对比而不是模型自我评分（避免"自己说自己变好了"）；给每条经验记录适用条件和证据，新任务里选择性复用而不是整体继承（防止一次任务的特化配置污染后续任务）。

最后是边界。这批实验都跑在基准任务流上，经验库从零攒起、任务分布相对连续；真实生产环境的任务漂移更大，坏经验的累积、经验库自身的安全审查（谁能写入、写进去的内容会不会变成新的注入面）都还是开放问题。论文在 Limitations 里也明确承认：递归细化消耗额外执行与编辑成本，行为对比对执行随机性和模型共同偏差敏感，不构成正确性保证。结合[上下文压缩](./13-上下文压缩Compaction是什么.md)一节的治理衰减结论，这里又多出一层新的治理面：你不仅要审查 Harness 会不会忘记规则，还要审查"改 Harness 的过程"会不会把错误的东西当成经验记住。

## 任务成功就说明 Harness 可靠吗

上一节讨论了 Harness 怎么自己变好，但有个更基本的问题被跳过了：你怎么知道现在的 Harness 靠不靠谱？直觉答案是看任务成功率——活干成了就是好 Harness。2026 年 10 月的 TraceTrial-Bench（arXiv:2610.32285）专门检验了这个直觉，结论是它靠不住。

这个基准把 Harness 可靠性拆成七个可独立检查的组件：上下文、执行、治理、生命周期、可观测性、工具和验证，配上 95 个机制导向的任务——每个任务都有可执行或基于状态的标准答案，专门设计来触发特定的 Harness 行为，而不是泛泛地问"这个任务能不能完成"。4 个 Harness、9 个模型、3420 次运行之后，两个数字值得记住：最好的 Harness 宏观得分也只有 72.0%，没有一家接近满分；更关键的是，31.1% 的运行虽然任务成功，却至少违反了一条 Harness 可靠性标准。

第二个数字解释了为什么需要这个基准。一个 Agent 可以在权限失控、验证缺失或者上下文已经被污染的状态下把任务做完——就像测试全绿但代码里藏着没人发现的竞态。成功率衡量的是"结果对不对"，Harness 可靠性衡量的是"过程中该守的规矩守没守住"，两件事的相关性远没有直觉假设的那么强。这也让前面几节反复出现的过程视角有了统一的度量框架：治理衰减关心约束还在不在，行为对比验证关心改动有没有副作用，TraceTrial-Bench 把这类问题归拢成可复现的基准，用轨迹追踪和多源证据支持运行级归因，并且要求失败归因给出显式的机制链，而不是一句"模型不行"。

如果说 TraceTrial-Bench 回答的是"可靠不可靠"，同期另一篇工作补上了"对谁可靠"：Evolving to Match Capabilities（arXiv:2610.33024）发现，上一节那些 Harness 改进——尤其是 Skill——不是普适的，是能力条件性的。这篇论文在七个模型、三个基准里找出 103 对任务-技能组合：同一批 Skill 让 GPT-5.6-luna 拿到 31.1 分提升，却让 Gemma-4-E4B 掉了 8.8 分。更值得注意的是失败原因的分布：86% 的弱模型失败中，被违反的要求本来就写在 Skill 文本里。信息没有缺失，是执行能力跟不上指令密度——把"必须先读文件再改"写十遍，也救不了不会主动读文件的模型。

这篇论文给的对策叫 Skill 适配：先诊断失败落在哪个维度（工具执行、上下文管理、指令遵循还是验证），再按诊断结果重写 Skill——把抽象要求拆成执行者能走的具体步骤，或者裁掉执行者撑不住的部分。用外部强模型（Kimi-K3）按固定元技能直接改写、不需要执行证据，三个弱执行者提升 5.1 到 14.1 分；把适配环节嵌进上一节的自进化循环后，七个执行者额外多拿 2.0 到 5.1 分。改进的次序由此清楚：先让指令匹配执行者，再谈让执行者自己进化。

对自建 Agent 的开发者，这两篇合起来给出三条便宜的做法。第一，成功指标要配过程指标：除了交付通过率，盯住权限使用、验证覆盖、上下文卫生这类过程维度，否则你看到的永远是那 31.1% 之外的"成功"。第二，换模型等于重新验证 Harness：在一个模型上调好的提示、流程和技能，换模型后应视为未验证状态，能力条件性意味着增益不保证随模型迁移。第三，弱模型跑不动强 Skill 时先做失败诊断：多数时候问题出在 Skill 表达与执行能力的错配，改写 Skill 比换模型便宜。

边界也要说清楚。TraceTrial-Bench 的七组件划分和机制任务都是人工设计，真实生产负载更多样，基准上的 Harness 分数高不等于线上不出事；Evolving to Match 的适配本身要花额外的执行与改写预算，弱模型被适配后能吃下的 Skill 复杂度仍有上限。度量框架和能力匹配都没有一劳永逸地解决"过程可靠"，它们做的只是把"成功"这一个数字拆开，变成能下手分析的形状。

## 自进化的评测预算该花在哪

上一节留下的自进化循环里，藏着一笔没算的账：每筛选一个候选改进，都要把 Agent 在一批任务上跑一遍。Harness² 的行为对比要改前改后各跑一次，Self-HPO 的交替进化每轮都要重新评估 Harness 候选。任务集一大、候选一多，评测本身就是最贵的环节——而它从不缺席：搜索要靠它指路，最终定版也要靠它拍板。EvalAlloc（arXiv:2610.37276）把这笔账正式算了出来：固定的评测预算，应该怎么花在这两个角色上。

这篇论文先做系统实验、再提方案，三个发现值得单独记住。第一，进化搜索阶段用稀疏反馈就够：候选不评完整任务集、只抽一小部分任务，进化照样能持续推进；真正让搜索退化的是把反馈完全去掉。第二，稀疏的分数要可比才有用——所有候选都评同一批「信息量大的任务」，并且用同一个评分参照，相近候选之间的差距才测得出来。第三，搜索的改进集中在早期迭代，后期真正敏感的是最终选择：第一名和第二名只差一点时，选错的代价全在终选环节，这里值得多花评测。

EvalAlloc 据此把两个角色拆开。开局用一小批候选做全量评测当热身，既筛出共享的高信息任务核心，也校准一个低秩 logistic 响应模型（按多维项目响应理论的形式建模，任务与候选各有自己的参数）；进入搜索后，任务侧参数冻结成公共参照尺，每个新候选只从稀疏观测里估计自己的参数；搜索结束后重拟合模型，用热启动的配对 successive halving 做终选——已有观测全部复用，只补缺失的评测。四个基准（HotpotQA、HoVer、DROP、IFBench）乘两个进化框架的实验里，这套分配用大约一半的评测单元，拿到了与全量评测持平或略高的平均 TEST 分数；消融显示贡献主要来自高信息任务分配和终选环节。

对自建 Agent 的开发者，这节课可以压缩成一句话：评测预算是决策依赖的，花之前先想清楚这次评测服务于哪个决策。搜索期的评测要便宜且可比，类似招聘里的简历筛选——目标是快速排除，不追求精确排名；终选的评测要准，类似终面——只留给少数候选，但每个都看透。把终面的深度花在简历筛选上，预算很快就烧完；反过来用简历筛选的精度做终选，选错的代价更高。同一个道理也解释了上一节的一条教训为什么成立：换了参照尺的分数不可比——这正是「换模型等于重新验证」的另一种表述。

边界照例要说。实验任务都有明确的验证器（QA 有标准答案、IFBench 有可执行检查），无验证器场景下的行为对比怎么分配预算，这篇论文没有覆盖；热身候选数、稀疏采样比例这类超参数依赖任务集规模，照搬具体数字没有意义。它和前两节合起来，自进化的三件事算是齐了：改什么（两路分工的提案）、改得对不对（行为对比与过程指标）、花多少评测（按角色分配预算）——剩下的都是工程。

## 成功之前，路径本身靠不靠谱

前面两节把「成功」拆出了过程维度，但那种拆法仍以运行为单位：一条轨迹要么成功要么失败，失败之后才去归因。Prefix Executability（arXiv:2610.40444，2026 年 10 月底，Oracle AI）把镜头再拉近一格：不看整条轨迹，看它的每一段前缀——在任何一步停下时，已经发生的工具调用序列是否仍然可执行（工具存在、参数合法、前置条件满足、数据依赖成立）。这给出一个比「成功/失败」细得多的刻度：轨迹在第几步第一次出现不可执行的调用、可执行前缀能活多深、失败之后有没有恢复。

这套协议在 BFCL-v3、ToolSandbox 和 τ³-bench 上的审计抓出了一个此前不可见的分歧：按最终成功率排名，先做规划再执行的 Agent（plan-conditioned ReAct）常常领先——GPT-5.4 在 BFCL 上成功率 0.94 对基线的 0.61；但按前缀可执行率排名，它反而垫底——可执行轨迹率（TER）只有 0.47，基线是 0.69。也就是说，规划条件化的 Agent 一部分「成功」建立在带伤的轨迹上：中间步骤本已不可执行，靠后续调用侥幸绕了回来。只看终点的评测会把这种成功和真正干净的成功混在一起，而这两种成功在换环境、换模型时的稳健性完全不同。τ³-bench 的迁移审计还发现验证的收益依赖环境：BFCL 这类预定义组合任务上验证明显有益，交互式反馈会不断改状态的 τ³ 场景则收不回收益——提前定好的计划过时得很快。这也是一次便宜的提醒：验证不是免费的普适保险，每个环境的账要单独算。

对自建 Agent 的开发者，这里多出一个便宜的过程指标：除了成功率和上一节的权限/验证覆盖，再盯一下「首错深度」——第一次出现非法调用发生在第几步。首错深度浅而成功率不低，说明系统在靠恢复能力兜底；这本身不是坏事（论文的验证干预显示，显式的执行前计划检查能在不牺牲终态成功率的前提下显著延长可执行前缀的存活），但你至少应该知道自己的系统属于哪一种。边界照旧：可执行性检查是确定性的 schema/前置条件判定，管不了「调用合法但语义错误」；实验以 GPT-4.1/GPT-5.4/Llama-4 三档模型在三个基准上进行，其余环境的数字不可直接外推。

## 训练任务里的规格，比你想的稀

前面几节都在讲怎么评测和改进一个已经存在的 Harness。换一个视角：Agent 的能力上限，很大程度是训练任务决定的——如果训练里的任务只要求「把这个问题修好」，Agent 学到的就是修主目标，顺带把别的东西改坏。CodeSpecWeave（arXiv:2610.40256，2026 年 10 月底，小米）先给现有 SWE 训练集量了个身，结论是规格饥荒：任务普遍只有一两条规格，而且彼此独立——主目标之外，接口兼容、状态一致、错误处理这些真实开发中绕不开的约束几乎缺席。

缺规格还只是数量问题，更要命的是规格之间的关系。论文区分了两种任务结构：可加规格（additive）和互依规格（interdependent）。形式化地说，设工程决策变量为 d，理想可加任务的可行域可以分解成每个决策各自可行域的笛卡尔积，于是 Agent 可以逐条贪心地满足，把它当成清单打勾；互依规格破坏这个分解——为满足 A 而做的选择，直接压缩了 B 的可行空间，局部修改无法解耦，Agent 必须把所有要求放在一起推理。一个具体例子：给交易记录加签名合并功能，同时要求不改动原始状态——实现者顺手用整状态拷贝，结果两个状态共享了同一个交易对象，往副本加签名时把原件也改了。单独看每条要求都「做了」，合在一起就是错的。这种失败模式有个共同名字：检查表任务养出来的局部补丁习惯。

论文的合成流水线围绕两个难点设计。第一是规格设计：从真实仓库的 commit、issue 和 PR 里挖出 104,182 条候选规格作种子，由合成 Agent 把互补的要求锚定到同一状态转换或核心组件上，故意造出「满足任何一条单独看都对、合在一起必须统筹」的耦合。第二更麻烦：验证。测试要在「放过隐藏缺陷」和「误杀合法实现」之间走钢丝——耦合规格下，测试很容易假定某种具体实现，从而拒绝其他同样正确的写法。试写阶段的数字很直白：3,067 个候选任务里，2,267 个（73.9%）的测试有对齐缺陷，其中一半以上是假阳性（接受不完整实现），近 14% 是假阴性（拒绝合法方案）。解法是把验证从静态审查改成执行证据对账：收集多个独立模型在任务上的补丁和执行轨迹，跑挂了的轨迹暴露测试漏检了什么，合法写法被拒暴露测试多管了什么——Review Agent 拿着（任务、测试、补丁、轨迹）四元组迭代修测试。14,905 个初始任务经过难度过滤剩 3,275 个，审查后只有 766 个通过。最终产出 4,670 个训练任务、覆盖 2,865 个仓库；另附一个 100 任务、1,044 条规格的评测集，平均每条任务 10.44 条规格。

训练收益把故事讲完整了。前沿模型在这套评测集上的通过率只有 44%–74%——最强的 GPT-6 Astra 也挂掉四分之一，而且同一框架内成绩和输出长度负相关：GPT-6 Astra 以最低的输出量（17.2k tokens）拿下最高分，Claude Opus 5 比 Qwen3.8-Max 高 6.1 个百分点却少生成约 47% 的 token。这说明耦合规格下多产出大多是无用的试错。用 4,670 个任务做 RL，两个 310B MoE 底座（MiMo-V2.5 与其 SFT 版）在长程基准 DeepSWE-v1.1 上的提升最扎眼：25.3% 和 63.0%，而对照训练集 SWE-PI 在其中一个底座上是负迁移（6.8%，反而低于不训练的 12.4%）。行为层面，训练后的模型思考 token 涨到 3–5 倍、改动范围从局部补丁转向跨文件重构，编辑-测试循环次数显著上升（一个底座从 2.96 涨到 4.90 次/轨迹）——涨的不是蛮力，是主动验证。

把这条放回本文的线索里：上一节 Prefix Executability 教你便宜地看出一条轨迹是不是带伤跑完全程，这一节说的则是带伤的根源可能不在推理时的 Harness，而在训练任务本身——规格稀疏且独立的任务，等于告诉 Agent「只满足主目标就行」。自建训练数据的开发者可以带走三条：规格的量不等于质，互依性才让任务无法被逐条打勾；耦合规格的可执行测试极难一次写对，执行轨迹对账比静态审查可靠，但接受率低是常态不是事故；评估模型别只看主目标成功率，补一组规格覆盖率的指标，否则评测本身就在复制「重主目标、轻约束」的偏差。边界照例：流水线依赖大量前沿模型的轨迹作审查原料，成本不低；RL 收益在两个同源的 MoE 底座上验证，换模型家族是否复现是开放问题；评测以 SWE 式仓库任务为主（SWE-bench Pro 含多语言任务），跨语言、跨任务形态的外推仍需更多证据。

## 评测量具也会坏：基准维护债与连续验证

前面几节的隐含前提是量具本身可信：任务成功、轨迹可执行、规格覆盖都查过了，分数就该反映能力。这一节质疑这个前提。2026 年 11 月，斯坦福的 Buchanan 等发表了 Benchmarks as Software（arXiv:2611.08417），核心发现是：基准不是刻在石头上的尺子，而是活在不断变化的生态系统里的软件。Terminal-Bench 2.0 在发布前做过大量人工审查、LM 辅助检查和 red-teaming，这套流程已经比绝大多数基准严格；对其全部 89 个任务的审计仍然发现约 30% 的任务存在问题。论文给这类缺陷起了名字：基准维护债（benchmark maintenance debt）——基准分数与它想测的能力之间持续扩大的差距。

先看任务由什么组成，才知道什么东西会坏。论文把每个基准任务定义成一场限时考试：自然语言题面、预装软件的 Docker 环境、参考解加验证器构成的 oracle、测试，以及时间、内存、CPU 预算。五样东西里没有一样是静止的。模型在变强，外部依赖在漂移，运行基础设施在升级——发布那一刻的验证结论，保质期取决于这些变量什么时候动。

审计归纳出三类反复出现的维护债。第一类是题面与验证不匹配：28 个修复任务里占了 16 个。任务发布时题面和验证器自洽，但模型变强之后解法空间扩大，开始踩进设计者没预料到的合法路径——解法真实有效，验证器却按旧假设把它拒了。这可能是最反直觉的一类：分数上不去不再说明模型不会，而是量具在误杀；基准在模型进步面前被动「变难」了。第二类是环境问题（8 个）：任务依赖的软件包、API、外部网站在发布后继续移动。caffe-cifar-10 修复前通过率只有 5.0%，环境修好之后 69.2%——整个任务之前被环境判了死刑，和模型能力毫无关系。第三类是任务漂移（12 个）：题面渐渐与当代开发实践脱节。值得一提的是也有反方向的案例：overfull-hbox 在 2.0 里环境构建损坏，验证器拿不到 ground truth，错误地给了一些本该拒绝的输出发分；修复后这个任务的通过率反而下降。所以修复不是「把分数都放松到涨」——有的分数上涨是过去漏判，有的下降是过去错判，修复后的数字才更接近想测的东西。

发现和修复的流程本身值得细看，因为它回答了一个现实问题：模型裁判到底能信到什么程度。整条流水线是 propose-only 的：证据收集 Agent 汇总三路输入（静态任务文件、历史 agent 执行轨迹、社区报告），审计 Agent 按规格保真、测试、资源、风险四条原则起草带引用的修复提案；然后 /oracle 做确定性复核——重建任务环境、运行参考解，已知正确的解必须能过；再由一个专职的验证 Agent 去挑战审计员的标签。全部跑在 GitHub Actions 上，每轮修复上限五次迭代，Agent 只产出维护者可审的 diff，没有直接改动仓库的权限。一致性数据给出了清晰的分工：两个 managed coding assistant（Claude Code 配 Opus 4.6、Codex 配 GPT-5.4）对主缺陷类别的判断一致度 κ=0.80，连「无缺陷」的判断都包括在内；低成本 API 模型做二元分诊（标记/干净）也有 κ=0.55–0.77。但分类别看，题面-验证不匹配 κ=0.60、环境问题 κ=0.59，任务漂移只有 κ=0.21–0.41。所以工作流的实际设计是：缺陷分类交给模型裁判，漂移检测交给确定性 oracle 复核——pilot 阶段单靠审计员打标抓不住漂移，才加上了专职验证环节。想复用这套流程的人应该记住这个分工边界，而不是假设模型裁判处处可靠。

修复之后重新测了 19 个 agent，结论可以概括成「大排序稳，近距离不可信」。两个版本的排名高度相关（Spearman ρ=0.958，95% CI [0.881, 0.979]），但个体分数移动至多 12 个百分点，榜单位置至多变动 3 位。收益分布很不均匀：Claude Code 配 Opus 4.6 高出拟合线 7 个百分点以上、上升 3 位，而两个最弱的 agent（2.0 上低于 40%）反而低于拟合线掉了分——28 个修复任务里 19 个是 hard，弱 agent 本来就做不动，修复让难题变得可解对他们没有意义；固定预算下这些 agent 的失败本来就被超时主导。涨幅最大的五个任务通过率从不超过 15% 提到 50% 以上，集中来自题面-验证不匹配的修复。

实验的另一半把资源预算本身变成了被审计对象。同一厂商的两个 harness 在 GPT 5.4 上相差约 20pp，把时限加长后大部分差距消失——差距量的是速度而不是能力；GPT 5.4 mini 上 30pp 的差距同样缩到 5pp。论文的修复惯例是把被约束的资源轴调到 oracle 实测需求的至少 1.5 倍：既防止基础设施噪音把正确解误判为失败，又给真实解题留出余地。这一半的结论对做 agent 对比实验的人最扎手：固定时限是一个任意选的工作点，选在哪能改变单个模型的效率结论。正确的做法是设一个有原则的下限，然后测结论对预算的敏感性，而不是把校准点定在某一组 agent 的便利上。

对自建或重用基准的开发者，这一节可以浓缩成三条便宜的做法。第一，给基准配 CI：把「oracle 参考解还能通过」当成回归测试定期跑，参考解过不了就是量具坏了，比模型分数先知道。第二，引用任何 agent 分数时注明基准版本和资源预算：绝对分数和邻近名次依赖版本（TB 2.0 到 2.1 之间个别分数动 12pp），大排序虽然稳定，近距离比较随时可能翻转。第三，把「分数变化」和「模型变化」分开归因：看到榜单变动先问量具动没动——oracle 修复、环境修复、时限调整都会移动分数，而模型一行代码没改。

边界照例说清楚。这套工作流审的是任务、验证器和预算，不直接评测模型能力；外部效度只在 Harbor-Index 的 34 个随机任务上验证过（来自 80 任务快照、29 个源基准），样本规模有限；「约 30% 有缺陷」测自一个发布流程已经非常严格的基准，自家基准如果发布审查更松，这个比例只高不低；修复前后的分数变化不代表模型变强或变弱，是量具校准，引用时必须注明版本。把它放回本文的线索里：Prefix Executability 把「成功」拆到了路径级，这一节把「分数」拆到了量具版本级——以后看任何 agent 评测结论，至少要问三个问题：跑的哪个版本的基准、oracle 还过不过、预算是多少。

## 跑了几小时的 Agent 靠什么活着

前面所有小节都在讨论单窗口内的质量。把时间拉长——一个要跑几个小时、跨越几十个上下文窗口的 Coding Agent——问题就不再是「这一步做得对不对」，而是「上一个它消失时，给下一个它留了什么」。业界给这类系统的名字叫持久化 Agent（Durable Agent）或长时运行 Agent，Anthropic 工程团队在两篇文章（2025-11 的 Effective harnesses for long-running agents 与 2026-03 的 Harness design for long-running application development）里给出的不是理论，而是一份踩坑清单。

先看最朴素的方案为什么失败。让同一个模型在循环里反复跑、只给一句「做一个 claude.ai 克隆」，即使有[上下文压缩](./13-上下文压缩Compaction是什么.md)兜底，也会稳定出现两种死法。第一种是「一口吃成胖子」：模型试图一口气把整个应用写完，上下文在半路耗尽，下一个会话接手时面对的是一个半成品加零文档，只能花大量时间先猜测和修复。第二种出现得更晚、也更讽刺：项目已经有不少成品之后，新的 Agent 实例环顾四周，看见一片繁荣，宣布项目完成——而功能清单上还有大半没做。

Anthropic 的解法分两层。环境层由一个初始化 Agent 在第一次运行时搭建：一份 200 多项的功能清单（从用户提示展开，每项都带验证步骤，初始全部标记 failing）、一个进度文件、一个 init.sh 启动脚本和首个 git 提交。执行层的每个会话遵循固定仪式：pwd 确认目录 → 读 git log 和进度文件接上脉络 → 从功能清单挑一项 highest-priority 未完成项 → 实现它 → 端到端验证 → git 提交加更新进度文件。一次只做一项功能，是对「一口吃成胖子」的直接矫正；「先跑一遍现有功能再动手」，是对第二种死法的——开工前先确认自己不是接手了一个坏掉的项目。

两个实现细节比架构本身更反直觉。其一，功能清单用 JSON 而不是 Markdown，并只允许改 passes 字段——实验发现模型乱改或重写 Markdown 清单的倾向明显更强，而结构化文件加上「删除或修改测试不可接受」的强措辞，能把清单本身变成防「提前宣布胜利」的机制。其二，测试要求「像人一样用浏览器自动化工具走一遍」，而不是只跑单元测试或 curl：Anthropic 观察到的第三种失败模式正是模型改完代码、单测过了，就标记功能完成，端到端却根本不通——给它 Puppeteer 或 Playwright 之后，很多只在真实页面暴露的 bug 才被发现。

到 2026 年 3 月的第二篇文章，这套双人 Harness 又升了级，暴露出一个更深的问题：**自己干、自己验，模型会给自己打高分**。让生成代码的 Agent 自己评价产出，它倾向于自信地表扬自己的工作，哪怕在人类看来质量明显平庸；这个自评偏乐观在主观任务（设计）上最刺眼，在可验证任务上也照样拖后腿——早期运行里，QA Agent 会发现真问题，然后说服自己「这不是大事」，照常放行。解法是把干活和判断拆成两个角色：规划 Agent 把一句话提示展开成产品规格，生成 Agent 按 sprint 实现，评测 Agent 用 Playwright 像用户一样实际操作运行中的应用，按合同逐条验收，任何一条低于硬阈值整个 sprint 打回重做。评测 Agent 的提示需要多轮校准——开箱即用的 Claude 是个糟糕的 QA，得读它的日志、找出判断和人不一致的地方、针对性改提示。

代价必须诚实报：同样的一个「2D 复古游戏制作器」提示，单 Agent 跑 20 分钟花 9 美元，完整三角色 Harness 跑 6 小时花 200 美元——20 倍成本换来的是「核心功能真的能用」和「核心功能表面好看点进去是坏的」的差别。这篇文最后还有一个对所有人都有用的结论：**Harness 里的每个组件都是一条「模型自己做不到 X」的假设，模型升级后要逐个拆除验证**。Opus 4.6 发布后，作者逐个移除组件测试：sprint 结构整个删掉了（4.6 能自己保持连贯两个多小时），评测 Agent 保留但降为末尾单轮——它在任务超出模型可靠能力边界时仍有真价值，在边界内成了纯开销。模型在进化，脚手架的最优形状也在移动；昨晚还救命的组件，今天可能只剩成本。

把这条放回本文线索里：Agent Loop 讲的是单窗口内「行动-观察-再决策」，这一节讲的是跨窗口的同一件事——git 历史和进度文件是 Agent 的外部化观察，功能清单是外部化计划，初始化/执行的分工是外部化的规划与恢复。上一节 Prefix Executability 教你看单条轨迹是否带伤，这一节教你检查跨会话交接面：清单是否被偷偷放宽、进度文件是否如实记录失败、验收合同是否被「说服自己」绕过。自建长时 Agent 时最便宜的三步：把「怎么跑起来」写成脚本而不是让每个会话现场探索；把「完成了什么」放进只允许改状态字段的结构化清单；把「验没验过」交给一个独立提示的评审者——它不需要更聪明，只需要不被写代码的那个带偏。

边界照例：Anthropic 两篇都以全栈 Web 应用为实验场，功能清单模式依赖「成果可逐项枚举验证」的任务形状，研究型或探索型任务未必适用；成本数字（$9 对 $200）来自特定提示与当时的模型定价，只当量级参考；「自评偏乐观」的强度随模型版本变化，Opus 4.6 时代 QA 保留但形态已变，把这些当成需要重新验证的假设，而不是固定结论。

## 调模型 API 与委托完整 Coding Agent 的区别

一次模型 API 调用接收输入并返回文本或工具请求；完整 Coding Agent 还拥有工作目录、会话状态、工具运行时、权限、错误恢复和验证循环。委托给另一个 Agent 等于启动一个受约束的执行者，不只是向模型问一道题。

子 Agent 能独立搜索和测试，但也会带来额外上下文、权限与协调成本。任务若只是改写一句文案，直接模型调用更合适；若需要在独立代码范围内探索、修改并交付证据，Agent 运行时才有价值。

## 回答关键问题

**Coding Agent 和代码补全有什么区别？** 前者能跨文件使用工具并根据执行结果循环，后者主要续写局部上下文。

**为什么还需要符号导航？** 它帮助定位定义、引用和调用关系，比只做文本读取更有效地建立大型仓库上下文。

**测试通过就完成了吗？** 不一定，还要检查需求、Diff、测试覆盖和环境差异。

**为什么频繁运行搜索、测试和 Git 工具？** 因为项目状态在模型之外且会变化；工具把真实证据带回循环，避免凭训练记忆一次性猜完整仓库。

**怎样避免改对一个文件却改坏项目？** 检索调用关系和规则，采用小 Diff，运行分层验证，检查失败路径，并保护用户现有变更。

**直接调用模型与委托 Coding Agent 有何区别？** 后者多出有状态运行时、工具、工作目录、权限、恢复和可验证交付。

**Harness 会自己越用越好吗？** 开始出现这类方法：用行为对比验证 Harness 修改、把改进经验沉淀成库供后续任务复用；代价是额外的执行开销，经验库本身也需要治理。

**任务成功就说明 Harness 靠谱吗？** 不。实验里 31.1% 的成功运行至少违反一条 Harness 可靠性标准；成功率和过程质量要分开度量，而且 Skill 类改进是能力条件性的，换模型后要重新验证。

**基准分数涨了，一定是模型变强了吗？** 不一定。验证器修复、环境修复、时限调整都会移动分数：Terminal-Bench 2.0 到 2.1 的修复让平均准确率涨了 10 个百分点以上，而模型一行代码没改。看分数先问量具版本。

**为什么引用评测结论要连资源预算一起引用？** 固定时限下 harness 之间约 20pp 的差距，加长时限后可能缩到 5pp——量的是速度不是能力。预算是测量规格的一部分，单点预算下的结论不可迁移。
**让一个 Agent 跑几个小时，最怕什么？** 不是模型「变笨」，是窗口之间的交接面断裂：新会话不知道上一个做到哪、面对半成品瞎猜，或者看见已有进度就宣布完工。功能清单、进度文件、git 历史和「先验证再动手」的开工仪式，都是给交接面补的保险。

**既然模型能自己检查，为什么还要单独的评测 Agent？** 因为自评偏乐观是稳定倾向：生成者会发现自己的问题，然后说服自己「不是大事」。独立提示的评审者不需要更聪明，只需要不被生成者带偏——代价是多一轮推理成本，任务在模型可靠能力边界内时它就是纯开销。
