Coding Agent 是面向软件项目的 Agent。它不只生成代码片段，还会读取仓库、搜索符号、编辑文件、运行测试和构建，并把真实环境结果带回下一轮决策。

关键差异不只是“模型更会写代码”，而是项目上下文、开发工具、Agent Loop 和权限边界组成了完整系统。

## 一次任务如何形成闭环

```text
读取需求与仓库规则
  ↓ 搜索相关文件、符号和历史
制定或调整步骤
  ↓ 编辑代码
运行测试、类型检查或构建
  ↓ 读取真实结果
修复、验证或明确受阻
  ↓
交付 Diff 与证据
```

这张图想说明“写完代码”只是中间步骤。读图时注意，完成必须由测试、构建、业务行为或其他证据支持，不能只靠 Agent 宣布。

## 为什么不能把仓库一次读完再修改

仓库可能远大于上下文窗口，而且开工时并不知道哪些文件真正相关。Coding Agent 使用 `rg`、`find`、符号导航和目录读取逐步缩小范围；修改后再用测试、构建和 `git diff` 获取新证据。

工具循环不是模型能力不足的补丁，而是软件任务的现实结构：代码、依赖、运行环境和当前变更都在模型参数之外。一次性读取会混入大量无关内容，后续代码或测试结果还会让早期判断过期。

每次工具调用都应有问题意识。搜索用于定位定义和引用，测试用于验证行为，Git Diff 用于检查实际改动；机械重复命令却不更新假设，只会浪费上下文。

## 为什么需要项目级上下文

同一个需求在不同仓库有不同架构、依赖、测试和约定。Agent 要读取代码、配置、文档、Git 历史和 `AGENTS.md` 等规则，不能用训练记忆猜当前项目。

大型仓库也不能全部塞入上下文。文件搜索能找到文本，符号导航还能追踪定义、引用、类型和调用关系。公开真实需求提出“像 IDE 一样的语义导航”，正因为只读原始文件会在跨文件关系中浪费上下文并漏掉依赖。

## 工具和权限同时扩大能力与风险

终端允许 Agent 运行真实测试，Git 提供 Diff、历史和可恢复边界。文件写入、命令、网络和发布权限也可能删除数据、泄露凭证或影响外部系统。

终端、Shell、命令和真实进程分别承担什么，见：[Shell 和 Command 是什么](./02-Shell和Command是什么.md)。

因此应使用沙箱和最小权限，对破坏性或外部副作用操作确认，避免把密钥写入日志。能修改仓库不代表应自动合并、推送或发布。

## 怎样判断任务真的完成

Diff 要与需求一致，相关测试、类型检查和构建通过；新增逻辑应覆盖失败路径和边界；没有意外文件、调试残留或被削弱的断言。无法验证的外部条件要明确记录，高风险变化仍需人工 Review。

Benchmark 只能测特定任务和环境，不能替代生产权限、私有依赖和发布门禁。最终应审查代码和证据，而不是只看模型名称或运行轮数。

## 设计一个 Coding Agent 要补哪些系统能力

一个可用设计通常包括：

1. 项目发现：规则、目录、语言、构建与 Git 状态；
2. 检索：文本、符号、依赖和按需文件读取；
3. 编辑：结构化 Patch、冲突检测和用户变更保护；
4. 执行：沙箱命令、超时、资源和网络限制；
5. 验证：测试、类型、构建、静态检查和业务证据；
6. 恢复：检查点、可逆 Diff、失败分类和取消；
7. 权限：读取、写入、命令、密钥、提交和发布分层授权；
8. 观测：轨迹、工具输入输出、成本和最终产物。

“Git 回滚”不能依赖破坏性清空工作区。Agent 应先识别哪些变化属于用户，优先用小 Patch、反向修改或独立分支，并在任何会覆盖数据的操作前确认目标。

## Harness 能不能自己改进自己

前面列出的系统能力合在一起，就是业界所说的 Harness：模型参数之外、决定 Agent 怎么干活的整套运行时脚手架。前几节默认它由工程师设计、发布后基本冻结；这一节讨论一个更新的问题——它能不能自己改进自己。

2026 年 10 月，这个方向的工作集中出现，可以看作一个子领域的成型标志。Harness²（arXiv:2610.14224）代表"模型冻结、只改脚手架"的路线：它把 Harness 拆成系统提示、护栏、记忆、技能、工具指引、脚本、子 Agent、中间件八个文件级组件，让一个编辑器模型针对当前任务提出两份修改——一份盯可能跨领域复现的通用缺陷（计划、工具使用、上下文管理），一份盯当前领域的知识与流程——然后把修改前后的 Agent 在同一任务、同一环境下各跑一遍，用行为对比代替评分：不看输出"对不对"，只看目标缺陷的行为有没有缓解、有没有引入退化，最后只把有证据支持的修改组合进新 Harness。

两处设计值得细看。其一，没有标准答案也能改：开放世界的任务大多没有真值和验证器，Harness² 不假装能验证正确性，只利用"只变 Harness、其他全部相同"带来的可比性。这是它敢用执行证据的原因，也是证据的边界——执行有随机性，模型判断有共同偏差，行为对比只能支持"这个改动缓解了那个缺陷"，不保证任务做对，更不保证改动能迁移到别的任务。其二，改进过程本身也被沉淀：每个任务结束后，系统回顾整个改进记录，把"什么改动、在什么条件下、产生了什么后果"写成经验条目存入改进库；下一个任务仍从通用 Harness 出发，但提案和组合会参考库里的组件与教训，而不是整体继承上一个任务的特化配置。这就是两层递归：第一层改当前任务的 Harness，第二层改"以后怎么改 Harness"。消融实验中去掉经验库、去掉两路分工提案、去掉证据组合都会掉分；在 JobBench 上攒出的库搬到 WorkBuddy-Bench 仍然有效。结果上，一步改进就让 GLM-5 和 Gemini 3.5 Flash 在三个职业基准上全部上涨（最高 +11.5 分），递归预算加大还能继续涨；弱模型配上改进后的 Harness 甚至能反超强模型配原始 Harness。另一个反直觉的细节：编辑器不需要是更强的模型，多个模型用自己改自己，全部基准都有提升。

同一窗口还有两条互补路线，合起来看更完整。Self-HPO（arXiv:2610.22791）指出只改一边是次优的：Harness 调优针对的是旧模型的失败模式，而策略训练又受限于固定 Harness 产出的轨迹，于是它让两者交替进化——策略模型先分析自己的失败并提出 Harness 候选，再用强化学习在选定 Harness 下更新策略，训练中暴露的难题反过来构成下一轮 Harness 搜索的目标；Qwen3.5-35B-A3B 的平均解决率从 57.8% 提到 64.8%，增益还能带到分布外任务。Self-Evolving Agent Harness（arXiv:2610.18813）则退后一步做形式化：把 Harness 自进化定义为"被接受的修改跨运行持久生效"的反馈过程，区分解释态修改（提示、记忆）与代码级修改（工具、控制逻辑），用进化搜索刻画整个过程，并给出泛化界与修改准入规则，强调可靠部署需要持续验证和独立的安全护栏——当修改能跨运行持久生效，信任、权限与问责就成了工程问题，而不只是提示词写法问题。

对自建 Agent 的开发者，当下值得搬的不是完整递归框架，而是三个便宜的做法：把 Harness 拆成可独立修改的组件文件（这是所有路线的前提）；让改动依据行为对比而不是模型自我评分（避免"自己说自己变好了"）；给每条经验记录适用条件和证据，新任务里选择性复用而不是整体继承（防止一次任务的特化配置污染后续任务）。

最后是边界。这批实验都跑在基准任务流上，经验库从零攒起、任务分布相对连续；真实生产环境的任务漂移更大，坏经验的累积、经验库自身的安全审查（谁能写入、写进去的内容会不会变成新的注入面）都还是开放问题。论文在 Limitations 里也明确承认：递归细化消耗额外执行与编辑成本，行为对比对执行随机性和模型共同偏差敏感，不构成正确性保证。结合[上下文压缩](./13-上下文压缩Compaction是什么.md)一节的治理衰减结论，这里又多出一层新的治理面：你不仅要审查 Harness 会不会忘记规则，还要审查"改 Harness 的过程"会不会把错误的东西当成经验记住。

## 任务成功就说明 Harness 可靠吗

上一节讨论了 Harness 怎么自己变好，但有个更基本的问题被跳过了：你怎么知道现在的 Harness 靠不靠谱？直觉答案是看任务成功率——活干成了就是好 Harness。2026 年 10 月的 TraceTrial-Bench（arXiv:2610.32285）专门检验了这个直觉，结论是它靠不住。

这个基准把 Harness 可靠性拆成七个可独立检查的组件：上下文、执行、治理、生命周期、可观测性、工具和验证，配上 95 个机制导向的任务——每个任务都有可执行或基于状态的标准答案，专门设计来触发特定的 Harness 行为，而不是泛泛地问"这个任务能不能完成"。4 个 Harness、9 个模型、3420 次运行之后，两个数字值得记住：最好的 Harness 宏观得分也只有 72.0%，没有一家接近满分；更关键的是，31.1% 的运行虽然任务成功，却至少违反了一条 Harness 可靠性标准。

第二个数字解释了为什么需要这个基准。一个 Agent 可以在权限失控、验证缺失或者上下文已经被污染的状态下把任务做完——就像测试全绿但代码里藏着没人发现的竞态。成功率衡量的是"结果对不对"，Harness 可靠性衡量的是"过程中该守的规矩守没守住"，两件事的相关性远没有直觉假设的那么强。这也让前面几节反复出现的过程视角有了统一的度量框架：治理衰减关心约束还在不在，行为对比验证关心改动有没有副作用，TraceTrial-Bench 把这类问题归拢成可复现的基准，用轨迹追踪和多源证据支持运行级归因，并且要求失败归因给出显式的机制链，而不是一句"模型不行"。

如果说 TraceTrial-Bench 回答的是"可靠不可靠"，同期另一篇工作补上了"对谁可靠"：Evolving to Match Capabilities（arXiv:2610.33024）发现，上一节那些 Harness 改进——尤其是 Skill——不是普适的，是能力条件性的。这篇论文在七个模型、三个基准里找出 103 对任务-技能组合：同一批 Skill 让 GPT-5.6-luna 拿到 31.1 分提升，却让 Gemma-4-E4B 掉了 8.8 分。更值得注意的是失败原因的分布：86% 的弱模型失败中，被违反的要求本来就写在 Skill 文本里。信息没有缺失，是执行能力跟不上指令密度——把"必须先读文件再改"写十遍，也救不了不会主动读文件的模型。

这篇论文给的对策叫 Skill 适配：先诊断失败落在哪个维度（工具执行、上下文管理、指令遵循还是验证），再按诊断结果重写 Skill——把抽象要求拆成执行者能走的具体步骤，或者裁掉执行者撑不住的部分。用外部强模型（Kimi-K3）按固定元技能直接改写、不需要执行证据，三个弱执行者提升 5.1 到 14.1 分；把适配环节嵌进上一节的自进化循环后，七个执行者额外多拿 2.0 到 5.1 分。改进的次序由此清楚：先让指令匹配执行者，再谈让执行者自己进化。

对自建 Agent 的开发者，这两篇合起来给出三条便宜的做法。第一，成功指标要配过程指标：除了交付通过率，盯住权限使用、验证覆盖、上下文卫生这类过程维度，否则你看到的永远是那 31.1% 之外的"成功"。第二，换模型等于重新验证 Harness：在一个模型上调好的提示、流程和技能，换模型后应视为未验证状态，能力条件性意味着增益不保证随模型迁移。第三，弱模型跑不动强 Skill 时先做失败诊断：多数时候问题出在 Skill 表达与执行能力的错配，改写 Skill 比换模型便宜。

边界也要说清楚。TraceTrial-Bench 的七组件划分和机制任务都是人工设计，真实生产负载更多样，基准上的 Harness 分数高不等于线上不出事；Evolving to Match 的适配本身要花额外的执行与改写预算，弱模型被适配后能吃下的 Skill 复杂度仍有上限。度量框架和能力匹配都没有一劳永逸地解决"过程可靠"，它们做的只是把"成功"这一个数字拆开，变成能下手分析的形状。

## 自进化的评测预算该花在哪

上一节留下的自进化循环里，藏着一笔没算的账：每筛选一个候选改进，都要把 Agent 在一批任务上跑一遍。Harness² 的行为对比要改前改后各跑一次，Self-HPO 的交替进化每轮都要重新评估 Harness 候选。任务集一大、候选一多，评测本身就是最贵的环节——而它从不缺席：搜索要靠它指路，最终定版也要靠它拍板。EvalAlloc（arXiv:2610.37276）把这笔账正式算了出来：固定的评测预算，应该怎么花在这两个角色上。

这篇论文先做系统实验、再提方案，三个发现值得单独记住。第一，进化搜索阶段用稀疏反馈就够：候选不评完整任务集、只抽一小部分任务，进化照样能持续推进；真正让搜索退化的是把反馈完全去掉。第二，稀疏的分数要可比才有用——所有候选都评同一批「信息量大的任务」，并且用同一个评分参照，相近候选之间的差距才测得出来。第三，搜索的改进集中在早期迭代，后期真正敏感的是最终选择：第一名和第二名只差一点时，选错的代价全在终选环节，这里值得多花评测。

EvalAlloc 据此把两个角色拆开。开局用一小批候选做全量评测当热身，既筛出共享的高信息任务核心，也校准一个低秩 logistic 响应模型（按多维项目响应理论的形式建模，任务与候选各有自己的参数）；进入搜索后，任务侧参数冻结成公共参照尺，每个新候选只从稀疏观测里估计自己的参数；搜索结束后重拟合模型，用热启动的配对 successive halving 做终选——已有观测全部复用，只补缺失的评测。四个基准（HotpotQA、HoVer、DROP、IFBench）乘两个进化框架的实验里，这套分配用大约一半的评测单元，拿到了与全量评测持平或略高的平均 TEST 分数；消融显示贡献主要来自高信息任务分配和终选环节。

对自建 Agent 的开发者，这节课可以压缩成一句话：评测预算是决策依赖的，花之前先想清楚这次评测服务于哪个决策。搜索期的评测要便宜且可比，类似招聘里的简历筛选——目标是快速排除，不追求精确排名；终选的评测要准，类似终面——只留给少数候选，但每个都看透。把终面的深度花在简历筛选上，预算很快就烧完；反过来用简历筛选的精度做终选，选错的代价更高。同一个道理也解释了上一节的一条教训为什么成立：换了参照尺的分数不可比——这正是「换模型等于重新验证」的另一种表述。

边界照例要说。实验任务都有明确的验证器（QA 有标准答案、IFBench 有可执行检查），无验证器场景下的行为对比怎么分配预算，这篇论文没有覆盖；热身候选数、稀疏采样比例这类超参数依赖任务集规模，照搬具体数字没有意义。它和前两节合起来，自进化的三件事算是齐了：改什么（两路分工的提案）、改得对不对（行为对比与过程指标）、花多少评测（按角色分配预算）——剩下的都是工程。

## 调模型 API 与委托完整 Coding Agent 的区别

一次模型 API 调用接收输入并返回文本或工具请求；完整 Coding Agent 还拥有工作目录、会话状态、工具运行时、权限、错误恢复和验证循环。委托给另一个 Agent 等于启动一个受约束的执行者，不只是向模型问一道题。

子 Agent 能独立搜索和测试，但也会带来额外上下文、权限与协调成本。任务若只是改写一句文案，直接模型调用更合适；若需要在独立代码范围内探索、修改并交付证据，Agent 运行时才有价值。

## 回答关键问题

**Coding Agent 和代码补全有什么区别？** 前者能跨文件使用工具并根据执行结果循环，后者主要续写局部上下文。

**为什么还需要符号导航？** 它帮助定位定义、引用和调用关系，比只做文本读取更有效地建立大型仓库上下文。

**测试通过就完成了吗？** 不一定，还要检查需求、Diff、测试覆盖和环境差异。

**为什么频繁运行搜索、测试和 Git 工具？** 因为项目状态在模型之外且会变化；工具把真实证据带回循环，避免凭训练记忆一次性猜完整仓库。

**怎样避免改对一个文件却改坏项目？** 检索调用关系和规则，采用小 Diff，运行分层验证，检查失败路径，并保护用户现有变更。

**直接调用模型与委托 Coding Agent 有何区别？** 后者多出有状态运行时、工具、工作目录、权限、恢复和可验证交付。

**Harness 会自己越用越好吗？** 开始出现这类方法：用行为对比验证 Harness 修改、把改进经验沉淀成库供后续任务复用；代价是额外的执行开销，经验库本身也需要治理。

**任务成功就说明 Harness 靠谱吗？** 不。实验里 31.1% 的成功运行至少违反一条 Harness 可靠性标准；成功率和过程质量要分开度量，而且 Skill 类改进是能力条件性的，换模型后要重新验证。
