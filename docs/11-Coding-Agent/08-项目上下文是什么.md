# 项目上下文是什么？

> 所属专题：Coding Agent · 前置：[Coding Agent 是什么](./04-Coding-Agent是什么.md) · 后续：[上下文工程是什么](./09-上下文工程是什么.md)

模型见过许多代码，为什么进入一个大型仓库后仍需要搜索、符号导航和项目规则？因为训练知识只提供通用模式，当前仓库的真实架构、版本、未提交变更和团队约定必须在运行时读取。

项目上下文（Project Context）是 Coding Agent 完成当前任务需要了解的项目信息：相关代码、配置、测试、文档、仓库规则和当前变更状态。

它不等于把整个仓库一次性塞进模型窗口。

## 修复登录超时需要看什么

任务是“修复登录超时”。有用的项目上下文可能包括：

- 登录入口和会话代码；
- 超时配置与环境变量；
- 失败日志和相关测试；
- 项目编码规范；
- 当前 Git 差异与近期相关提交。

图片素材、无关模块和完整历史日志可能只会增加噪声。

刚接到任务时，Agent 还不知道登录入口在哪里。它可能先看目录和项目说明，再搜索“session”“timeout”等符号，沿调用关系找到会话服务，最后读取失败测试和配置。此时真正有用的不是搜索命中的所有文件，而是能解释“请求从哪里进入、超时值在哪里生效、失败怎样被验证”的那一小片代码邻域。

如果第一次修改后测试出现数据库错误，任务所需信息又变了。数据库连接配置和测试夹具会进入项目上下文，刚才读过但与新错误无关的页面组件可以退到背景。项目上下文因此更像一份随证据更新的工作材料，不是一包在开工前一次装满的文件。

## 项目上下文从哪里来？

```text
用户需求
 + 仓库指令
 + 文件与符号搜索
 + 配置、测试和文档
 + 终端 / Git 当前状态
 + 工具执行结果
       ↓
当前任务可用的项目上下文
```

项目上下文会随任务推进变化。测试报错后，新日志和相关文件可能比最初计划更重要。

## 为什么不能读取整个项目？

仓库可能远大于[上下文窗口](../02-聊天Token与上下文/07-上下文和上下文窗口是什么.md)。即使放得下，更多信息也不保证利用得更好：无关内容会稀释重点，旧文件还可能误导模型。

更合理的过程是先建立项目地图，再按任务检索，读取必要邻域，并在发现新证据时更新选择。

“必要邻域”通常包含目标代码的定义、调用者、被调用者、类型、配置和测试。只看目标函数可能漏掉上游传入的单位，也可能没发现下游依赖某种错误格式；把邻域无限扩大，又会让旧实现和相似命名混进来。选择范围要能解释当前假设，也要能支持下一步验证。

## 减少每次开工重新认识项目

Coding Agent 第一次进入仓库时，需要建立目录、语言、构建、测试和核心模块地图。若每个任务都从零扫描，会浪费工具调用和上下文；若把旧扫描永久当真，又会在仓库变化后误导。

可以保存低成本、可刷新且带版本的信息：

- 仓库入口、主要包和构建命令；
- 规则文件与适用目录；
- 符号索引和依赖图，标记生成时间或提交；
- 常用测试与 CI 入口；
- 架构决策记录及其来源；
- 最近任务状态，但恢复时核对当前 Git。

稳定地图用于缩小首次搜索范围，具体任务仍需读取当前实现。缓存应以提交哈希、文件时间或索引版本失效，不能把“上次目录”当成永远的项目事实。

探索也应由粗到细：先读根目录和规则，再搜索目标符号，沿调用链展开，最后才打开大文件或长日志。每一步都根据新证据缩小范围，而不是并行读取所有可能相关内容。

## 大型仓库为什么会让 Agent 变慢

文件多不只增加“阅读量”。未跟踪的构建产物会拖慢 Git 状态，递归扫描可能进入 `node_modules` 或生成目录，符号索引会占 CPU 与磁盘，搜索结果和日志又可能膨胀上下文。

诊断时把各层分开：

- Shell 命令本身是否慢，例如 `git status` 或文件遍历；
- 搜索是否遵守 `.gitignore` 并排除生成目录；
- 索引是一次构建、增量更新还是每轮重建；
- Tool 输出是否截断与分页；
- Agent 是否重复读取同一文件；
- 上下文压缩后是否丢失已建立的项目地图。

优化可以从收紧工作区根目录、维护忽略规则、缓存带版本索引、限制输出和复用已验证地图开始。不能为了提速跳过 Git 状态或规则检查，否则会把性能问题变成数据覆盖风险。

## 除了代码还要看什么？

- `README`、`AGENTS.md` 与贡献规范；
- 依赖和构建配置；
- 数据库迁移与接口结构定义；
- 测试、CI 和发布设置；
- 当前分支、未提交变更与差异；
- 需求、错误复现与验收标准。

只读实现文件，可能写出能编译却破坏项目约定的修改。

## 三个边界不要混在一起

### 项目上下文不等于模型训练知识

模型可能懂某个框架，但不知道当前仓库使用的版本、封装和规则。

### 项目上下文不等于上下文窗口

上下文窗口是容量边界；项目上下文是从项目中选择出来的任务信息。

### 项目上下文不等于全部文件

关键是相关、最新且可验证，不是数量最大。

## 为什么符号导航不只是“高级搜索”

文本搜索能找到同名字符串，符号导航还能追踪定义、引用、类型和调用关系。大型仓库中，同名函数、生成代码和跨包封装很常见；只读原始文件会消耗更多上下文，也更容易漏掉真正运行路径。

搜索到同名函数后仍要检查调用链、测试、配置和运行路径。工具结果和代码修改还会改变状态，因此任务开始时读取一次并不够。

当前未提交变更属于真实状态，不能因为历史提交更整齐就覆盖用户工作。Agent 每次编辑前都应检查分支、状态和差异。

## 指令文件为什么会过期：维护债的利息

前面几节反复强调「缓存要以提交哈希或索引版本失效，不能把上次的目录当成永远的项目事实」，但有一类信息长期漏掉了这条规则：`AGENTS.md`、`CLAUDE.md` 这类仓库指令文件。它们和符号索引一样是缓存——某个时刻对项目状态的一次快照——却几乎没有团队给它们配套失效机制。2026 年 11 月，北卡罗来纳州立大学的 Mehtiyev 等发表了第一篇受控实验来量化这个缺口（arXiv:2611.09802）。论文借技术债的比喻给这种现象起了名字：指令文件里过期的一行是文档债（documentation debt），本金是修复它需要的那一行编辑，利息是之后每个 Agent 会话都要替它多付的工作。

实验设计很克制，也因此结论扎实。研究者从三个活跃开源项目里各找了一条真实过期过的指令，覆盖指令文件最常见的三种指引：一条测试命令（`pyflow`，测试目录搬走后命令还指着旧路径）、一处代码位置（`cog`，接口文件换了地方）、一套操作步骤（`aghub`，新增组件的步骤指向已迁走的目录）。然后他们把同一个仓库、同一批 22 个真实缺陷任务，分别在指令的三种版本下跑：保留过期（stale）、改成正确（corrected）、整行删掉（removed），两个模型（Claude Sonnet 5.5 与 Haiku 5.5）共分析了 732 条运行轨迹，逐个工具调用对比。

第一个发现是：过期的指令只有在任务路线经过它时才产生利息。测试命令几乎所有任务都要用——每个修复的最后一步都是跑测试——于是 80 次过期运行里 78 次都执行了那条失效命令；操作步骤在缺陷报告只说了「某模块行为不对」时，80 次里 55 次走进旧目录；而代码位置那条，没有任何任务需要靠它找文件，84 次运行零次碰它。最值得警惕的是一个反直觉细节：缺陷报告明明写出了函数所在的正确模块，Sonnet 仍在 20 次里的 12 次钻进指令指向的旧文件夹——文件是宿主每个会话自动加载的，它的权威感压过了报告里更新、更准确的证据。

第二个发现是利息的形状：任务照常完成，成本藏在过程里。因为旧目录不存在，那条测试命令收集不到任何测试就报了错——但 Agent 习惯把输出接给 `tail` 或 `head`，管道让 shell 报了成功。80 次过期运行里 64 次至少跑了一次「没跑任何测试的测试」，Sonnet 有 19 次运行第一次验证修复时用的是这种空跑，而它的 40 次正确指令运行里一次都没有。两个条件下缺陷修复率几乎完全一样（p=1.0），有四个任务甚至三种条件下产出的补丁逐字节相同——变的只有到达补丁的路径：Sonnet 在过期条件下平均 7.8 次工具调用，正确条件下 5.8 次，多出约三分之一。一项只看任务成功率的评测会给三种条件打出一模一样的分数，这正是文档债能长期藏住的原因。

第三个发现最说明债务为什么还不上：Agent 会绕过，但从不修理。133 次真正踩到过期路径的运行里，130 次在几次调用内恢复了进度——大多靠搜索仓库找到当前位置。可恢复不等于上报：最终答复真正指出那条指令失效的只有 21 次；指出来的也没有一次提议修正；而 732 次运行里，没有一次运行修改过指令文件。Agent 付掉了利息，本金的偿还权在维护者手里，而绕行恰好切断了这两者之间的信息通路——补丁交付了，下一次会话面对的还是同一条过期指令。

给维护者的操作结论，论文的数据支持「改对优于删除」。删掉过期行能阻止大部分踩踏（命令场景 80 次里只剩 1 次），但删不干净也不省钱：没有指令时 Agent 会自己猜目录（步骤场景删掉后 80 次里仍有 20 次猜进旧目录），Sonnet 在删除条件下跑测试花的工具调用和保留过期指令时一样多——它得自己摸索怎么跑。只有把那行改成正确路径，80 次运行才全部归零。再配三条便宜的防线：指令文件里的路径可以脚本化核验存在性（过期路径是可检测的，不需要判断内容对错）；shell 开 `pipefail`，让接进 `tail` 的失败命令不再伪装成功；Agent 侧把「no tests ran」当失败而不是成功。这些建议论文都注明未评估效果，但成本都接近零。

边界照例说清楚。这是三个案例、两个模型、一个宿主的深度实验，指令类型、仓库和任务捆绑在一起，没法拆开各自的影响；任务都是小型缺陷修复，更重的维护工作可能呈现不同的成本形态；作者自己修正过一次过期路径检测器的漏报并公布了修正前后两套数据——这种透明本身就值得学。把这一节放回本文的线索里：项目上下文的每一条来源都有保鲜期，指令文件不因为它是「写给 AI 的规则」就豁免——它恰恰是唯一每个会话都被全量读取、却最缺少失效机制的来源。

## 项目上下文错了会怎样

信息缺失时，Agent 可能重复实现已有能力、调用错误版本的接口，或者只修表面症状。信息过期时，它可能按照旧目录、旧配置或已经撤销的需求修改代码。信息互相冲突时，则要先确认哪一份更权威、更新日期是什么，而不是挑一段最容易执行的内容。

判断项目上下文是否够用，可以问三个问题：现在的证据能否解释问题，修改是否符合仓库规则，验证方式能否证明任务真的完成。如果其中一个答案仍靠猜，就应该继续检索或运行工具，而不是急着生成更多代码。

## 把真实问题收回来

**为什么大型代码库还需要 IDE 式符号导航？** 因为定义、引用、类型和调用关系不总能靠字符串可靠恢复。语义导航能用更少上下文定位真正相关的代码邻域。

**指令文件里的测试命令失效了，Agent 为什么不自己修？** 实验里 732 次运行没有一次修改指令文件：Agent 能绕过失效路径完成任务，但绕行不留信息通路——130 次恢复里只有 21 次在最终答复里指出指令失效，0 次提议修正。任务要求的是修代码，维护指令文件不在目标里，债务就留给下一个会话。

**过期指令和过期的符号索引有什么区别？** 都是缓存失效，但指令文件每个会话被全量自动加载，且以「规则」的身份出现，权威感压过了新证据——缺陷报告给出正确模块时，模型仍有超过半数的运行钻进指令指向的旧目录。

**发现指令过期该删除还是改对？** 改对。删除能阻止大部分踩踏但不省钱：Agent 会从代码结构猜目录（仍有 25% 运行猜进旧目录），跑测试的成本和保留过期指令时一样高；只有改对才让 80 次运行全部归零。

**项目上下文是整个仓库吗？** 不是。它是当前任务所需、最新且可验证的信息集合，并会随执行结果变化。

**历史代码和当前工作区冲突时看哪个？** 当前工作区是正在操作的真实状态；历史用于理解背景，不能覆盖未提交修改。

**怎样减少 Coding Agent 每次重新认识项目？** 保存带版本的目录地图、规则、索引和测试入口作为导航缓存，但在具体任务中用当前文件与 Git 状态重新验证。

**大型 Git 仓库为什么让 Agent 卡住？** 文件遍历、Git 扫描、索引、超大工具输出和重复上下文都会贡献，应逐层计时而不是只归因于模型。
