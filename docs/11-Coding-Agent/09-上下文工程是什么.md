# 上下文工程是什么？

> 所属专题：Coding Agent · 前置：[项目上下文是什么](./08-项目上下文是什么.md) · 后续：[聊天记录是什么](../12-Memory/01-聊天记录是什么.md)

上下文工程（Context Engineering）是系统性地决定模型运行时应该看到什么信息、以什么顺序看到、何时更新或压缩这些信息。

它比“把 Prompt 写得更漂亮”范围更大。

## 上下文里可能有什么

- 系统与开发者指令；
- 用户请求与对话历史；
- 检索到的项目文件和资料；
- Tool 定义与执行结果；
- 计划、状态和长期记忆；
- 输出格式与验证规则。

```text
收集候选信息
  ↓
选择相关且可信内容
  ↓
按角色、顺序和结构组织
  ↓
模型计算与工具行动
  ↓
根据新结果更新或压缩上下文
```

## 和提示工程的区别

提示工程（Prompt Engineering）主要关注怎样表达指令、示例和输出要求。上下文工程还包含检索、工具结果、历史裁剪、长期记忆、权限过滤和长任务状态管理。

Prompt 是上下文的一部分，提示工程是上下文工程的一个子问题。

例如一句“修复支付失败”写得再清楚，也没有告诉模型当前仓库使用哪个支付模块、最新错误是什么、哪些文件不能改。提示工程可以把目标和约束说准确；上下文工程还要负责找出相关代码、放入可靠日志、保留仓库规则，并在测试结果出现后更新材料。

## 为什么更多 Context 不一定更好？

上下文窗口有容量限制，模型对不同位置和噪声的利用能力也有限。重复、冲突和无关内容可能让重要证据更难被使用。

因此目标不是“塞满窗口”，而是在正确时间提供完成当前步骤所需的最小充分信息。

这里的“最小”不是越少越好，“充分”也不是把一切都带上。若任务要求修改接口，至少需要接口定义、关键调用方和验证方法；若其中缺少一个，信息就不充分。反过来，把整个仓库、几百条旧日志和重复规则一起加入，只会增加成本与冲突机会。

顺序也会改变使用效果。系统规则、用户目标、原始证据和工具结果承担的角色不同，不应揉成一段无法追溯的摘要。遇到冲突时，系统要知道谁更权威，并保留来源，才能判断该遵守仓库规则、最新用户要求，还是已经过期的旧计划。

## 长任务怎样管理 Context？

常见做法包括：

- 把稳定规则保留在明确位置；
- 按需检索文件，不重复粘贴全仓库；
- 把旧步骤压缩成可核验摘要；
- 将详细证据保存到外部状态，按需读取；
- 保留关键决策、失败和未完成项；
- 工具执行后淘汰已经失效的假设。

摘要也可能丢信息，因此重要原始证据需要可回查。

以一个长时间运行的 Coding Agent 为例：开始时需要需求、仓库规则和目录地图；定位问题时需要搜索结果、调用链与复现日志；修改后需要差异、测试结果和失败原因。三个阶段看到的信息不必完全相同，但目标、关键约束和未解决风险不能在压缩时消失。

如果摘要写着“测试通过”，原始输出却只跑了一个测试文件，这份摘要就会制造错误信心。好的压缩不仅缩短文字，还要保留完成了什么、没有完成什么、证据在哪里，以及哪些判断仍需复核。

## Coding Agent 的持久记忆怎样落地

长任务最怕把“曾经聊过”误当作“以后能恢复”。架构决定、接口约束和调试结论若只存在对话里，压缩或新会话后就可能丢失。更稳妥的做法是把可长期复用的事实写入版本化项目文档，把当前计划、未完成项和阻塞写入结构化任务状态，把测试输出、日志和差异作为可回查证据；对大量历史再建立检索入口。

保存时要区分事实、判断和尝试。例如“接口返回 401”是观察，“令牌过期”是尚待验证的解释，“刷新令牌后重试”是行动。若把三者压成一句“认证问题已修复”，后续 Agent 会在错误完成状态上继续。每条关键记录最好包含来源、时间、适用版本和验证状态。

持久化也需要清理。代码和环境变化后，旧决策可能失效；失败尝试可以帮助避免重复撞墙，却不应永远压过最新证据。恢复任务时先读取当前仓库与外部状态，再把长期记录当线索核对，而不是把记忆当作永远正确的事实库。

## 三个相邻概念的边界

### 上下文工程不等于扩大窗口

窗口更大只是容量变化；工程问题是如何选择和组织信息。

### 上下文工程不等于 RAG

RAG 是检索外部资料的一种流程；上下文工程还管理指令、工具、历史和状态。

### 上下文工程不等于微调

上下文工程改变运行时输入，不更新模型参数。

## 长任务最容易出什么问题

重复会消耗容量并可能造成冲突，重要规则应清晰、单一且放在正确层级。

摘要是有损压缩，需要保留原始来源并验证关键细节。

在 Agent 中，它还会影响 Tool 选择和现实操作，因此权限过滤非常重要。

上下文工程还承担安全边界。检索到的网页、代码注释或文档可能包含不可信指令；系统需要区分“任务规则”和“被分析的内容”，并在敏感数据进入模型前做权限检查。能检索到某份文件，不代表当前用户或当前任务就有权使用它。

## 判断是否做对了

好的上下文不是最长，而是让模型在当前步骤看到相关、可信、及时的最小充分信息。还要能追溯关键证据，发现环境变化后淘汰失效假设，并确认权限过滤发生在内容进入模型之前。

**Coding Agent 怎样保留架构决策和调试经验？** 把稳定决策写入版本化项目文档，把进行中的任务写入结构化状态，把日志和测试保留为证据，再用检索按需取回；每次恢复都要与当前代码和环境重新核对。

提示工程是其中一部分；RAG、历史裁剪、工具结果、长期记忆和状态压缩都属于更大的运行时信息工程。它们改变输入，不等于训练参数。
