# Vector Database 是什么？

> Level: `Core` · Path: `Main`

## 一个小白真的会怎么问？

> 向量数据库里存的是原文，还是一堆数字？
>
> 做 RAG 是不是一定要买一个向量数据库？

## 先说人话

Vector Database（向量数据库）是面向向量保存、索引和相似性检索设计的数据库系统。

它通常把 Embedding 向量与原文引用、ID 和元数据关联起来，让系统能快速寻找“与查询向量较接近”的候选内容。

## 举个例子

知识库里有十万段文档。系统可以保存：

```text
chunk_id: policy-2026-017
vector: [0.12, -0.37, 0.81, ...]
source: 差旅政策.pdf
region: CN
updated_at: 2026-07-01
text: 对应原文或原文位置
```

用户提问后，系统生成查询向量，检索相近向量，并通过元数据过滤到中国区、当前版本的资料。

## 严格来说

向量数据库常提供：

- 向量与关联数据的写入、更新和删除；
- 相似度搜索；
- Metadata Filter（元数据过滤）；
- 面向大规模数据的向量索引；
- 持久化、权限、备份或分布式运行等数据库能力。

不同产品支持范围不同。“能搜索向量”不自动代表拥有所有传统数据库能力。

## 为什么需要向量索引？

数据很少时，可以把查询向量与每个文档向量逐一比较。数据变大后，逐个计算会变慢。

向量索引会组织向量，减少需要完整比较的候选。HNSW 等方法常用于 Approximate Nearest Neighbor（近似最近邻）搜索：用较高召回率换取更快速度和更大规模。

“近似”意味着结果不保证每次都是数学上绝对最近的全部向量，需要在速度、内存和召回率之间调节。

## 数据库里要保存原文吗？

系统至少需要保留从向量回到可使用证据的方式。常见做法是：

- 向量数据库同时保存原文和元数据；
- 或只保存 ID，再到文档库读取原文；
- 或由同一数据库的不同字段共同保存。

只返回向量数字，模型无法据此引用和回答原文内容。

## 做 RAG 一定需要 Vector Database 吗？

不一定。小规模数据可以使用内存索引、向量检索库，或带向量扩展的普通数据库。关键词检索和 SQL 也可能更适合某些任务。

是否需要专用向量数据库，取决于数据规模、更新频率、延迟、过滤、权限、运维与现有技术栈。

## 最容易搞混的东西

### Vector Database ≠ Embedding Model

Embedding Model 产生向量；Vector Database 保存和检索向量。数据库不会自动生成高质量语义表示。

### Vector Database ≠ Knowledge Base

知识库还包括原始资料、版本、权限和治理。向量数据库可能只是其中一个索引组件。

### Vector Database ≠ RAG

RAG 还需要查询理解、检索、Context 组织、生成和验证。

### 向量相近 ≠ 事实相同

向量搜索返回的是候选。数字、否定、时间和细粒度条件仍可能不匹配。

## 常见误区

### 误区 1：Top 1 就是正确答案

排名第一只表示在当前向量、索引和过滤条件下得分较高，不代表它能回答问题。

### 误区 2：换 Embedding Model 不用重建索引

通常需要重新生成资料向量，因为新旧模型的向量空间往往不兼容。

### 误区 3：向量数据库会自动处理权限

只有正确写入权限元数据并在查询时强制过滤，访问控制才会生效。不能让模型事后自行保密。

## 为什么我要知道它？

理解 Vector Database，能帮助你判断 RAG 问题出在向量、索引、过滤、原文还是生成阶段，也能避免把购买数据库当作完成知识系统。

## 你只需要记住

1. Vector Database 面向向量保存、索引和相似性检索。
2. 向量通常要关联原文、ID 与元数据，才能成为可检查证据。
3. 近似最近邻在速度与召回之间权衡，不保证绝对精确的最近结果。
4. Vector Database 不等于 Embedding Model、Knowledge Base 或完整 RAG，也不是所有 RAG 的必需品。
