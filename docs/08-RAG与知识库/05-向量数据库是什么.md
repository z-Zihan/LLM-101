# 向量数据库是什么？

> 所属专题：RAG 与知识库 · 前置：[Embedding 是什么](./03-Embedding是什么.md) · 后续：[检索是什么](./08-检索是什么.md)

向量数据库（Vector Database）是面向向量保存、索引和相似性检索设计的数据系统。它让应用在大量 Embedding 中快速寻找与查询向量接近的候选，并把候选重新连回原文、来源和元数据。

买了向量数据库不等于完成 RAG。数据库解决的是存储与检索基础设施，Embedding 质量、文档治理、查询策略、生成和验证仍在其他层。

## 一条向量记录里通常有什么

公司知识库的一段政策可能被保存为：

```text
chunk_id: policy-2026-017
vector: [0.12, -0.37, 0.81, ...]
source: 差旅政策.pdf
region: CN
version: 2026-07
text: 原文片段，或指向原文存储的 ID
```

查询时，系统生成问题向量，按相似度找候选，同时用 `region=CN`、当前版本和用户权限过滤。只返回向量数字，生成模型无法阅读政策，也无法向用户展示证据。

原文是否与向量存放在同一个数据库里，由实现决定。有的记录直接保存文本和元数据，有的只保存文档 ID，再到对象存储或搜索系统读取。关键是必须保留一条受权限控制、可审计的回原文路径。

## 为什么不能把每个向量都逐一比较

数据很少时，查询向量可以与所有文档向量做精确计算。数据达到百万或更多后，逐个比较会带来延迟和计算成本。向量索引会组织空间，优先探索可能接近的区域。

HNSW 等近似最近邻（Approximate Nearest Neighbor，ANN）方法用少量召回损失换取更快搜索。参数调整会影响内存、建库时间、延迟和召回率；“近似”意味着它不保证列出数学上绝对最近的所有结果。

```text
精确搜索：比较全部向量 → 成本随数据量增长

近似索引：先缩小候选范围 → 更快，但可能漏掉近邻
```

这张图想说明索引优化的是搜索代价。读图时注意，找到“最近”也不代表内容能回答问题；语义模型、过滤和业务条件仍决定结果是否有用。

## 向量数据库和普通数据库的边界

许多普通数据库已经提供向量字段和索引，专用产品也会增加分布式扩展、过滤和运维能力。是否需要专用系统，取决于规模、更新频率、延迟、过滤、权限、备份和现有技术栈。

小型项目可以使用内存索引或现有数据库的向量扩展；精确编号与交易查询可能根本不该使用向量搜索。技术选型不应从“做 RAG 必须买 Vector DB”出发。

数据库也不会自动生成高质量 Embedding。模型升级后，新旧向量空间通常不兼容，需要重新向量化和建索引。数据库能保存错误向量，也能高效返回错误候选。

## 更新、删除与权限为什么重要

政策更新时，要写入新片段并撤下旧版本；删除文档时，也要删除对应向量和缓存。否则已经失效或无权访问的内容仍可能被召回。

权限应在检索前或检索过程中由系统强制过滤，不能先把机密片段放进模型上下文，再靠 Prompt 要求保密。向量相似性不会理解组织授权。

备份、恢复、一致性和审计能力因产品而异。“能做向量搜索”不等于拥有传统数据库的所有保证，选型要核对实际文档与测试。

## 回答真实问题

**向量数据库里存原文还是数字？** 至少存向量；通常还保存原文和元数据，或保存能受控取回原文的 ID。

**为什么不能只存向量？** 模型需要可读证据来回答和引用，向量本身不是可审查原文。

**做 RAG 一定需要向量数据库吗？** 不需要。关键词、SQL、内存索引、普通数据库扩展和混合方案都可能适合。

**Top 1 是正确答案吗？** 只是当前模型、索引和过滤条件下得分较高的候选，不是正确性保证。
