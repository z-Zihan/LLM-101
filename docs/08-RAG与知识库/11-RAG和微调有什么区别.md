# RAG 和微调有什么区别？

> 所属专题：RAG 与知识库 · 前置：[检索是什么](./08-检索是什么.md) · 后续：[RAG 有哪些局限](./12-RAG有哪些局限.md)

想让模型“懂公司资料”，应该做 RAG 还是微调？先别从技术名词选方案，要确认缺的是资料，还是行为。RAG 在请求时检索外部证据并加入上下文；微调（Fine-tuning）继续训练模型，用样本更新参数。

```text
RAG：改变这次请求给模型看什么
微调：通过训练改变模型以后怎样响应
```

这张图概括的是主要边界，不是说微调学不到事实、RAG 影响不了行为。读图时注意两者发生的阶段和维护方式不同。

## 两个需求会走向不同方案

公司政策每周变化，希望答案引用当前条款。RAG 更容易维护：更新权威资料和索引，下次请求检索新版本，不必重新训练整个模型。

另一个团队希望客服模型稳定输出固定 JSON 字段、使用统一标签，并学会大量示范中的分类边界。若 Prompt 和普通代码仍不稳定，微调可能更合适，因为目标是反复出现的行为模式。

现实项目可能两者都需要：微调模型遵循领域任务和格式，RAG 在每次请求中提供最新证据。组合前仍要分别证明每一层带来收益。

## 对比的是更新位置，不是流行程度

| 维度 | RAG | 微调 |
|---|---|---|
| 主要改变 | 当前上下文与外部证据 | 模型参数 |
| 发生时间 | 每次请求的检索与生成阶段 | 独立训练阶段 |
| 更新资料 | 替换资料并重建相关索引 | 准备数据并再次训练、评估、发布 |
| 来源追踪 | 可保留原文与引用 | 参数中的来源难以逐条追踪 |
| 常见用途 | 私有、易变、可引用知识 | 格式、风格、分类和任务行为 |

这张表只描述常见倾向。效果还取决于模型、数据质量、任务、评测和部署条件，不能用它替代实验。

## 微调能把知识可靠地写进参数吗

训练样本会改变参数，模型可能记住或泛化其中的信息。但微调不是逐行更新数据库：无法保证每条事实都被准确保存、在所有问法下稳定取出，或只修改目标知识而不影响其他行为。

对必须显示来源、频繁变化或有访问权限的事实，外部权威系统通常更易治理。微调数据还可能过时、冲突或泄露敏感内容，发布前需要单独评估。

微调也不会自动消灭幻觉。它优化的是给定训练目标，模型仍可能在未知问题上生成无依据内容。

## 个人文档问答为什么通常先试 RAG

一位真实提问者想让模型回答一组个人文档里的事实：既然模型能回答训练语料中的知识，为什么不直接把这些文档拿去微调？关键不是微调“绝对学不会”，而是这个需求更像查询资料，而不是塑造行为。

个人文档会增删和改版，回答还常常需要指出原文依据。RAG 可以保留文档、版本、权限和引用位置；更新资料后重新处理相关索引，就能让后续请求检索新内容。若把事实主要压进参数，每次更新都要重新准备训练数据、训练、评估和发布，而且很难说明某句话究竟来自哪一页。

微调当然可能记住部分事实，也可能学会领域术语和回答方式。问题在于它不保证每条事实都能在不同问法下稳定取回，更没有逐条更新、删除和审计的数据库语义。把“微调不适合作为首选知识查询层”说成“微调完全学不到事实”，同样不准确。

RAG 也不是稳赢：检索可能漏文档、切片可能丢语境，模型也可能忽略正确证据。实际选择应比较可引用性、更新频率、权限要求和评测结果；如果还需要固定格式或领域行为，可以在 RAG 提供事实的同时，用微调改善行为。

## RAG 能不能教会模型新行为

检索到的示例和指令会影响当前输出，few-shot Prompt 也可能暂时表现得像“学会了”。但底层参数没有因此更新；信息离开上下文后，行为不一定保持。

若需求可以通过清晰 Prompt、结构化校验或固定 Workflow 解决，不必立即微调。若问题是知识库里根本没有当前事实，再多微调格式也补不回来。先定位失败层，才能避免用昂贵方案修错位置。

## 微调数据先围绕目标，而不是围绕数量

准备数据前，先写清楚模型要在哪类输入上改变什么行为，以及用什么指标判断。分类任务要覆盖真实类别和容易混淆的边界；格式任务要保持输出协议一致；领域问答要区分“希望学会表达方式”还是“希望记住会变的事实”。把互相冲突、来源不明或模板化复制的样本堆得更多，可能让训练 Loss 更好看，却让真实任务变差。

训练集之外要留出未参与参数更新的验证和测试样本，并按来源、时间或用户场景防止近重复泄漏。少量高质量数据是否足够，没有脱离任务的固定答案：窄而稳定的行为可能很快出现改善，开放领域能力则需要更广覆盖。数据量、质量和任务目标不是三选一；任务目标决定“质量”具体指什么，评测再告诉你数量是否已经覆盖主要变化。

## 为什么训练 Loss 不等于产品变好

Loss 表示模型对训练目标的拟合程度，不直接等于事实正确、格式稳定、安全或用户满意。训练 Loss 持续下降而验证表现变差，可能是过拟合；验证集与训练集高度重复，也可能制造虚假的提升。

评估应从部署场景抽取独立任务集，与未微调基线做同条件比较，分别看目标能力、原有通用能力和风险行为。能够自动判断的格式、分类和单元测试可以量化；开放回答还要规定人工或模型评审的准则并抽查一致性。发布后数据分布改变，也要继续监测，而不是把一次离线分数当永久结论。

## LoRA 和 QLoRA 在节省什么

完整微调会更新大量基础参数。LoRA 冻结基础权重，在部分线性层旁加入较小的低秩可训练矩阵；训练和保存的参数显著减少，但前向、反向计算仍要使用基础模型。

QLoRA 沿用 LoRA 适配器，同时把**冻结的基础模型**以低比特形式放在显存中，并通过量化相关设计降低微调的内存占用。训练的适配器通常仍使用更高精度。它不是与 LoRA 毫无关系的另一种训练目标，也不意味着任何模型、数据和硬件上都保持相同质量。

两者主要改变微调的资源账和参数更新方式，不解决数据是否正确、任务是否适合微调、评测是否可信。若需求本来是查询持续变化的资料，换成 QLoRA 仍没有获得知识库的更新与引用能力。

## 选择前做一张需求账

问清楚信息多久变化、是否必须引用、谁能访问、是否已有足够高质量示例，以及错误能否自动验证。再比较建库、训练、推理延迟、评测和持续运维成本。

可以先做最小基线：Prompt 加普通代码；需要外部事实时加简单检索；行为问题有稳定数据和评测后，再尝试微调。每次只增加一个变量，才能知道提升来自哪里。

## 回答开头的问题

**想让模型懂公司资料，选哪个？** 易变、私有、需要引用的资料优先评估 RAG；稳定行为和格式问题再考虑微调。

**微调以后能当知识库吗？** 不能获得可逐条查询、更新和审计的数据库保证。

**RAG 会改变模型参数吗？** 普通 RAG 只改变本次上下文，不执行生成模型训练。

**两者能一起使用吗？** 可以，但要分别评估检索质量、回答忠实性和微调后的行为变化。

**个人文档问答为什么不直接微调？** 可以实验，但 RAG 通常更容易更新资料、控制权限、展示引用并审计答案。微调更适合稳定行为模式，不等于一套可逐条查询的文档存储。

**微调数据量、质量和任务目标哪个更重要？** 任务目标先定义什么算有效样本和成功；质量决定样本是否提供正确、一致的信号；数量要覆盖目标场景的变化，三者不能脱离彼此比较。

**微调后只看训练 Loss 为什么不够？** 它只反映对训练目标的拟合。要用隔离的真实任务集比较基线，并检查过拟合、能力退化和风险行为。

**LoRA 和 QLoRA 有什么区别？** LoRA 用少量低秩适配器避免更新全部基础权重；QLoRA 进一步量化冻结的基础模型以节省显存，训练目标和适配器思路仍属于 LoRA 路线。
