# RAG 和直接把资料放进 Prompt 有什么区别？

> 你现在的位置：[上下文](../02-聊天Token与上下文/07-上下文和上下文窗口是什么.md) → **直接上下文与 RAG** → [RAG 到底是什么](./01-RAG到底是什么.md)
>
> 所属专题：RAG 与知识库 · 本文是 Optional 扩展阅读

长上下文模型能一次放入越来越多文字以后，公开社区里出现了一个很实际的问题：传统 RAG 还有必要吗？如果资料能直接贴进 Prompt，为什么还要切片、索引和检索？

两种方式最后都要把资料放进模型当前上下文。差别发生在前面：直接上下文由用户或应用把选定资料整体送入；检索增强生成（RAG）先从更大的候选集合中查找，再只送入相关片段。一个省掉检索，一个省掉重复输入与无关内容。

## 先用十份合同，不要用一百万份文档

你要比较十份短合同，所有文件总量远小于上下文窗口。直接放入往往最清楚：资料集合固定，模型能同时看到跨文档条款，不必担心检索漏掉一份。

如果公司有一百万份文档，每天更新，还要按员工权限回答问题，就不能每次全部输入。RAG 会先根据问题、元数据和权限缩小候选，再把相关片段与来源送给模型。

```text
直接上下文：用户选资料 → 解析 → 整体放入 Context → 生成

RAG：资料入库与索引 → 查询 → 检索 / 过滤 / 重排
                         ↓
              相关片段放入 Context → 生成
```

这张图最重要的地方是：RAG 没有绕开上下文窗口，它增加了“选择资料”的系统。选择可以降低输入量，也会引入检索失败。

## 直接放资料的优势是少一层不确定性

当资料数量小、用户明确知道要看哪些文件、任务需要全局比较时，直接上下文有明显优势。系统不用建索引，不会因为查询词不匹配而漏掉关键段落，也更容易解释“模型看到了哪些完整文件”。

它仍然不是复制粘贴那么简单。PDF 要解析，扫描件需要 OCR，表格和页码要保留；超过窗口时必须截断、压缩或分批。即使全部放得下，模型对很长输入不同位置的利用也可能不均匀，“在上下文里”不保证“一定正确使用”。

每次重复发送相同大文件还会增加 Token、延迟和费用。资料更新后，应用要确认传入的是新版本；多人共享场景还要在每次请求前重新做访问控制。

## RAG 的价值是选择、更新和治理

RAG 把资料处理分成离线与在线两部分。离线阶段解析文档、切片、建立 Embedding 或关键词索引并保存元数据；在线阶段根据问题检索、过滤、重排，再把少量证据送进模型。

这适合候选集合大、查询只涉及局部、资料频繁复用的系统。索引可以增量更新，片段可以保存来源、版本和访问标签；检索日志还能说明某次回答为什么看到了这些证据。

代价是多出一整条失败链：文档可能解析错、Chunk 切断语义、查询改写偏离问题、Embedding 找不到精确型号、权限过滤遗漏、重排把正确片段排到窗口外。模型回答得不好时，必须先判断是“没检到”还是“检到了但没用对”。

## 长上下文不会自动消灭 RAG

更大的窗口提高了直接输入的可行上限，却没有消除带宽、延迟、费用、更新、权限和来源追踪。候选资料增长通常比单次问题需要的证据快；把所有内容都送入还会让无关段落相互干扰。

反过来，也不能因为已经建设知识库，就对每个问题强制 RAG。用户刚上传一份 20 页报告并要求总结，先把完整报告直接送入可能比切成几十块再检索更忠实。需要比较整本规范的章节结构时，只召回局部片段也会丢失全局关系。

实用判断可以从四个问题开始：

1. 候选资料能否稳定放进窗口，还是只会越来越大？
2. 任务需要完整阅读、跨文档比较，还是只找少量局部证据？
3. 同一批资料会不会被反复查询，更新和权限是否需要集中治理？
4. 检索漏答与长上下文遗漏，哪一种更容易被发现和验证？

## 很多系统最后会采用混合方式

用户可以把当前合同完整上传，同时让 RAG 从公司制度库检索相关条款；系统也可以先用元数据筛出十份候选文档，再把十份完整内容放入长上下文；还可以对短文档全文输入，对长文档只检索片段。

这不是两套互斥架构。直接上下文负责当前任务中明确选定的材料，RAG 负责从大集合中选择补充证据。最终都要记录资料身份、版本、权限和引用位置。

缓存也会改变成本，但不改变边界。平台可能复用相同前缀的计算，让重复长输入更便宜；缓存没有替你挑选相关资料，也不能自动更新过期文件或修正权限。

## 怎样验证两种方案

不要只看回答“读起来是否不错”。准备真实问题集，标出需要哪些文档和证据，再分别测量：检索是否找到、上下文是否包含、回答是否忠实、引用是否准确、拒答是否合理，以及延迟和成本。

直接上下文失败时，记录是否截断、解析失败或关键内容处在长输入中难以利用。RAG 失败时，把检索召回和最终生成分开评估。若正确证据根本没有进入上下文，就不应先调 Prompt 要求模型“更认真”。

权限也必须在资料进入模型前执行。RAG 的元数据过滤不能只靠模型生成；直接上传时也要确认用户有权读取文件和把它交给当前模型服务。回答阶段的引用不会补救之前的数据越权。

## 回到最初的问题

**上下文足够长，RAG 还有必要吗？** 对小而明确的一次性资料集，可能没有必要；对大规模、反复查询、持续更新且有权限要求的集合，RAG 仍负责选择与治理。

**直接放资料是不是一定更准确？** 它避免了检索漏召回，但仍可能解析失败、被截断或在长输入中利用不佳。准确性要按真实任务测试。

**RAG 是否更省 Token？** 它通常减少每次送入的资料量，却增加索引、检索、重排和运维成本。应比较完整系统成本。

**两者可以一起用吗？** 可以。当前文件全文输入，组织知识库按需检索，是很常见也容易解释的组合。
