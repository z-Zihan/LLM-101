# safetensors 和 GGUF 是什么？

> 所属专题：[参数](./06-参数到底是什么.md) → **模型文件格式** → [推理](./18-训练和推理有什么区别.md)
>
> 扩展路线：本篇解释文件、精度、量化和运行时四层边界，不改变主路线阅读顺序。

原始聊天追问“参数最后体现形式是啥”，公开开发者问题又问：一个 `safetensors` 模型能不能转换成 `GGUF`？这两个问题背后都藏着同一个误区：把“模型”“权重文件”“量化精度”和“运行软件”当成了同一件事。

训练后的参数确实会保存成文件，但扩展名只是入口。一个文件能不能运行，还取决于里面怎样记录张量、模型架构是否被目标程序支持、Tokenizer 和元数据是否齐全，以及权重使用什么数值类型。

## 先把四层分开

| 层次 | 它回答什么 | 例子 |
|---|---|---|
| 模型与架构 | 这些张量应怎样连接和计算 | Llama、Qwen 等架构及配置 |
| 容器格式 | 张量、名称、形状和元数据怎样排进文件 | safetensors、GGUF |
| 数值编码 | 每个权重用多少位、怎样分组近似 | F16、BF16、Q4、Q8 |
| 运行时 | 谁读取文件并在硬件上执行算子 | Transformers、llama.cpp 及其上层应用 |

这张表最值得看的不是产品名，而是四个问题互不替代。`GGUF` 文件可以保存 F16 张量，也可以保存多种量化张量；`safetensors` 可以保存不同数据类型的张量，本身也不保证某个推理引擎懂得怎样运行对应架构。

## safetensors 保存的是一组有边界的张量

safetensors 是 Hugging Face 推出的张量容器格式。文件开头先写一个长度值，随后是 JSON 头部，记录每个张量的名称、数据类型、形状和在后续字节区间中的位置；剩余区域主要保存连续的张量数据。

```text
8 字节头部长度
      ↓
JSON：张量名、形状、类型、数据位置
      ↓
连续的张量字节数据
```

这种布局允许程序先查看目录，再按需读取某些张量，也便于使用内存映射减少不必要的 CPU 内存复制。大模型权重仍可能拆成多个 `.safetensors` 分片，再用索引文件说明某个张量位于哪一片。

名称里的“safe”主要是在和 Python `pickle` 比较：safetensors 只表达受限的张量与字符串元数据，不把可执行 Python 对象一起反序列化，因此读取文件不应执行任意代码。

但“不会借反序列化执行代码”不等于“这个模型绝对安全”。文件仍可能损坏、包含 NaN 或异常权重，模型内容本身也可能产生有害输出；下载还应核对来源、许可证、哈希和仓库说明。格式安全只关闭了一类攻击面。

## GGUF 面向 GGML 生态的推理部署

GGUF 是 GGML 及其执行器使用的模型文件格式，也是早期 GGML、GGMF、GGJT 格式的后继。它把带类型的元数据、张量目录和张量数据组织在一起，强调可扩展、便于内存映射和较完整的单文件部署。

GGUF 常把架构名称、上下文相关配置、Tokenizer 信息和权重编码等元数据放进同一文件，llama.cpp 一类运行时可据此加载已支持的模型。这个设计适合在本地 CPU、GPU 或混合硬件上分发推理文件，但“元数据更完整”不代表任何 GGUF 都能被任何版本的软件打开：架构、量化类型和运行时版本仍须兼容。

GGUF 规范同时列出 F32、F16、BF16 和多种 Q4、Q5、Q8 等张量类型。因此：

> GGUF 经常承载量化模型，但 GGUF 不是量化算法的同义词。

一个文件名里的 `Q4_K_M` 通常描述权重编码方案；`F16.gguf` 仍是合法而且未采用 4-bit 权重量化的 GGUF。反过来，量化权重也不只存在于 GGUF 生态。

## 为什么不能只改扩展名

把 `model.safetensors` 重命名为 `model.gguf` 不会完成转换。转换程序至少要做这些事：

1. 读取模型配置，确认来源架构与张量名称；
2. 把来源张量映射到 GGUF 运行时约定的名称和布局；
3. 写入架构、Tokenizer 等必要元数据；
4. 按目标编码保存权重，若需要再执行量化；
5. 用目标运行时加载，并用已知输入检查输出与质量。

如果转换工具还不支持某个新架构，权重数值本身再完整也无法正确映射。多模态模型还可能需要视觉编码器或投影器等附加文件。LoRA 适配器也不能被当成完整底座模型直接运行。

转换与量化最好分开理解：先把来源模型转换成目标生态可识别的高精度 GGUF，再按需要生成 Q4、Q8 等变体，是常见流程；具体工具也可能合并步骤。无论哪种方式，量化后都要在目标任务上重新评估，而不是只看文件成功生成。

## 一个“模型仓库”通常不止权重

Transformers 生态中的仓库常同时包含：

- 一个或多个权重文件与分片索引；
- `config.json` 一类架构配置；
- Tokenizer 词表、规则与特殊 Token 配置；
- 生成配置、模型卡、许可证，有时还有自定义代码。

safetensors 文件本身通常不承担全部这些职责。GGUF 追求把推理所需信息放在单文件中，但实际应用仍可能另有聊天模板、视觉投影器、许可证和运行参数。一个 GUI 能列出文件，不代表它已经验证了这些资产彼此匹配。

Checkpoint 的范围还可能更大。为了继续训练，它可以另外保存优化器状态、学习率调度器、训练步数和随机状态；这些数据常比只用于推理的权重更多。把训练 Checkpoint 直接等同于发布模型文件，也会误判体积与用途。

## 下载时怎样选对文件

先看你使用的运行时明确支持什么格式和架构，再看硬件容量与目标任务，不要先被最小文件吸引。至少检查：

- 模型名称、版本与架构是否正确，底座版还是指令版；
- 文件是完整模型、适配器、视觉投影器，还是某个分片；
- 权重编码与量化方法是什么，目标硬件是否有对应算子；
- 上下文运行时还需要多少 KV Cache，不能把文件大小直接当峰值内存；
- 来源、许可证、校验哈希和转换者是否可信；
- 目标任务上的质量、速度和内存是否实测通过。

同一个 7B 模型的 Q4 文件通常比 F16 小，但实际内存还包含运行时缓冲、KV Cache 和可能的 GPU/CPU 副本。两个文件大小相近，也可能因量化方法、架构支持和硬件内核不同而速度差很多。

## 回答开头的问题

**参数最后体现成什么？** 训练后的参数是带名称、形状和数据类型的张量。它们可以写入 safetensors、GGUF 等容器；运行时还需要正确的架构与 Tokenizer 约定。

**safetensors 是“原始模型”、GGUF 是“量化模型”吗？** 这个说法过度简化。两者首先是容器格式；GGUF 支持 F16 等非量化类型，也支持多种量化编码。是否量化应看张量类型和转换说明。

**两者能互相转换吗？** 某些受工具支持的架构可以转换，但不是改扩展名。转换要映射张量、配置和 Tokenizer；目标运行时不支持的结构，格式转换也解决不了。

**用了 safetensors 就可以完全信任下载文件吗？** 不可以。它降低了 pickle 任意代码执行风险，不保证来源、许可证、权重质量和模型行为安全。
