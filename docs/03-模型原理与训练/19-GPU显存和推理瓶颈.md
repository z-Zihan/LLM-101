# GPU、显存和推理瓶颈

>
> 这是一篇硬件与性能扩展页，不改变 32 篇主路线顺序。

“模型能装进显存”只回答了能否启动，没有回答跑得多快。LLM 运行时间可能花在矩阵计算、从显存搬权重和缓存、GPU 间通信、请求调度或等待小 Batch 上；不同阶段的瓶颈也会变化。

GPU 提供大量并行计算单元和分层存储。HBM 或 GDDR 常被统称为显存，容量大于片上缓存，却离计算单元更远。算子只有同时安排好计算和数据移动，理论 FLOPs 才可能转成实际速度。

## 算力瓶颈与带宽瓶颈

一个操作需要的运算量与搬运字节之比称为算术强度。若每读一批数据就做大量计算，更可能受计算吞吐限制；若反复搬很多权重却只做少量运算，更可能受显存带宽限制。Roofline 模型用这个关系解释性能上限。

LLM 的 Prefill 会一次处理 Prompt 中许多 Token，矩阵乘法形状较大，权重可在多个 Token 间复用，通常更容易提高 GPU 计算利用率。Decode 每步只生成少量 Token，却要读取大量模型权重和 KV Cache，低 Batch 时常更像带宽受限。

这不是永久标签。更大的 Batch、量化、并行策略、投机解码和不同硬件会改变算术强度；超长 Prompt 的 Attention 也可能让 Prefill 受到显存容量或带宽限制。

## VRAM 无限大也不会让 GPU 无限快

显存容量决定权重、KV Cache、激活和运行缓冲区能否同时放下。增加容量可以避免 CPU Offload 或频繁换入换出，却不会自动增加：

- Tensor Core 等计算单元的峰值吞吐；
- HBM/GDDR 每秒可传输的数据量；
- PCIe 或 NVLink 的跨设备带宽；
- 内核、Batch 与调度对硬件的利用率。

一张容量很大但计算和带宽较低的卡，可以装下模型却生成很慢。相反，算力很强但容量不足，也可能因无法放置权重或 KV Cache 而不能服务目标上下文与并发。

## Tokens/s 需要拆开报告

把 Prompt 处理和生成混成一个 Tokens/s 会隐藏实际体验。常见指标包括：

- Time to First Token：从请求到首 Token 的时间，受排队和 Prefill 影响；
- Prefill Throughput：每秒处理多少输入 Token；
- Inter-Token Latency：连续输出 Token 之间的间隔；
- Decode Throughput：单请求或全服务每秒生成多少 Token；
- Request Throughput：给定延迟目标下每秒完成多少请求。

测试时应记录输入长度、输出长度、Batch/并发、精度、采样、硬件、软件版本和是否包含排队。单用户 50 tokens/s 与服务器总吞吐 5000 tokens/s 不能直接比较。

## KV Cache 怎样估算

标准自回归 Transformer 会为每层保存历史 Token 的 Key 和 Value。一个常用近似是：

```text
KV 字节 ≈ 层数 × 2(K和V) × KV Head 数
          × Head Dimension × 已缓存 Token 数
          × 每元素字节 × Batch
```

多头注意力中 KV Head 数可能等于 Query Head 数；Multi-Query 或 Grouped-Query Attention 会减少 KV Head，因此缓存明显变小。实际服务还会有分页、对齐、元数据、临时缓冲和碎片，公式只是下界估算。

例如 32 层、8 个 KV Head、Head Dimension 128、16-bit（2 字节）、8192 Token、Batch 1，近似需要 `32 × 2 × 8 × 128 × 8192 × 2` 字节，约 1 GiB。并发和上下文长度会近似线性放大这部分。

## 为什么两张卡通常不会快两倍

模型并行把一次推理拆到多卡后，设备要交换激活、分片结果或同步信号。PCIe、NVLink 和跨机网络都有有限带宽与启动延迟；算子过小、切分不均或频繁同步时，通信会盖过并行收益。

两张卡也可能只是解决“单卡装不下”，而不是缩短关键路径。流水线并行会有气泡，张量并行每层都有通信，CPU 调度和采样仍可能串行。只有可并行计算足够大、互联足够快且软件能重叠通信与计算时，速度才可能接近线性扩展。

## HBM、片上存储和计算核心怎样配合

HBM 容量大、带宽高，但访问仍比寄存器和片上 SRAM 慢。GPU 会把数据分块搬进更近的层级，让一个线程块重复使用；Warp 是一组以相同指令节奏执行的线程，Tensor Core 则加速特定矩阵运算。

数据不能一直留在 HBM 里“原地计算”，因为算术单元位于芯片内部。每次从 HBM 取数都付出能耗和时间；若数据在片上被重复利用，就能减少外部读写。布局不连续、分块不合适或线程分歧都会降低利用率。

## FlashAttention 主要减少数据搬运

标准 Attention 若把完整分数矩阵写回 HBM，再读取做 Softmax 和乘 V，会产生大量中间读写。FlashAttention 使用分块与在线 Softmax，在片上存储中计算局部块，避免物化完整矩阵。

它计算的是精确 Attention 的数值等价实现（受浮点舍入影响），主要收益来自更少的 HBM I/O 和更好的融合，而不是把理论上的所有 `QKᵀ` 乘加都删掉。序列长度、Head Dimension、硬件和实现版本会影响加速比例。

## 把「找 Key」的成本也压下去：从 FlashAttention 到层级稀疏注意力

FlashAttention 解决的是「别把中间结果来回搬」，但每一步 Attention 仍然要给全部历史 Key 打分——计算量随上下文长度平方增长，这个渐近规律它一点也没改。上下文到百万、千万 Token 量级时，平方项会压过一切常数优化，于是问题换了一种问法：能不能让每个 Query 只给一小部分 Key 打分？这就是稀疏注意力的出发点。注意区分两层：注意力在数学上仍是二次方的，但「决定看哪里」的索引器（indexer）可以做得更便宜——难点恰恰在这里，索引器自己若要扫一遍所有 Key，成本还是随长度线性涨。2025 年以来的稀疏注意力方案（NSA、MoBA、各家的块稀疏实现）都在回答「怎么选块」，而 2026 年 10 月底的两篇工作把「索引器本身的成本」也拉下了水。

第一篇是 Prefrontal AI 与 ETH Zürich 的 LSA（Latent Sparse Attention，arXiv:2610.42147）。它的索引器分两步：先把相邻 4 个 Key 池化成小块，再用一种叫 Ward 凝聚聚类的算法把语义相近的块合并成桶（bucket）——注意是按内容相似度聚类，不是按位置切窗口，所以语义相关但散落在 KV Cache 各处的 Key 会落进同一个桶。查询来了先给桶心（centroid）打分，只对选中的桶展开精确 Attention，另外保留 sink（开头的几个 Token）和局部窗口兜底。每个 Query 最终只看约两千多个 Key，与上下文总长无关。部署有两条路：D-LSA 用蒸馏把现成模型的稀疏化器训练出来（只训索引投影，主干冻结）；N-LSA 更激进——不设任何辅助损失和教师，预训练时直接靠「预测下一个 Token」这一个目标，让稀疏选择自己长出来。实测数字（10M Token 上下文）：在 GLM-5.3-Flash 上单层 Attention 的 Prefill 提速 22.7 倍、Decode 提速 4.6 倍；在标准全注意力基线的 Qwen-3.8-27B 上分别是 72.4 倍和 42.5 倍；端到端首 Token 延迟降低 2.2 到 9.2 倍。精度方面，RULER 长上下文基准在 10M 处与训练时就在用稀疏注意力的基线差距保持在 4 分以内；从头预训练的 N-LSA 在 0.5B 混合架构模型上几乎追平全注意力（128k 处 RULER 32.2 对 34.7，远超同预算下 NSA 的 19.2 与 SWA 的 3.0），单层训练还快 1.6 倍。

但 LSA 的 Flat 版本索引器仍要扫所有桶心，每个查询的成本随长度线性增长——只是常数极小。第二篇 Zyphra 的 ZHA（Hierarchical Attention，arXiv:2610.42112）从理论上把这层也解决了。它的出发点是一个实证观察：对自然语言，维持每层注意力概率质量所需的 Key 数量（top-p 集合大小）随上下文呈次线性幂律增长——上下文越长，注意力其实越「可压缩」。既然如此，把 Key 摘要递归地再摘要，建成一棵树；查询自顶向下路由，每层只展开少数分支。树深 L、每层压缩 C 倍时，打分成本按 O(log T) 增长，总注意力成本变成次二次方（但仍超线性）。ZHA 的可学习参数只有一组参考查询（reference query），用 4B Token 的 KL 蒸馏即可把 4B 到 35B 的现成模型转成树形索引，主干权重零改动；深至 6 层的树保持精度，roofline 成本模型预测与单层块稀疏方案的交叉点在约 0.5M Token——超过这个长度，层级索引开始碾压线性扫描。LongBench v2 上，ZHA 用 1.1% 的 Decode Key 比训练 Token 预算多十倍的 MSA 高出 14 分。

把这两篇放回本文的线索：FlashAttention 属于「常数因子」优化——把搬运做省；稀疏注意力属于「渐近复杂度」优化——把要打分的 Key 数量与上下文解耦；而 LSA/ZHA 这类层级索引是在渐近曲线上再压一档——连「找该看的 Key」这个动作本身也不随长度线性涨。三条线索各自独立成立，也常常组合出现。边界照例要说清：22.7 倍/72.4 倍是单层 Attention 的数字，全模型收益会被非全局层摊薄；LSA 的评测集中在 1M–10M 区间，日常几千到几万 Token 的场景下索引开销可能不划算（512k 处 Prefill 增益只有 2.1 倍）；ZHA 的次线性依赖「自然语言注意力可压缩」这一经验观察，对抗性的「随机 Token 任意检索」任务上该前提不成立；两篇都是 2026 年 10 月底论文，第三方复现结果尚待积累。对使用者的判断指引很简单：上下文在十万以内，FlashAttention 加 KV Cache 管理仍是主力；要到百万级以上乃至 Agent 长程任务的千万级，层级稀疏注意力这类方法就是绕不开的基建。

## 打分这件事也有讲究：KV Cache 驱逐该让哪一层来判

稀疏注意力解决「历史太多看不过来」，但只要历史还要留着，就绕不开另一件事：显存装不下时删什么、留什么。KV Cache 随层数、并发和上下文长度线性膨胀，最直接的省法是驱逐（eviction）：给每个缓存位置打分，留下分数最高的 k 个，其余的在 Decode 阶段遮掉。H2O、SnapKV 这类方法都这么干，它们吵的是「怎么打分」（累积注意力、滑动窗口、调整过的 Softmax），却共享一个从未被质疑的默认设置——**哪一层打分，就用哪一层自己的缓存**：第 7 层的缓存由第 7 层的注意力打分。打分层是所有驱逐方法都不报告、也不调节的超参数。

2026 年 11 月初的一项研究（arXiv:2611.02230）把这个默认设置翻了出来。它在 18 个有逐层缓存的模型上（0.5B 到 109B，横跨四家实验室）系统测量了「让同一层给所有层的缓存打分」时的精度曲线，得到一条在所有模型上形状一致的结论：浅层当裁判是灾难性的（最多掉 25 到 56 个百分点），精度在 0.4 到 0.75 深度处到达峰值，而最后一层也开始退化。机制不难理解：一层要打好分，前提是它已经「用问题找到了答案」——Query 拿着问题去匹配 Key 这个动作需要若干层的传播才能完成，浅层还没干完这件事，它的注意力分布分不出哪些 Token 是问题需要的；最后一层则已经转入产出分布的阶段。作者给了一个零自由参数的「存活率模型」验证这个解释：把驱逐建模成 top-k 截断，用预填充注意力直接算「答案 Token 全部落入保留集」的概率，这条曲线能复现实测的深度曲线（Spearman 相关 0.90 到 1.00），也能预测共享缓存架构里各读取层的排名。反过来做对照实验：把问题从窗口里拿掉，各层对答案 Token 的注意力差距缩小 6.5 倍——没有问题，各层一样瞎。

这条曲线有一个立刻能用的推论：与其让每层判自己的缓存，不如让一个校准选出的中深层统一给所有层打分。在 SnapKV 上的实验里，改动两处默认（中深层打分 + 所有头共享同一保留集）让 5% 到 15% 预算下的精度比原版高出 18 到 43 个百分点，在 1.5B 到 14B 的五个模型上显著。机制上的解释是：中深层的选择最能代表「答案需要什么」，而逐头保留集在每个头内做 top-k 会把「头间差异」误当成「重要性差异」。这个收益随规模递减——32B 以上检测不到增益，因为大模型的逐层默认已经接近最优中深层——但选错层的代价不随规模缩小，最差的层在任何规模都掉 25 个点以上。边界同样要说清：在开放域问答（LongBench）上没有任何中深层能显著超过逐层默认，收益集中在精确检索类任务（大海捞针、变量追踪、财报抽取）；校准需要一批已知答案的提示词。

这条曲线还解释了一类架构自带的坑。跨层共享缓存的模型（Gemma 3n/4、CLA/YOCO 一系）让一层计算缓存、多层直接读取，省显存的代价是「只能留一套 Token」——于是打分权归了写入层（writer），也就是最浅的那个读取层。在 Gemma-4-E2B 上写入层在 0.41 深度，正好落在曲线的坍塌区：10% 预算下写入层自己打分只得 23 分，换一个 0.56 深度的读取层（L19）打分拿到 51 分，差距 28 个百分点。同门的 E4B 把写入层放在 0.56 深度，这个惩罚就基本消失了——架构把打分权交给谁，比缓存怎么压缩更影响精度。给部署者的教训是：如果你在用共享缓存或逐层驱逐的模型，值得查一下打分层深度；如果自己校准不现实，rank consensus（几个读取层按排名投票）能收回大部分收益。

## 不训练也能上稀疏：CISA 与「改造存量模型」的路线

上一个问题问的是「缓存装不下时删什么」，还有一条互补的路线：干脆让每个 Query 只对选中的块做精确 Attention，从根上压掉要读的 KV 数量。上一节的 LSA/ZHA 都需要蒸馏或预训练才能把稀疏化器装进模型，而大量已经部署的稠密注意力模型没有这个待遇。NVIDIA 2026 年 11 月的 CISA（Chunk-Indexed Sparse Attention，arXiv:2611.03200）专门回答「不训练能不能改造存量模型」：把历史按 16 个 Token 一块分块（对齐 vLLM 的分页大小），每块用 Key 均值当一个代表向量；一个独立的索引 Query 给代表打分、选固定预算的块（比如 1M 上下文选 4096 块，约 6.6 万 Token），然后对选中的块用原始 K/V 做精确 Attention。索引器的初始化完全免训练：从模型现成的 Query 头里，按 DSA 式的 KL 匹配标准挑一个注意力分布最接近「组内各头平均分布」的投影直接复制过来，Ultra 550B 上 24 个层-KV 组里 23 个都选中了「各头 Query 的行平均」。

工程上的三个选择值得注意，它们共同回答「稀疏化怎么才能真正变快」。第一，按块而不是按 Token 索引：Token 级稀疏（如 DSA）的索引器仍要扫全历史，块级代表只有 1/16 的数量，且代表随主 Key 的张量并行分片存放，避免一份索引缓存跨卡复制。第二，prefill 时相邻 G 个 Query 共享一次块选择（QShare），索引打分和 top-k 的成本被摊薄，选中块的 K/V 也被更多 Query 行复用，提高 GPU 利用率——代价是组内 Query 各自最想要的块取了并集的近似。第三，选中的是「物理页 ID」，注意力内核原地读原始 K/V，不需要 gather 缓冲。效果分两层报：单层 Attention 核心在 1M Token 处 prefill 提速 11.7 倍、decode 提速 13 倍；算上索引打分、选择和所有实测 GPU 开销后是 8.6 倍和 3.0 倍——名义少做的点积和真实省下的时间是两本账，这篇论文把两本都摊开给你看。端到端上，4 张 B300 服务 1M Token 请求（32 并发、每条 4K 输出）总吞吐是稠密的 2.29 倍。

精度账本同样有边界意识。RULER 在 128K 到 1M 全程与稠密差距 2.05 分以内（1M 处差距反而更小）；MRCR、LongBench v2 在 4096 块预算下 aggregate 差距 1.5 分以内；但 GraphWalks（多跳图遍历）对预算敏感，2048 块时掉 3.59 分，加倍预算缩到 1.49 分。还有两个容易被忽略的坑：省下的是「缓存读取」，不是「缓存容量」——全量历史仍在显存里，想省容量还得配合驱逐或卸载；稀疏化会改变生成行为，某些评测上输出 Token 数最多多出 78% 到 128%（更长的推理链甚至重复生成耗尽输出预算），论文因此专门定义了「按输出长度折算的吞吐代理指标」——变快和变省之间还隔着一条生成行为改变的暗流。

把这一节和上一节合起来看，超长上下文的推理优化现在是一条完整的决策链：上下文在十万以内，FlashAttention 加 KV Cache 管理仍是主力；到百万级，先用层级稀疏注意力（LSA/ZHA，需要训练或蒸馏）或免训练改造（CISA，NVIDIA 模型家族实测）把「要读的历史」与总长解耦；显存仍然吃紧时，再让「对的层」（0.4–0.75 深度，用校准提示词选出）来决定「删哪些缓存」。读、删、判三件事各有专门的技术，也各有自己的边界条件。

## 线上变慢怎样定位

先固定可复现负载，分别测 Prefill、Decode、首 Token、单请求和总吞吐，再观察：

1. GPU 利用率、Tensor Core 利用率和内核时间；
2. HBM 使用量、带宽、KV Cache 命中与碎片；
3. Batch 大小、排队、动态批处理和请求长度分布；
4. 多卡链路带宽、Collective 时间与拓扑；
5. CPU Tokenization、采样、网络与日志是否占关键路径；
6. 最近模型、精度、内核、驱动或调度配置变化。

只看到“GPU 100%”不能判断是高效计算还是等待内存；只看到显存满也不能证明容量就是延迟根因。需要 profiler、服务指标和受控 A/B 实验一起定位。

## 回答十一个真实追问

**Prefill 与 Decode 为什么瓶颈不同？** Prefill 能在大量 Token 间复用权重，Decode 每步常要重新读取大量权重和缓存，算术强度不同。

**无限 VRAM 能高效跑超大模型吗？** 只能解决容量；计算吞吐、带宽、互联和软件利用率仍会限制速度。

**多 GPU 为什么不直接翻倍？** 切分增加通信、同步、流水线气泡和调度开销，有时多卡只让模型放得下。

**Tokens/s 怎样测？** 分开输入处理、首 Token、逐 Token 延迟、单请求速度和服务器总吞吐，并写清负载条件。

**KV Cache 如何估算？** 按层数、K/V、KV Head、Head Dimension、Token、精度和 Batch 相乘，再给运行开销留余量。

**HBM、SRAM、Tensor Core、Warp 是什么关系？** 它们分别属于外部显存、片上存储、矩阵计算单元和线程执行组织，共同决定数据能否高效喂给计算。

**FlashAttention 省 FLOPs 还是读写？** 核心优势是分块和融合减少 HBM 中间读写，而非取消精确 Attention 的主要乘加。

**百万级上下文为什么离不开稀疏注意力？** 全注意力的打分量随长度平方增长，常数优化改变不了渐近线；稀疏/层级索引把每步要打分的 Key 数量与总长解耦，才可能把上下文推到百万甚至千万级。

**KV Cache 装不下要删一些历史时，该由哪一层决定删什么？** 让所有层共用一个校准选出的中深层（0.4–0.75 深度）打分最稳；浅层还没完成「用问题找答案」，判别力最差，最后一层已转入输出阶段。逐层默认在大模型上尚可，但共享缓存架构的写入层往往偏浅，是实测掉分的重灾区。

**不重新训练能把稠密注意力模型改造成稀疏的吗？** 可以。CISA 把历史按块建索引、索引器直接从现成 Query 头里按 KL 匹配挑选初始化，零训练改造；RULER 全程与稠密差距 2 分内，1M 上下文端到端吞吐约 2.3 倍。注意它省的是缓存读取而非容量，且输出长度可能变长。

**线上突然变慢先查什么？** 拆阶段与指标，再用 profiler 区分计算、带宽、缓存、Batch、通信和调度。
