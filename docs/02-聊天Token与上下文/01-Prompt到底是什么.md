# Prompt 到底是什么？

> 课程导航：[上一篇：参数到底是什么](../03-模型原理与训练/06-参数到底是什么.md) · 第 7 / 28 篇 · [下一篇：Token 到底是什么](./04-Token到底是什么.md)

原始聊天把“提示词工程”列成了下一步要学的问题：怎样和模型说话效果更好，结构化提示是什么，为什么给几个示例会有帮助。网上常见的回答会立刻给出“角色、任务、格式、约束”四格公式，但零基础读者更需要先看懂：Prompt 究竟进入了哪里，它能改变什么，又为什么不是一条百试百灵的咒语。

## 从一次失败的“帮我总结”开始

你把一段两小时的会议记录贴给模型，只写：

> 帮我总结一下。

模型返回了一段通顺的内容，却没有列出谁负责什么，也没指出会议中尚未决定的事项。它未必“没有听懂中文”，更可能是输入里没有说明你拿这份总结做什么。摘要可以是三句话概览、管理层结论、待办清单，也可以是逐议题纪要；“总结”本身不能唯一确定你要哪一种。

把请求改成这样：

> 阅读 `<会议记录>` 中的内容，输出“已决定事项”和“待办”两部分。每项待办写负责人和截止时间；原文没有写就标“待确认”，不要自行补全。全文不超过 500 字。

这一次，模型得到了任务对象、输出用途、字段、缺失信息处理方式和长度边界。更好的结果不是因为尖括号有魔法，而是歧义少了，输出是否合格也更容易检查。

Prompt（提示）就是在模型运行时提供、用来影响当前输出的输入内容。它可以是一句问题，也可以包含任务、材料、背景、示例、约束与输出要求。日常聊天里，“我发给 AI 的这句话”通常就是用户 Prompt；在完整系统中，模型收到的内容往往不只这一条。

## 你写的 Prompt 只是完整输入的一部分

一个聊天产品可能在后台把几类内容一起交给模型：产品或系统规则、开发者为应用设置的说明、选中的历史消息、工具返回结果、检索资料，以及用户刚刚发来的请求。不同产品和 API 使用的角色名称、优先级与拼接方式会变化，不能把某一家当前的消息格式当成 Prompt 的永久定义。

这张图想帮你看懂用户 Prompt 与[上下文](./07-上下文和上下文窗口是什么.md)的关系。

```text
系统与应用说明
      +
被选中的历史、资料和工具结果
      +
用户 Prompt
      ↓
模型本次实际接收的 Context
      ↓
模型生成输出
```

读图时最重要的是加号。用户 Prompt 属于 Context，但 Context 不等于用户 Prompt。你明明没有写“回答要安全、不要泄露密钥”，产品仍可能把这类规则放在更高优先级；你也可能在界面上看见很长的聊天记录，但产品只选择其中一部分放入本次输入。

Prompt 也不等于[训练](../03-模型原理与训练/18-训练和推理有什么区别.md)。训练通过大量样本更新模型参数，影响以后许多请求；Prompt 在普通推理中提供这一次计算的条件，通常不会改写参数。模型在当前对话里按照示例改变输出方式，属于利用上下文，不代表它已经永久学会。

## 换一种说法，为什么答案会变

[大语言模型](../01-AI与大模型/04-什么是大语言模型.md)会根据当前已有内容，计算后续 [Token](./04-Token到底是什么.md) 的概率。Prompt 改变了已有内容，也就改变了后续生成所依据的条件。

“介绍一下苹果”可能指水果，也可能指公司；“给小学生介绍苹果这种水果，要包括味道、常见品种和过敏提醒”把目标对象和读者范围限定得更清楚。模型不是先独立得出一个固定答案，再给不同问法换包装；输入变化会从生成第一步开始影响后续选择。

即使文字完全相同，两次回答也可能不同。生成过程可能包含随机采样，服务配置、模型版本和产品上下文也可能变化。因此，好的 Prompt 追求的是提高任务成功率和可验证性，不是保证每次逐字相同。

## 写之前先问：这次输出拿来做什么

复杂 Prompt 不必套固定模板，但可以沿着五个问题检查。只有当前任务真正需要时才补充，不要为了“专业”把简单请求写成合同。

1. **结果**：完成后要得到什么，供谁使用？
2. **材料**：模型必须依据哪些内容，哪些内容只是背景？
3. **边界**：哪些事情不要做，缺失信息怎样处理？
4. **形式**：输出要有哪些字段、顺序、长度或数据格式？
5. **验收**：怎样判断结果可用，是否需要来源、测试或人工复核？

例如，请模型修改代码时，“修一下登录问题”没有说明现象、期望行为和验证方式；补上错误信息、复现步骤、相关文件范围与必须通过的测试，通常比添加“你是世界顶级工程师”更有帮助。角色描述只有在它能带来具体视角或约束时才有价值，例如要求以无障碍审查者视角检查页面，并明确依据哪套标准。

材料边界尤其重要。把待处理文本放在清晰分隔符或代码块中，并说明“只总结分隔符内的会议记录”，可以减少模型把说明文字和原文混在一起。分隔符本身仍不是安全边界；如果材料来自不可信网页或文件，其中可能包含试图改变任务的指令，应用还需要权限、内容隔离和 Prompt Injection 防护。

## 示例为什么常常有效

只写规则时，人和模型都可能对“简洁”“正式”“结构化”有不同理解。给出一两个输入—输出示例，可以直接展示分类标签、语气、字段和边界，这种在 Prompt 中提供少量示范的方式常被称为少样本提示（Few-shot Prompting）。不给示例、只描述任务，则常称为零样本提示（Zero-shot Prompting）。

假设要把客户反馈分成“功能问题、故障、咨询”三类。规则写得再长，也可能卡在“希望增加深色模式”算功能问题还是咨询。加入两个边界示例，再说明不确定时输出“需人工判断”，模型更容易延续你真正需要的分类方式。

示例不是越多越好。它们会占用上下文窗口，也可能互相冲突或把偶然错误教给当前回答。优先选择能说明边界的少量代表样本，并让示例格式与真正输入一致；如果任务可以用程序规则稳定完成，就不必全部交给自由生成。

## Prompt 不具备程序的强制性

自然语言允许省略、歧义和冲突，模型又是根据概率生成内容，所以 Prompt 更像对一次计算的条件和要求，而不是传统程序中必然执行的指令。写“绝对不要出错”不会自动增加事实来源，写“请访问数据库”也不会凭空赋予网络、账号或工具权限。

当任务要求机器可验证的格式时，除了在 Prompt 中说明 JSON 字段，还应使用 API 的结构化输出能力、Schema 校验或程序重试。要执行搜索、发邮件或修改文件，还需要真正的[工具](../06-工具与Function-Calling/02-AI工具到底是什么.md)及其权限控制。Prompt 可以表达“想做什么”，外部系统负责判断“能不能做、怎样安全执行”。

高风险任务更不能只优化措辞。医疗建议要有合适专业人员与证据，法律条文要回到权威原文，代码修改要运行测试，数据提取要用样本和校验规则评估。模型回复“明白”只是一段输出，不是验收结果。

## 把 Prompt 当成需要测试的接口

写完 Prompt 后，不要只挑一个顺利样本看。准备几类代表输入：正常情况、缺失字段、边界情况、很长材料和容易误解的反例。检查模型是否遵守范围、是否承认信息缺失、输出结构是否稳定，以及失败时能否被发现。

如果表现不好，先定位是哪一类问题：任务本身没说清，所需资料没有提供，要求互相冲突，输出无法验证，还是模型根本没有相应能力或工具。对应修复比不断堆“认真思考”“非常重要”更有效。

Prompt 的改进也要绑定具体模型和场景。某个版本、某类任务上有效的写法，不一定对另一模型同样有效；模型或产品升级后，关键流程应重新评估。所谓 Prompt Engineering，与其说是背模板，不如说是设计输入、管理上下文、建立评价样本并持续迭代。

## 回答原始聊天里的三个问题

**怎样和模型说话效果更好？** 先说明这次输出的用途，再提供必要材料、边界、期望形式和验收方式。简单任务保持简单；复杂任务消除真正影响结果的歧义。

**结构化提示是什么？** 它是把任务说明、材料和输出要求分区组织，让人和模型更容易识别各部分职责。编号、标题、分隔符和明确字段都可以帮助结构化，但没有某种必须使用的符号。

**Few-shot 示例为什么有用？** 示例把抽象要求变成当前上下文里的具体模式，尤其适合展示标签、格式和边界。它影响本次输出，不等于重新训练参数，也不能替代测试。
