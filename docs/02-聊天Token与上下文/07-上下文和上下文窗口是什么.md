# 上下文和上下文窗口是什么？

这个问题很直接：“上下文窗口是啥意思？”常见回答会把它比作短期记忆，但这个类比很容易继续制造误解：聊天列表里保存了消息，是否就代表模型一直记得？窗口足够大，是否就能可靠使用里面每一句话？缓存、Memory 和 RAG 又分别放在哪里？

另一个紧接着的问题是：上下文窗口明明装着历史消息，为什么 LLM API 仍会被称为无状态？下面从一次真实请求的组装过程开始，逐层拆开“保存过”“本次带上了”和“模型有效使用了”这三件不同的事。

## Context 是这一次实际交给模型的信息

假设你先说“项目代号是北斗”，十轮之后问“项目代号是什么”。模型要答出“北斗”，这条旧消息必须以某种形式进入当前计算：可能是原始历史消息，可能被写进摘要，也可能由 Memory 系统检索后重新加入。

模型不会因为那句话曾经出现在屏幕上，就天然从某个永久记忆中读到它。聊天界面、服务端数据库和模型本次输入是不同层。

```text
产品保存的聊天记录
        ↓ 选择、截断、摘要或检索
系统说明 + 选中的历史 + 当前问题 + 附加资料 + 工具结果
        ↓ 编码为 Token
模型本次实际接收的 Context
        ↓
生成当前回答
```

这张图想帮你看懂 Context 的边界：它不是“所有可能相关的信息”，而是经过应用选择后，**这一次实际可供模型计算的信息**。读图时最重要的是第一根箭头，保存下来的内容只有被重新选入，才会进入本次 Context。

Context 常译为上下文。对大语言模型来说，它可以包含系统与应用说明、用户 [Prompt](./01-Prompt到底是什么.md)、历史对话、检索资料、工具输出和模型刚刚生成的 Token。不同模型和服务会用不同格式编码这些内容，但它们最后都要以模型能处理的序列进入计算。

## Context Window 是容量边界，不是里面的内容

上下文窗口（Context Window）规定一次模型计算能够处理多长的 Token 序列。Context 是实际放进去的材料，Context Window 是容量上限；就像当前桌面上的文件与桌面可用面积不是同一个概念。

窗口通常以 [Token](./04-Token到底是什么.md) 计量，因为模型处理的是 Token 序列。具体服务怎样计算输入、预留输出、系统消息和工具结果，要看对应模型与 API 文档。不能把某个平台“输入加最大输出”的规则当作所有系统的永久定义。

“上下文窗口是 128K”这类说法只告诉你容量数量级，还没有告诉你产品实际放了什么，也没有保证所有位置都被同样好地利用。两次请求使用同一个模型，实际 Context 可以完全不同；同一段聊天在不同产品里，也可能因为历史选择和摘要策略不同而产生不同输入。

短期工作台是一个有用类比：参数像训练后长期固定的内部计算关系，Context 像这次摊在桌上的材料，窗口像桌面容量。但类比到这里就该停。模型没有像人一样主动感知“这件事很重要，应该长期记住”；材料能否留下由产品逻辑决定，能否被正确利用还取决于模型能力和任务设计。

## 一次长对话并不是无限向后追加

随着对话增长，系统说明、历史消息、当前问题和计划输出会争用有限窗口。超过服务允许的长度时，应用必须处理，而不是让模型凭空看见超出边界的部分。

常见策略包括删除较早或较不相关的消息、把历史压缩成摘要、分块处理长文档、只检索与当前问题相关的片段，或改用支持更长窗口的模型。每种策略都会做取舍：

- 直接截断简单，但可能删掉最早提出的重要约束；
- 摘要节省空间，却可能丢失细节或把误解继续带下去；
- 分块适合局部处理，却需要额外步骤汇总跨块关系；
- 检索可以挑相关片段，但检索错了，模型就拿不到正确证据；
- 更长窗口保留更多原文，也会带来更多计算、延迟和信息筛选压力。

所以“超出窗口就一定删除最早消息”不是定义，只是一种实现。产品也可能保留开头的系统规则、最近若干轮和一份中间摘要；用户通常看不到完整组装过程，排查问题时应查看产品或 API 是否提供输入记录、Token 用量或调试信息。

输出也要占 Token 预算。部分模型把输入和输出放在同一个总窗口内，同时再规定单独的最大输出长度；也有服务用不同字段和计费规则表达这些限制。输入已经占满时，请求可能被拒绝、历史被产品裁剪，或留给输出的空间很少；生成达到输出上限、结束 Token 或其他停止条件时会停止，常见表现是回答被截在中途。具体行为必须查看所用模型与 API 文档。

这就是为什么“上下文窗口 128K”和“最多输出 16K”不能互相替换。前者描述一次计算的总序列容量口径，后者限制新生成部分；某个服务允许的输入上限还可能为了预留输出而更小。

## 放进窗口，也不等于被可靠记住

容量问题解决的是“能不能送进模型”，利用问题回答“模型能不能在正确时候找到并使用”。两者不能画等号。

“Lost in the Middle”研究测试了模型从长输入中取回相关信息的表现，发现信息位置会影响结果，一些模型更容易使用开头或结尾，而对中间内容表现较差。具体能力会随模型和训练变化，但结论提醒我们：窗口长度是最大可处理长度，不是每个 Token 都能得到同样可靠注意的质量承诺。

材料越多还可能引入相似但无关的段落、相互冲突的指令和过时信息。让模型“把整家公司资料都读一遍”不一定比只提供几段高相关证据更好。设计 Context 时要考虑相关性、来源、时间和冲突处理，而不只是想办法塞满。

对于需要精确引用的任务，可以让应用先检索候选段落，再要求回答附带可检查的出处；对于跨整份文档的统计或一致性检查，则可能需要分块、程序计算和汇总验证。长窗口扩大了可选方案，不会自动替代任务分解与核验。

标称长度和有效长度因此是两件事。有效上下文不能只用一个“真正是多少 K”的数字概括：在中间找一句话、跨很远合并两条证据、遵守早期约束和总结整份文档，是不同任务。评测应改变信息位置、距离、干扰项和问题类型，观察正确率怎样随长度变化；只做一次“针藏在干草堆”测试，也不能代表全部长上下文能力。

## 有历史消息，为什么还会说“无状态”

“无状态”通常是在描述某一层请求：一个原始模型调用不会自动记住上一次调用的输入和输出。应用若想延续对话，需要在新请求里再次提供相关历史，或使用服务端提供的会话/响应存储功能，让服务替应用关联状态。

```text
请求 1：发送“代号是北斗” → 得到回答

请求 2A：只发送“代号是什么”
       → 原始无状态调用没有足够信息

请求 2B：发送历史 + “代号是什么”
       → 历史成为本次 Context
```

这张图想区分“跨请求保存”与“本次输入携带”。读图时注意 2B 并没有让模型参数保存第一轮，只是应用把信息重新交给了模型。

一些现代 API 或 Agent 平台可以在服务端保存对话对象、响应链或线程，因此从开发者体验看是“有状态”的。底层模型在每次生成时仍依赖当次构造出的 Context。讨论系统是否有状态时，必须说明是在谈模型计算、单个 API 端点、服务端会话，还是完整聊天产品。

这也回答了上面的表面矛盾：窗口可以承载过去消息，但它不会自己从历史数据库里取消息。负责保存和重新放入的是应用或服务；模型只处理当前交给它的序列。

## 参数、聊天记录、Memory、RAG 和缓存分别做什么

这些词都像是在说“模型知道的信息”，实际生命周期完全不同。

**参数**来自训练，是模型内部长期使用的数值关系。把一句新资料放进 Context，通常不会改写[参数](../03-模型原理与训练/06-参数到底是什么.md)；普通聊天也不会在每轮结束后重新训练模型。

**聊天记录**是产品保存的消息日志。它可以完整存在数据库中，却因为窗口预算、隐私设置或产品策略没有进入当前请求。聊天记录是候选材料，不等于实际 Context。

**Memory**通常是应用跨请求或跨会话保存的用户偏好、事实、摘要或事件。系统要先判断何时写入、怎样检索，再把相关内容放入当前 Context。Memory 的价值来自保存与取回流程，不是另一个无限窗口。

**RAG**（检索增强生成）是先从外部资料中检索，再把相关片段加入 Context 的流程。知识库可以远大于窗口，模型每次只看到被检索和选中的部分；检索遗漏或文档过时都会影响答案。

**缓存**保存可复用的计算结果，用来减少重复工作。生成时常见的 KV Cache 会保留先前 Token 在注意力计算中的中间状态，让新 Token 不必从头重算全部前缀。缓存提高效率，但它不是语义记忆，通常也不会让模型突破逻辑上的上下文长度限制。

在因果生成里，新的 Token 会产生自己的 Query，并用它去读取所有可见历史位置的 Key 和 Value。历史 Token 的 Key、Value 会被后续每一步反复使用，所以值得缓存；历史 Query 只服务于当时那个位置的输出，未来 Token 会生成新的 Query，通常没有再次读取旧 Query 的需要。这是“缓存 K/V 而不缓存 Q”的核心原因。不同注意力变体和推理引擎会改变缓存布局，但不会把 KV Cache 变成长期记忆。

可以把关系串成一句话：参数决定模型怎样计算，聊天记录与 Memory 保存候选信息，RAG 负责从外部资料挑选，Context 是最终送进本次计算的材料，Context Window 限制材料长度，缓存则尽量减少这次计算中的重复工作。

## 窗口越大，成本一定按平方增长吗

原始 Transformer 的全注意力会比较序列中许多位置，朴素计算和内存需求会随长度快速增长；这也是长序列昂贵的重要原因。但现代系统会使用优化注意力实现、稀疏或局部机制、缓存、并行和专门硬件，不同训练与推理阶段的瓶颈也不同。

因此，可以安全地说“更长 Context 通常消耗更多计算、内存或延迟预算”，却不应对所有模型宣布一个永久统一的平方公式。API 价格还会受模型、输入/输出区分、缓存折扣和服务策略影响，必须按日期查看官方文档。

更长窗口也会改变产品工程：需要决定哪些历史值得保留，怎样防止不可信资料中的指令干扰任务，如何在回答里标明来源，以及怎样评估模型有没有漏掉中间信息。窗口是资源，Context Engineering 才是使用这项资源的方法。

## Context Length 为什么不能随手改大

可处理长度同时受位置表示、注意力与遮罩实现、训练时见过的长度、KV Cache 容量、推理引擎和服务配置约束。修改配置文件里的一个数字，只是让程序尝试接受更长输入；位置方法可能没有合适外推，模型也可能从未学会在那个距离上稳定使用信息，内存还可能先耗尽。

一些模型通过位置缩放、继续训练或专门长上下文数据扩展窗口，这仍需要质量评测。服务端公布的上限还可能低于架构理论值，因为提供方要控制延迟、并发与显存。讨论某个模型“支持多长”时，应同时给出模型版本、推理实现和核验日期。

## 回答开头的四个问题

**上下文是什么？** 是模型在当前这次计算中实际可以利用的信息，包括被选中的指令、消息、资料、工具结果和已经生成的 Token。

**上下文窗口是什么？** 是一次能够处理的 Token 容量边界。它限制 Context 能有多长，不代表里面每一项都会被同样可靠地使用。

**聊天列表里有消息，模型就记得吗？** 不一定。产品保存消息后，还要在新请求中重新选择、摘要或检索，相关内容进入本次 Context 才能直接影响回答。

**有历史消息，API 为什么仍可能叫无状态？** 因为“历史被应用重新发送”与“模型调用自动保存历史”是两回事。有些接口无状态，有些服务提供状态管理；无论哪种，模型生成时都依据本次构造出的 Context。

**输出 Token 达到限制会怎样？** 生成会在最大输出、结束 Token 或其他停止条件处终止，可能出现未写完的句子。输入、系统说明、工具结果和输出怎样共享总窗口，取决于具体模型与服务。

**标称 128K 就代表能可靠使用 128K 每个位置吗？** 不代表。上限说明可接受容量，有效利用要按任务、位置、距离和干扰分别评测。

**KV Cache 为什么通常只缓存 K 和 V？** 新 Token 的 Query 只用于当前一步读取历史 K/V；未来步骤会产生自己的 Query。历史 K/V 会被反复读取，旧 Query 通常不会。
