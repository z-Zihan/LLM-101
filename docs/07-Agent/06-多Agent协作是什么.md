# 多 Agent 协作是什么？

> 所属专题：[Agent](./01-Agent到底是什么.md) · [规划与恢复](./04-Agent如何规划和恢复.md) · [上下文工程](../11-Coding-Agent/09-上下文工程是什么.md)
>
> 这是一篇高级系统扩展页，不改变 32 篇主路线顺序。

多 Agent 系统让多个拥有独立角色、上下文或工具权限的 Agent 围绕同一目标协作。拆分不会凭空增加模型智力；它改变的是搜索宽度、职责边界、上下文隔离和并行方式，同时增加通信、仲裁和调试成本。

## 一个超级 Agent，还是多个专门 Agent

单 Agent 共享完整状态，协调简单，适合任务耦合强、步骤依赖多或规模不大。专门 Agent 可以只加载领域工具与材料，减少无关上下文，并让独立子任务并行。

决定拆分前先问：

- 子任务能否用清晰输入输出契约隔开；
- 是否真的可并行，还是后一步必须等前一步；
- 不同部分是否需要不同权限、模型或工具；
- 合并结果的规则是否明确；
- 新增通信成本是否低于上下文和专业化收益。

Router 负责把任务送到合适角色，Handoff 把控制权和必要状态交给下一角色，共享状态则保存所有人都要遵守的目标、约束与进度。三者若没有明确契约，会把一个 Agent 的内部混乱变成跨 Agent 混乱。

## 多 Agent 为什么可能更贵却不更好

每个 Agent 都需要 Prompt、上下文和模型调用；讨论、复核和仲裁还会重复读取材料。延迟可能由最慢分支决定，错误也会在摘要和交接中传播。

值得使用的场景通常具有可测结构：独立检索源并行、不同专长产生候选、一个执行一个验证，或权限必须隔离。若只是让三个同模型 Agent 互相赞同，Token 增加不代表证据增加。

比较时应与强单 Agent、固定 Workflow 和简单并行采样做基线。报告同等预算下的成功率、尾延迟、成本与错误类型，不能只展示一次精彩对话。

## 多个小模型会超过一个大模型吗

多个小模型通过搜索不同方案、投票或专门分工，可能在某些任务上超过单次大模型调用。提升来自额外计算和聚合结构，不表示每个小模型的基础能力变强。

若所有小模型共享同一盲点，投票会稳定地产生同一错误；弱模型也可能无法评价彼此。与其问“几个小模型等于一个大模型”，不如在固定总 Token、延迟和费用下比较：

- 单个大模型一次或多次采样；
- 多个小模型独立候选加可靠验证器；
- 大模型规划、小模型执行；
- 固定算法搜索而非自由对话。

## 长任务最难的是状态一致性

每个 Agent 有自己的上下文时，容易重复搜索、使用过期结论或修改同一资源。共享全部对话又会迅速膨胀窗口，并泄露不必要权限。

可靠协作需要外部任务图和结构化状态：

```text
共同目标与验收
  ├─ 子任务、负责人、依赖、状态
  ├─ 产物位置与版本
  ├─ 已验证事实和来源
  ├─ 未决问题与风险
  └─ 资源锁、权限与取消信号
```

Agent 完成时应提交产物与证据，而不是只发“已完成”。协调器用版本、测试或规则检查，再解锁依赖。共享状态是权威记录，对话摘要只是上下文材料。

## 并行、串行和仲裁怎样选

互不修改同一状态、输入已齐全的子任务适合并行，例如分别查三份独立资料。后一项依赖前一项输出，或多个动作会竞争同一资源时，应串行或加锁。

扇出后汇总需要明确聚合器。事实冲突不能靠多数投票自动解决，应回到来源和可重复测试；设计方案冲突可以按预先定义的需求、成本和风险评分；高风险决策则交给责任人。

子 Agent 不应默认继承父 Agent 的全部上下文。传递任务目标、输入、必要约束、产物格式和验证标准即可；需要历史时提供可定位来源。过少会丢背景，过多会增加成本并混入无关或敏感信息。

## 权限与失败会跨 Agent 传播

父 Agent 有发布权限，不表示所有子 Agent 都应继承。使用最小权限、能力令牌和作用域明确的工具，把高风险动作集中到受控执行者。

一个子 Agent 超时后，协调器要取消依赖任务或选择替代路径；父任务取消应向下传播。重试要避免重复副作用，失败状态不能被另一个 Agent 的乐观摘要覆盖。

观测系统要能串起父任务、子任务、工具调用、成本和产物版本，否则生产问题只会留下很多彼此矛盾的聊天记录。

## 共享状态人人都在写，为什么还是对不齐

上一节把「维护一份权威共享状态」当成了长任务协调的答案，写法也给了：JSON、版本、锁、取消信号。这个答案在 2026 年被一批实证工作补上了后半句——「有共享状态」和「状态对齐」是两件事，坑不在格式里，在时序和信任边界上。

先看规模。AgenticFlict（arXiv:2604.03551）从 GitHub 抓了 14.2 万个由 AI Coding Agent 发起的 PR，做完确定性合并模拟后数出一个数字：27.67% 的 Agent PR 存在文本合并冲突。两个 Agent 改同一个仓库，四分之一强的情况会撞车——这还只是能被 `git merge` 发现的文本冲突；行级合并能通过、语义上已经互相破坏的改动，根本不在这个统计里。

比撞车更隐蔽的是视图不一致。STORM（arXiv:2605.20563）把主流做法——每个 Agent 一个 git worktree、各改各的、最后合并——称为「工作区隔离」，并指出它的问题是把冲突解决整体推迟到合并那一刻，那时错误已经发生，恢复最贵。STORM 的替代思路是让所有 Agent 的读写经过同一个状态中介，写时立即检测冲突。在 Commit0 基准上，这套写时管理比 worktree 基线高 18.7 分。这个对比值得每个想开多 Agent 的人记住：隔离解决的是「互不踩脚」，解决不了「各自看到的版本不一样」——三个 Agent 基于三个不同时刻的仓库状态做决策，合并器拿到的本来就是三份对不上的计划。

时序问题再往前走一步，就是并发本身。CoAgent（arXiv:2606.15376）指出经典并发控制搬过来会水土不服：一次 Agent「事务」包含几分钟的推理，锁会把其他 Agent 卡死整个推理区间；乐观并发控制（OCC）遇到冲突就回滚重试，扔掉的却是几分钟的推理成本。它的协议反着来——写入先落、运行时发现某个读依赖的值被改了，不回滚，而是通知那个 Agent「你依赖的前提变了」，让模型自己判断计划还成不成立、只修补受影响的步骤。这等于承认了一个此前没人明说的假设：LLM Agent 拥有传统事务系统没有的能力，能理解冲突的含义并定向修复。十个竞争负载上，它在串行正确率 5% 以内做到 1.4 倍加速，而教科书式的锁和 OCC 几乎拿不到并行收益。

最后一条缝隙在交接处。Requirement Integrity（arXiv:2611.07483，2026-11）测的是一个所有多 Agent 系统都在做、却很少有人验证过的动作：编排器把需求拆给子 Agent，子 Agent 的结果合并回来——每经一次手，需求都可能被摘要掉、改写掉、或者静默忽略掉。实验用可精确计分的合成任务对比三种交接载体：自由文本、结构化 JSON、以及带 HMAC-SHA256 签名的需求清单（每条需求是逐字引用加可校验谓词，合并决策由确定性代码核对）。三个数字连起来读：被攻击时，自由文本交接的 69.4% 运行提交了不安全改动，签名清单降到 9.0%；同样这批轨迹，确定性校验器抓住 78.7% 的违规决策（误报 7%），换 LLM 裁判是 59.0%（误报 50%）；但一个预先污染清单的注入攻击，能让签名清单的违规率从 14.6% 拉回 37.5%（GPT-5.6-luna 上到 75.0%）——签名照常通过，因为签的是已经被污染的内容。结论浓缩成一句话：签名保护运输途中的需求，不保护提取需求的瞬间；提取发生在签名之前，它才是真正的信任边界。

把四条拼起来，这一节给「维护共享状态」补上四道具体检查：合并成功率之外，统计语义冲突率（文本能合、行为已坏的比例）；多 Agent 并行写同一资源时，确认每个 Agent 读到的是最新已提交版本，而不是它启动时的快照；高冲突工作负载下，评估「通知受影响 Agent 定向修复」是否比「回滚重跑」便宜；需求跨 Agent 传递时，用结构化清单加确定性核对，LLM 裁判只能当补充。共同教训依旧：共享状态是权威记录——前提是它的读、写、传三个环节各自有人守。

## 回答七个真实追问

**超级 Agent 还是多个专门 Agent？** 当子任务、权限或上下文能清晰隔离时拆分才有价值；耦合强时单 Agent 更简单。

**生产多 Agent 是提升还是炒作？** 两者都可能。必须与同预算单 Agent 和固定 Workflow 比较成功率、成本、延迟与可调试性。

**多个小 Agent 能超过大模型吗？** 在搜索、投票或分工任务上可能，但收益来自额外计算与聚合，不是自动的群体智慧。

**长任务协调最难什么？** 维护权威共享状态、依赖、版本、产物和取消，避免上下文各自漂移。

**共享文件已经写好了，为什么各 Agent 还是各干各的？** 因为「有共享状态」不等于「状态对齐」：Agent 可能在启动时读过一份快照后再没刷新，交接摘要可能悄悄丢掉一条需求，两个 Agent 的改动可能文本上能合并、语义上已经冲突。逐项检查读、写、传三个环节，参考本篇「共享状态」一节。

**需求传给子 Agent 又合并回来，怎么保证没有被改掉？** 用结构化需求清单加确定性核对，别指望 LLM 裁判——它在同等轨迹上的误报率是确定性校验器的七倍。签名能防运输途中的篡改，防不了提取阶段的污染：清单生成那一刻才是信任边界，先审提取，再谈签名。

**如何决定并行、串行和冲突仲裁？** 看数据依赖与副作用；事实冲突回到证据，方案冲突按预设标准或人工责任处理。
