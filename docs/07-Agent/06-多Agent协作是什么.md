# 多 Agent 协作是什么？

> 所属专题：[Agent](./01-Agent到底是什么.md) · [规划与恢复](./04-Agent如何规划和恢复.md) · [上下文工程](../11-Coding-Agent/09-上下文工程是什么.md)
>
> 这是一篇高级系统扩展页，不改变 32 篇主路线顺序。

多 Agent 系统让多个拥有独立角色、上下文或工具权限的 Agent 围绕同一目标协作。拆分不会凭空增加模型智力；它改变的是搜索宽度、职责边界、上下文隔离和并行方式，同时增加通信、仲裁和调试成本。

## 一个超级 Agent，还是多个专门 Agent

单 Agent 共享完整状态，协调简单，适合任务耦合强、步骤依赖多或规模不大。专门 Agent 可以只加载领域工具与材料，减少无关上下文，并让独立子任务并行。

决定拆分前先问：

- 子任务能否用清晰输入输出契约隔开；
- 是否真的可并行，还是后一步必须等前一步；
- 不同部分是否需要不同权限、模型或工具；
- 合并结果的规则是否明确；
- 新增通信成本是否低于上下文和专业化收益。

Router 负责把任务送到合适角色，Handoff 把控制权和必要状态交给下一角色，共享状态则保存所有人都要遵守的目标、约束与进度。三者若没有明确契约，会把一个 Agent 的内部混乱变成跨 Agent 混乱。

## 多 Agent 为什么可能更贵却不更好

每个 Agent 都需要 Prompt、上下文和模型调用；讨论、复核和仲裁还会重复读取材料。延迟可能由最慢分支决定，错误也会在摘要和交接中传播。

值得使用的场景通常具有可测结构：独立检索源并行、不同专长产生候选、一个执行一个验证，或权限必须隔离。若只是让三个同模型 Agent 互相赞同，Token 增加不代表证据增加。

比较时应与强单 Agent、固定 Workflow 和简单并行采样做基线。报告同等预算下的成功率、尾延迟、成本与错误类型，不能只展示一次精彩对话。

## 多个小模型会超过一个大模型吗

多个小模型通过搜索不同方案、投票或专门分工，可能在某些任务上超过单次大模型调用。提升来自额外计算和聚合结构，不表示每个小模型的基础能力变强。

若所有小模型共享同一盲点，投票会稳定地产生同一错误；弱模型也可能无法评价彼此。与其问“几个小模型等于一个大模型”，不如在固定总 Token、延迟和费用下比较：

- 单个大模型一次或多次采样；
- 多个小模型独立候选加可靠验证器；
- 大模型规划、小模型执行；
- 固定算法搜索而非自由对话。

## 长任务最难的是状态一致性

每个 Agent 有自己的上下文时，容易重复搜索、使用过期结论或修改同一资源。共享全部对话又会迅速膨胀窗口，并泄露不必要权限。

可靠协作需要外部任务图和结构化状态：

```text
共同目标与验收
  ├─ 子任务、负责人、依赖、状态
  ├─ 产物位置与版本
  ├─ 已验证事实和来源
  ├─ 未决问题与风险
  └─ 资源锁、权限与取消信号
```

Agent 完成时应提交产物与证据，而不是只发“已完成”。协调器用版本、测试或规则检查，再解锁依赖。共享状态是权威记录，对话摘要只是上下文材料。

## 同样的预算，多 Agent 到底赢在哪一步

前面说的都是定性判断。2026 年 11 月有一篇系统性的元分析（Sajjadi Mohammadabadi, *More Agents, More Samples, or More Thinking?*），把 9 项实证研究拆开重新对账，提取出 516 个多 Agent 配置与单 Agent 基线的可比对比，专门回答"多出来的钱花在了沟通协调，还是花在了更多采样"。结论对决策很有用，但它最有价值的部分其实是教你怎么比。

**先看结论**：如果对比的对手不是"只跑一次的单 Agent"，而是给了同等预算的单 Agent，多 Agent 的平均优势就消失了——在按采样数或预算对齐的 474 组对比里，74% 的对比中多 Agent 不优于基线，平均准确率差约 −0.04；把同一个对比对象从"单次贪心解码"换成"采样五次取多数"（自一致性），同一篇研究的辩论多 Agent 系统从"领先 0.045"变成"落后 0.031"。也就是说，看起来属于"多 Agent 协作"的收益，大部分其实属于"多花算力"——单 Agent 自己多采样几票，就能拿走大部分。

**元分析用了一个关键工具来拆解这件事**：把对比双方消耗的资源写成六维向量（思考 token、总 token、费用、延迟、采样数、工具脚手架），并把基线分成四档——A 档：单次贪心解码（没对齐任何资源）；B 档：对齐采样数；C 档：对齐某个声明的预算维度（如思考 token）；D 档：扫预算画准确率-成本边界。对账的主要发现都来自 B/C 档：对齐思考 token 后 96 组对比平均差 −0.007，从 500 个思考 token 起单 Agent 就追平或反超辩论；对齐迭代步数后 18 组对比平均 −0.042。而成本审计显示多 Agent 系统的费用中位数是贪心思维链的 8.1 倍（均值 27 倍，最高 225 倍）。

**为什么额外沟通经常帮倒忙**：论文给了两个机制。一是"脚手架挤占"——K 个 Agent 聊 T 轮，角色说明、消息历史这些沟通开销都从同一个 token 预算里扣，真正用于推理的预算随轮数被稀释；二是"冗余信息传不出新东西"——如果每个 Agent 拿到的材料本来就相同（比如同一份提示），那么无论怎么讨论，对话记录里都不会出现共享材料之外的信息，这是信息论意义上的不可能，不是模型不够聪明。多 Agent 真正可能赢的条件因此很明确：各方持有的证据天然不同（比如各自检索到不同来源），且任务需要把分开的证据汇总起来——经典实验里叫"隐藏画像"设定，独立投票无法还原只有合并证据才能支持的那个答案。

**这个结论该怎么用，论文给的三条决策规则可以直接抄**：第一，先把同等推理算力喂给单 Agent（更长思考、多次采样、自一致性），确认单 Agent 路线确实到顶了再考虑拆分；第二，因为任务结构而不是准确率目标上多 Agent——上下文超出单模型窗口、需要并行独立工具、需要隔离的沙箱执行，这三种结构约束才是拆分的正当理由；第三，如果用了多 Agent，必须接外部验证（编译器、单元测试、数据库查询）——模型实例之间的相互赞同不等于正确。论文里最扎眼的对比是：同一个基准上，GPT-5 的多 Agent 对话评分最高 63%，而人写的确定性工具达到 96.5%。

也要诚实地说这项研究的边界：9 项研究里约 35% 的配置（180/516）来自其中一篇，初始五项研究没有按系统化检索流程挑选，部分对比的测试集只有 20 道题；"45% 准确率以下才有多 Agent 收益"这类阈值说法，作者复核后认为现有数据不足以支持，按任务而变才是稳妥结论。方向性结论（对手要对齐预算、沟通不产生信息、要接外部验证）是稳的，具体数字会随后续研究修正。

## 并行、串行和仲裁怎样选

互不修改同一状态、输入已齐全的子任务适合并行，例如分别查三份独立资料。后一项依赖前一项输出，或多个动作会竞争同一资源时，应串行或加锁。

扇出后汇总需要明确聚合器。事实冲突不能靠多数投票自动解决，应回到来源和可重复测试；设计方案冲突可以按预先定义的需求、成本和风险评分；高风险决策则交给责任人。

子 Agent 不应默认继承父 Agent 的全部上下文。传递任务目标、输入、必要约束、产物格式和验证标准即可；需要历史时提供可定位来源。过少会丢背景，过多会增加成本并混入无关或敏感信息。

## 权限与失败会跨 Agent 传播

父 Agent 有发布权限，不表示所有子 Agent 都应继承。使用最小权限、能力令牌和作用域明确的工具，把高风险动作集中到受控执行者。

一个子 Agent 超时后，协调器要取消依赖任务或选择替代路径；父任务取消应向下传播。重试要避免重复副作用，失败状态不能被另一个 Agent 的乐观摘要覆盖。

观测系统要能串起父任务、子任务、工具调用、成本和产物版本，否则生产问题只会留下很多彼此矛盾的聊天记录。

## 共享状态人人都在写，为什么还是对不齐

上一节把「维护一份权威共享状态」当成了长任务协调的答案，写法也给了：JSON、版本、锁、取消信号。这个答案在 2026 年被一批实证工作补上了后半句——「有共享状态」和「状态对齐」是两件事，坑不在格式里，在时序和信任边界上。

先看规模。AgenticFlict（arXiv:2604.03551）从 GitHub 抓了 14.2 万个由 AI Coding Agent 发起的 PR，做完确定性合并模拟后数出一个数字：27.67% 的 Agent PR 存在文本合并冲突。两个 Agent 改同一个仓库，四分之一强的情况会撞车——这还只是能被 `git merge` 发现的文本冲突；行级合并能通过、语义上已经互相破坏的改动，根本不在这个统计里。

比撞车更隐蔽的是视图不一致。STORM（arXiv:2605.20563）把主流做法——每个 Agent 一个 git worktree、各改各的、最后合并——称为「工作区隔离」，并指出它的问题是把冲突解决整体推迟到合并那一刻，那时错误已经发生，恢复最贵。STORM 的替代思路是让所有 Agent 的读写经过同一个状态中介，写时立即检测冲突。在 Commit0 基准上，这套写时管理比 worktree 基线高 18.7 分。这个对比值得每个想开多 Agent 的人记住：隔离解决的是「互不踩脚」，解决不了「各自看到的版本不一样」——三个 Agent 基于三个不同时刻的仓库状态做决策，合并器拿到的本来就是三份对不上的计划。

时序问题再往前走一步，就是并发本身。CoAgent（arXiv:2606.15376）指出经典并发控制搬过来会水土不服：一次 Agent「事务」包含几分钟的推理，锁会把其他 Agent 卡死整个推理区间；乐观并发控制（OCC）遇到冲突就回滚重试，扔掉的却是几分钟的推理成本。它的协议反着来——写入先落、运行时发现某个读依赖的值被改了，不回滚，而是通知那个 Agent「你依赖的前提变了」，让模型自己判断计划还成不成立、只修补受影响的步骤。这等于承认了一个此前没人明说的假设：LLM Agent 拥有传统事务系统没有的能力，能理解冲突的含义并定向修复。十个竞争负载上，它在串行正确率 5% 以内做到 1.4 倍加速，而教科书式的锁和 OCC 几乎拿不到并行收益。

最后一条缝隙在交接处。Requirement Integrity（arXiv:2611.07483，2026-11）测的是一个所有多 Agent 系统都在做、却很少有人验证过的动作：编排器把需求拆给子 Agent，子 Agent 的结果合并回来——每经一次手，需求都可能被摘要掉、改写掉、或者静默忽略掉。实验用可精确计分的合成任务对比三种交接载体：自由文本、结构化 JSON、以及带 HMAC-SHA256 签名的需求清单（每条需求是逐字引用加可校验谓词，合并决策由确定性代码核对）。三个数字连起来读：被攻击时，自由文本交接的 69.4% 运行提交了不安全改动，签名清单降到 9.0%；同样这批轨迹，确定性校验器抓住 78.7% 的违规决策（误报 7%），换 LLM 裁判是 59.0%（误报 50%）；但一个预先污染清单的注入攻击，能让签名清单的违规率从 14.6% 拉回 37.5%（GPT-5.6-luna 上到 75.0%）——签名照常通过，因为签的是已经被污染的内容。结论浓缩成一句话：签名保护运输途中的需求，不保护提取需求的瞬间；提取发生在签名之前，它才是真正的信任边界。

把四条拼起来，这一节给「维护共享状态」补上四道具体检查：合并成功率之外，统计语义冲突率（文本能合、行为已坏的比例）；多 Agent 并行写同一资源时，确认每个 Agent 读到的是最新已提交版本，而不是它启动时的快照；高冲突工作负载下，评估「通知受影响 Agent 定向修复」是否比「回滚重跑」便宜；需求跨 Agent 传递时，用结构化清单加确定性核对，LLM 裁判只能当补充。共同教训依旧：共享状态是权威记录——前提是它的读、写、传三个环节各自有人守。

## 委托一次，安全就落到最弱的那一环

上一节的结论是：需求跨 Agent 交接时会丢内容，提取那一刻才是信任边界。这一节补上更不舒服的一半：交接丢掉的不只是需求条目，还有每个 Agent 与原始证据的接触——而系统的安全水位，恰恰取决于「证据的最弱读者」，不是系统里最强的那个模型。

2026 年 11 月一项被 NeurIPS 2026 Meta-Agents workshop 接收的研究（arXiv:2611.17520）把这个命题做成了可复现的攻击。实验环境刻意简单：磁盘上放一批档案文件，攻击者在里面塞一条伪造记录。伪造并不高明，反而带着两个固定破绽——日期比它声称要「更正」的真记录更早，而且缺了每份真记录都有的入藏号。任务是让 Agent 回答档案库里的双选问题；判定标准叫「有害修订」（harmful revision）：模型单独作答时选对，伪造记录经手之后再答就选了攻击者想要的那个错误答案。

先看强模型直接读档案的表现。Claude Code 里的 Opus 5、Codex 里的 gpt-5.6-sol、参考 harness 里的三个编排器，加起来 1080 次直接试验只出过 2 次有害修订；Opus 5 在 180 次里 180 次亲自指出「这条记录缺入藏号」。这不是一个能骗过前沿模型的攻击——单模型场景下它确实骗不过。

然后打开这些产品默认的子代理机制，让编排器把检索委托给自己生成的更便宜、更弱的子代理。同一批事实，失败率变成：20/180、44/180、75/180、553/900。驾驶舱里坐的还是同一个强模型，系统水位却落到了弱读者附近——比编排器单独的水平高出 10.6 到 24.4 个百分点，离弱模型单独作答的水平（22/180、58/180）只差 1.1 和 7.8 个点。

「是委托本身有害，还是子代理太弱？」论文用两组控制把这个混淆拆开了。第一组，委托到一个干净的档案库（没有伪造记录），有害修订 0/180——委托不产生伤害。第二组，子代理与编排器用同档模型，失败率回到 0/180、1/180、11/540——同档委托几乎无伤。两个控制放在一起，原因指向模型的弱点而非委托动作本身；而且效应随强弱差距单调变化：参考 harness 里八对强弱组合，子代理越弱，系统失败越多。

委托这一跳到底丢掉了什么？Claude Code 会把子代理的对话轮次转发给编排器，研究者得以直接查看编排器实际收到的报告。编排器亲自打开伪造文件时，180/180 会指出溯源缺失；弱子代理的摘要里，这个信号只保留了 96/180（p=10⁻³¹）；摘要里没有信号的场合，编排器 75 次采纳了伪造结论。更扎心的是反过来的数字：即使摘要保住了溯源信号，编排器仍然在 21/96 的场合出了有害修订——同一份记录，它自己读只有 1/180。所以别把责任全推给子代理，编排器拿到摘要之后自己也守不住；传递失败是两个环节叠加的结果。作者同时强调这段分析是关联性的：没有任何随机化决定子代理选择保留什么，gloss 攻击下同样的信号损失就不预测伤害（16/125 对 4/55，p=0.32）。

还有一个容易被忽略的攻击面：同一份伪造内容，送达通道不同，模型的态度也不同。通道实验里，同一条消息以「子代理报告」（工具调用返回值）的面目出现时被采纳 102/120（85%），作为同侪消息送达时只有 18/39（46%）——系统天然更信任子代理的产出，恰恰放大了污染。作者由此提醒：现有的注入防御常在文本进入系统时打上「不可信」标记，但子代理自己的输出不会被这样标记；在系统保留可供审计的原始证据之前，不应默认子代理和工具的产出是有据可查的。

传递实验把风险再推一层。在攻击者→工作者→聚合者的三链结构里，五个聚合器自己单独面对伪造记录时几乎从不犯错，却把被腐蚀工作者报告的错误在 751/757 次试验里原样重复——「多个模型互相检查」的直觉在这里翻车：互相赞同不需要接触证据，发现错误才需要。

防御实验的结论反而轻快。让子代理的验证器检索并引用原始记录，有害修订从 15/40 降到 3/40；只告诉验证器「这个档案库可能不可靠，请保持怀疑」，降到 1/40；两者统计上无法区分（p=0.63）。换句话说，在这个真实 harness 的实验里起作用的成分不是溯源核对，而是「怀疑」本身。防御侧的另两组对照同样干净：五个聚合器实验里，把检索到的原始记录交给聚合器，错误直接清零（0/780）——失败出在证据获取，不在判断力；另一组模拟场景的三个受试模型上，一个只断言正确答案、不引用原文的验证器也能保护两个。

这篇和本文前面提到的多 Agent 元分析（arXiv:2611.17610）放在一起读：那篇说协作在同预算下几乎不白给准确率，这篇说协作还会把安全水位拉到最弱组件。两条加起来，「强编排器 + 便宜子代理」的默认架构需要重新算账——省下来的是真金白银，付出的是整个系统的安全下限。

落到工程上，五件事值得直接搬走：

1. 评估多 Agent 系统的安全性，测的不是最强模型，是「每类证据的最弱读者」；新模型接进系统前，单独测它对伪造、矛盾证据的抵抗力。
2. 子代理的产出规范里明确要求保留溯源线索（来源、日期、格式异常），把「指出异常」当成摘要里必须保留的字段，而不是可以压缩掉的细节。
3. 编排器对委托回来的结果保持「怀疑」姿态——这条 prompt 级防御便宜到近乎免费，实测与完整溯源核验无法区分。
4. 关键决策前的验证必须引用原始记录，复述结论不算验证；能安排「读者接触原始证据」，就不要安排「读者接触二手摘要」。
5. 互查结构不能取代证据接触：聚合、评审、投票都只复制报告里的东西，发现错误的前提是有人重新打开原始文件。

## 回答八个真实追问

**超级 Agent 还是多个专门 Agent？** 当子任务、权限或上下文能清晰隔离时拆分才有价值；耦合强时单 Agent 更简单。

**生产多 Agent 是提升还是炒作？** 两者都可能。必须与同预算单 Agent 和固定 Workflow 比较成功率、成本、延迟与可调试性。

**多个小 Agent 能超过大模型吗？** 在搜索、投票或分工任务上可能，但收益来自额外计算与聚合，不是自动的群体智慧。

**长任务协调最难什么？** 维护权威共享状态、依赖、版本、产物和取消，避免上下文各自漂移。

**共享文件已经写好了，为什么各 Agent 还是各干各的？** 因为「有共享状态」不等于「状态对齐」：Agent 可能在启动时读过一份快照后再没刷新，交接摘要可能悄悄丢掉一条需求，两个 Agent 的改动可能文本上能合并、语义上已经冲突。逐项检查读、写、传三个环节，参考本篇「共享状态」一节。

**需求传给子 Agent 又合并回来，怎么保证没有被改掉？** 用结构化需求清单加确定性核对，别指望 LLM 裁判——它在同等轨迹上的误报率是确定性校验器的七倍。签名能防运输途中的篡改，防不了提取阶段的污染：清单生成那一刻才是信任边界，先审提取，再谈签名。

**多 Agent 互相检查，不是比单模型更安全吗？** 只有当每个检查者都接触原始证据时才成立。只读摘要的「检查」复制错误比发现错误容易得多——五个单独面对伪造记录几乎从不犯错的聚合器，把被腐蚀子代理的错误原样重复了 751/757 次；而防御可以便宜到一条「保持怀疑」的指令。

**如何决定并行、串行和冲突仲裁？** 看数据依赖与副作用；事实冲突回到证据，方案冲突按预设标准或人工责任处理。
