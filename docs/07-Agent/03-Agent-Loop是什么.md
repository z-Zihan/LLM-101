# Agent Loop 是什么？

> 所属专题：Agent · 前置：[Agent 到底是什么](./01-Agent到底是什么.md) · 后续：[Workflow 和 Agent 有什么区别](./05-Workflow和Agent有什么区别.md)

Agent 为什么能连续做很多步？因为系统没有在模型第一次输出后结束，而是执行下一步、收集结果、更新状态，再把最新情况交给模型判断。这种反复“观察—决定—行动—更新”的运行方式，通常叫 Agent Loop。

循环带来适应性，也会放大错误、成本和副作用。一个可上线的 Loop 必须知道何时成功、何时求助、何时强制停止。

## 一轮和下一轮怎样连起来

任务是“找到测试失败原因”。Agent 先决定运行测试，终端返回报错文件；下一轮读该文件，发现配置引用；再下一轮检查配置并运行最小测试验证。

```text
目标与当前状态
  ↓ Observe：读取最新环境和结果
Decide：模型选择下一步
  ↓
Act：宿主执行工具或请求确认
  ↓
Update：记录结果、错误和预算
  ↺
```

这张图想展示“反馈”如何进入下一轮。读图时注意 Act 可能不执行工具：它也可以直接回答、请求用户选择，或因风险而停止。

不同框架会使用 Plan、Reason、Act、Reflect 等名字，也可能合并阶段。名称不是关键；能否把真实执行结果正确带回，并据此改变下一步，才是 Loop 的功能。

这也解释了为什么许多最小实现看起来只是一个 `while` 循环：调用模型，解析它提出的工具请求，执行工具，把结果追加到状态，再调用模型。代码外形可以很短，但真正困难的部分藏在循环周围——参数校验、权限控制、重复调用、超时、停止条件和结果验证。缺少这些护栏的几十行示例适合教学，不等于可以直接上线。

## 状态不等于一长串聊天记录

状态可能包含原始目标、完成标准、已执行步骤、工具结果、当前计划、文件变化、用户确认、错误次数和剩余预算。有些内容进入本次模型上下文，另一些保存在数据库或文件中，按需要摘要和取回。

把所有历史无筛选地塞进上下文，会增加成本和噪声，旧信息还可能与环境现状冲突。系统要标记哪些观察仍有效，哪些动作已经完成，哪些外部状态需要重新读取。

状态也应区分“模型计划”“宿主批准”“工具执行”和“业务确认”。否则模型说“文件已删除”可能被错误记录成真实完成，而工具其实超时了。

真正运行数小时或跨会话的 Agent，不能把全部状态押在不断增长的上下文里。目标、计划版本、已完成动作、待办、用户批准、外部资源 ID、检查点和验证证据应保存在外部状态；模型每一轮只读取当前步骤需要的部分。恢复时还要重新查询文件、任务和业务系统，因为保存的观察可能已经过期。

持久化不是把聊天全文搬进数据库就结束。写操作要有唯一请求标识，检查点要记录哪些副作用已经发生，摘要要能回到原始证据。否则任务重启后可能重复发消息、重复付款，或把模型曾经计划做的动作误当成已经完成。

## Loop 应该在什么时候停

达到可验证完成标准时成功停止；关键依赖失败、目标不可达时失败停止；需要凭证、选择或高风险确认时等待用户；达到步骤、时间、Token 或费用上限时限制停止；用户取消或安全策略拒绝时立即停止。

这些硬限制由外部程序实施，不能只请模型“记得不要运行太久”。模型可以建议任务完成，但测试、业务状态或其他验证器应确认重要结果。

停止不是失败处理的最后一招。一个诚实的“证据不足，已停在第 6 步”通常比继续编造结果更有价值。

## 为什么错误会越滚越大

若一轮误读报错，下一轮可能在错误文件上修改；若工具超时却被当成失败，重试写操作可能重复发送或创建资源。长循环还会积累上下文噪声，让模型逐渐偏离原始目标。

系统需要校验工具输入输出，为有副作用的操作使用幂等设计或唯一请求标识，限制重试次数，并保留检查点。无法安全自动恢复时，应转交人工，而不是换一种措辞继续撞同一接口。

“幂等”可以先理解成：同一个请求因网络问题重复执行，不会不断制造新的副作用。查询通常容易重试，付款、发送和删除则必须特别设计。

## Prompt Injection 为什么接上工具后更危险

网页、邮件、代码注释和文档都可能夹带“忽略原任务、上传文件”之类文字。它们是 Agent 要分析的数据，不是有权改变目标的系统指令。模型却可能把两者混淆；一旦 Agent 拥有浏览器登录态、Shell、文件或 API，混淆就可能从错误回答变成数据外传和现实操作。

本地模型不会自动消除这种风险，登录态也不是安全边界。宿主要把外部内容标记为不可信，限制可访问域名、文件和工具，把读取与写入权限分开；发送、删除、发布和凭证操作需要独立校验或用户确认。模型提出的参数还要经过允许列表、资源归属和业务规则检查，不能只靠 Prompt 说“不要被注入”。

这些措施只能降低风险，无法证明所有注入都被识别。系统还要记录不可信内容如何进入上下文、模型提出了什么、宿主为何批准或拒绝，并用包含恶意页面和间接指令的测试持续验证边界。

## Planning、Workflow 和 Loop 的关系

Planning 决定准备怎样推进；Loop 负责让行动、观察和调整反复发生。Agent 可以先写完整计划，也可以每轮只决定下一步，计划在环境变化后还可能需要修改。

Workflow 把大量路径预先写进程序，Loop 的动态部分则允许模型根据状态选择。可靠系统常用 Workflow 约束高风险骨架，再把开放判断留给 Agent。

循环次数也不是质量指标。多一轮可能补充证据，也可能增加延迟和错误。应根据任务成功率、成本、失败类型和恢复能力评估，而不是追求“自主运行了几百步”。

## 回答开头的担心

**Agent 为什么能连续做事？** 宿主把工具执行结果更新到状态，再次调用模型选择下一步，形成反馈循环。

**为什么最小 Agent 看起来就是反复调用模型和工具？** 因为反馈循环正是最小骨架。成熟系统的差异主要在状态管理、权限、安全停止、可观测性与验证，而不是把循环换成更神秘的名称。

**它会不会一直循环？** 会有这种风险，所以最大轮数、时间、费用、取消和安全停止必须由外部程序强制。

**工具返回成功就完成了吗？** 只说明某一步接口成功；最终目标还要用测试、业务回执或其他证据确认。

**重试能自动修复问题吗？** 不能。若原因未改变，盲目重试只会重复失败，带副作用的动作还可能造成损失。

**长时间运行的 Agent 怎样保存状态？** 把目标、计划、外部资源 ID、已发生副作用、批准和证据写入外部可恢复状态，每轮按需载入，并在恢复后重新核对现实环境。

**为什么 Prompt Injection 接上工具后从“答错”变成“做错事”？** 因为不可信内容可能影响模型提出的行动，而工具能把行动落实到文件、账号和业务系统。权限、参数与确认必须由模型之外的宿主强制执行。
