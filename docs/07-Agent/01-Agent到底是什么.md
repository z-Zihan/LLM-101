# Agent 到底是什么？

原始聊天把 Agent 描述成“模型加上工具和自主规划后，为什么就能连续做事”。这句话抓到了几个重要部件，却容易让人误以为存在一条精确公式。AI 领域里的 Agent 没有跨论文、年代和厂商完全统一的单句定义。

在现代 LLM 应用里，可以先采用一个可检查的工作定义：**Agent 是围绕目标运行的系统，它读取当前状态，借助模型决定下一步，必要时调用工具，再根据执行结果继续推进，直到完成、失败或触发停止条件。**

## 一次回答和连续做事差在哪里

用户说“找出项目测试失败的原因”。普通模型调用只能根据当前输入生成一段建议；编程 Agent 可以先读取项目、运行测试、看到报错后再打开相关文件，最后用测试结果验证判断。

```text
目标：定位测试失败
  ↓
读取项目和已有报错
  ↓
模型选择：运行哪条测试
  ↓
宿主执行工具并返回结果
  ↓
模型依据新证据选择下一步
  ↺ 直到完成、受阻或达到限制
```

这张图想说明 Agent 的关键不是“调用过一次终端”，而是新结果能改变下一步。读图时注意执行者仍是宿主和工具；模型生成行动请求，不自动获得电脑权限。

## Agent 系统通常由什么组成

模型负责理解输入、比较选择和生成下一步；指令说明目标、规则和边界；状态保存任务、已执行步骤和工具结果；工具读取环境或产生现实操作；控制循环安排执行与回传；安全机制限制权限、预算和停止条件。

这些部分不一定由同一家服务提供，也不一定使用相同名称。一个 Agent 可以调用多个模型，一个模型也可以同时服务普通聊天、固定工作流和 Agent。判断系统是不是 Agent，应看运行结构，而不是产品名称里有没有 “Agent”。

Agent 也不必每次都先写出完整计划。有的系统先规划再执行，有的每轮只选择下一步，还有的把可预测部分写成固定 Workflow，只让模型处理少数开放分支。

## 零基础应该从框架开始吗

如果目标是理解 Agent，而不是尽快拼出演示，先用原生模型 API 做一个很小的闭环更稳妥：发送消息，接收模型返回的工具调用请求，由程序校验并执行，再把工具结果交回模型。亲手走完一次，才能看清哪些内容由模型生成，哪些权限掌握在宿主程序手里。

框架的价值是替你处理消息格式、工具注册、状态保存、重试和观测等重复工作。它不会替你理解这些边界；一开始就叠很多抽象，出错时反而难以判断问题在模型、提示、工具还是框架。比较实用的顺序是：

1. 先理解 [API](../06-工具与Function-Calling/01-API到底是什么.md)、[Prompt](../02-聊天Token与上下文/01-Prompt到底是什么.md) 和一次普通模型调用；
2. 再学 [Function Calling](../06-工具与Function-Calling/03-Function-Calling是什么.md) 与工具执行边界；
3. 接着亲手实现一个受限的 [Agent Loop](./03-Agent-Loop是什么.md)；
4. 然后区分 [RAG](../08-RAG与知识库/01-RAG到底是什么.md)、聊天记录、工作流与 MCP 各自解决的问题；
5. 最后根据项目复杂度选择框架，而不是把框架名称当作学习路线。

这不是唯一顺序。若只是验证业务价值，可以先用框架做原型，但仍要回头补齐权限、状态、停止条件和评测，否则原型很难安全地变成产品。

## 自主程度是一条连续谱

“自主”并非开或关。系统可以每一步都让人确认，也可以自动完成只读操作、在写入前确认；还可以在限定目录、费用和时间内连续执行，遇到高风险动作再暂停。

自主程度高不等于能力强，更不等于安全。权限越大、循环越长，错误累积和现实副作用越值得关注。生产系统通常要限制工具范围、数据边界、最大步骤、运行时间和费用，并允许用户取消。

完成标准也不能只靠模型自己宣布。“测试已修复”应由测试运行证明，“邮件已发送”应由邮件服务的业务回执确认。模型的自然语言总结只是状态的一种解释。

## Agent、聊天助手和自动化怎样区分

聊天助手可以多轮对话，却未必能执行工具或围绕目标自动推进。固定自动化可以连续执行许多步骤，却可能完全不使用模型。Agent 的特征通常在于：系统让模型根据变化中的状态参与后续行动选择。

一次 Function Calling 也不自动构成 Agent。查询天气后直接回答，可以只是一次工具增强调用；若系统能根据结果继续比较城市、调整计划并处理失败，才体现更完整的 Agent 循环。

Workflow 的路径主要由程序预先定义，Agent 的部分路径由模型动态决定。真实系统常把两者组合：固定流程控制权限、审批和可靠步骤，局部 Agent 处理无法提前穷举的判断。

## 能行动以后，风险发生了什么变化

纯文本错误通常需要人采纳才产生后果；Agent 可能把错误转成删除文件、发送信息或修改业务数据。工具返回的网页和文档也可能包含恶意指令，诱导模型越过原目标。

因此宿主必须把模型输出当作不可信建议，独立校验权限、参数和副作用。只读和写入工具要分级，高风险动作要确认；每轮决定、批准、执行与结果都应留日志，失败后才能定位是哪一层出错。

Agent 也可能循环、盲目重试或在错误假设上越走越远。外部程序应强制预算、超时和最大轮数，提供取消、恢复和转交人工的路径。这些约束不能只写进 Prompt。

## 回答两个真实问题

**Agent 智能体是什么？** 在本项目语境里，它是围绕目标组合模型、状态、工具、控制循环与安全边界，并能依据新结果继续行动的系统。

**AI 里的 Agent 有跨领域统一定义吗？** 没有一个覆盖经典 AI、强化学习、软件代理和 LLM 产品的唯一口径。使用这个词时应说明观察范围、可用动作、控制循环和自主程度。

**模型接上工具就自动变成 Agent 吗？** 不一定。工具提供能力，Agent 还需要目标、状态、结果回传、后续决策和停止机制。

**零基础要先学原生 API，还是直接学 Agent 框架？** 至少先用原生 API 看懂一次“模型提出调用—程序执行—结果回传”的闭环，再决定是否用框架减少工程重复。框架是实现选择，不是 Agent 原理本身。

**Function Calling、MCP、RAG、记忆和工作流应该按什么顺序学？** 先学模型调用与工具边界，再学循环和状态；RAG、记忆、工作流、MCP 是不同问题的解决办法，可以在看懂基本 Loop 后按项目需要分支学习。

**Agent 能替用户承担责任吗？** 不能。授权、审核和责任仍属于设计与使用系统的人和组织。
