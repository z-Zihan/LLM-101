# 主动式智能体是什么？

> 所属专题：Agent · 前置：[Agent Loop 是什么](./03-Agent-Loop是什么.md) · [Copilot 和 Agent 有什么区别](./07-从AI-Embedded和Copilot到Agent.md) · 后续：[Agent 的长期记忆是怎样实现的](../12-Memory/02-Agent的长期记忆是怎样实现的.md)

2026 年 10 月，Anthropic 上线了一个叫 Claude Duet 的产品（Research Preview，需排队获取资格）。官方页面对它的介绍只有一句话："一个你可以给它发消息的主动式智能体：它会标记收件箱和日历里需要你处理的事项，并替你起草回复。"注意这句话里的动作方向——不是你问它答，而是它盯着你的收件箱和日历，发现有事需要处理，主动来找你。

同一周，OpenAI 的 API 文档里出现了新模型 GPT-6.1 Terra，官方列出的典型用途中有一项是"在应用屏幕上执行操作"。模型能看懂并操作软件界面，等于给主动式系统配上了一双能替你点按钮的手。

这两件事放在一起，指向同一个此前没有被主流产品认真回答过的问题：如果 Agent 真的能替人干活，为什么每次都要由用户负责想起它、打开它、给它派活？本文要讲的就是这个新形态——主动式智能体（Proactive Agent）：它靠什么触发、触发之后要判断什么、打断用户的成本怎么算，以及它容易在哪些地方出问题。

## 触发器在哪，系统就属于哪一类

你之前学过的 [Agent](./01-Agent到底是什么.md)，无论多复杂，都有一个共同点：**由用户的一次输入启动**。你在对话框里发消息、在 IDE 里下达指令、给 Coding Agent 派一个任务——用户的输入就是触发器。任务结束，Agent 停下来，回到等待状态。

主动式智能体把这个前提改掉了：**触发器可以不是用户**。它可以是：

- 一条事件：新邮件到达、日历上出现会议冲突、CI 流水线挂了；
- 一个时间点：每天早上八点扫一遍未读消息；
- 一段状态：某个文件三天没人处理、某个指标连续两小时异常。

这些触发方式在软件工程里都不新鲜——定时任务和监控报警已经存在几十年。那主动式智能体和 cron 加一段脚本的区别在哪？区别在于**触发之后由谁判断**。cron 到点就执行固定动作，动作是人事先写死的；主动式智能体被事件唤醒后，要先判断这件事值不值得做、该怎么做、要不要打扰用户，判断本身交给模型。换句话说，cron 把"什么时候"写死在代码里，主动式智能体把"要不要、怎么做"交给运行时的推理。

这类产品到 2026 年才进入主流视野，一个合理的解释是：触发器不难，难的是触发之后的判断足够可靠。判断不可靠的主动性，产出的不是效率，是噪音。

## 一个主动闭环长什么样

用一个具体场景走一遍。假设 Agent 接入了你的邮箱和日历：

```text
[触发] 日历事件更新：明天上午与客户的会议改期了
  ↓
[观察] 检查相关上下文：客户往来邮件、会议议程、你的日程
  ↓
[判断] 这个变化需要你参与吗？
        → 只是例行改期、没有冲突：记下来，不打扰
        → 与你另一个会议冲突，且客户在等回复：值得行动
  ↓
[行动] 起草一封改期说明邮件（只起草，不发送）
  ↓
[打断] 在你下次查看时提示：有一封待确认的草稿
  ↓
[记录] 你的处理方式写回记忆，供下次判断参考
```

读这张图有两个重点。第一，**大部分环节和普通 Agent 一样**：观察、调用工具、生成草稿，走的仍是 [Agent Loop](./03-Agent-Loop是什么.md)。主动式不是一种新的运行结构，而是把"什么时候进入循环"的决定权从用户手里接了过来。第二，图里唯一的新环节是中间那道判断：**这件事值不值得打断用户**。这道判断是整个形态的成败所在，后面两节专门讲它。

## 触发之后：问用户、查环境，还是直接行动

Agent 被事件唤醒后，发现信息不够怎么办？人类的办法通常只有一种：问。但对 Agent 来说，"问用户"只是补信息的途径之一，还有另一条路：自己查。问用户花的是用户的注意力，查环境花的是时间和调用成本，两条路各有代价。

2026 年 9 月的一篇论文把这个问题形式化了。PROUR（Uncertainty Routing for Proactive Agents，arXiv:2609.32255）把 Agent 的选择分成三类：**行动（ACT）**——按当前理解直接执行；**问用户（CLARIFY）**——请求澄清；**查环境（VERIFY）**——调用工具去核实。它的核心思路是把"拿不准"拆成两种来源：如果模型对用户目标的几种理解之间分歧很大，说明问题出在用户侧的表达，该去问用户；如果某一种理解的内部仍然不确定，说明缺的是世界侧的证据，该去查环境。

在 τ-bench 的零售和航空两类任务上，PROUR 的平均成功率 28.17%，比此前最强方法高 4.57 个百分点，交互步数还少 2.17 步。绝对数字看着不高（这两类任务本身就难），但方向值得注意：**把"问谁"当成一个可学习的路由决策，比无脑问或无脑猜都好**。

这里有一个值得记住的对应关系：CLARIFY 花用户的注意力，VERIFY 花系统自己的资源。成熟的主动式系统会尽量用 VERIFY 消化掉大部分不确定性，把 CLARIFY 留给真正只有用户能回答的问题——你的会议偏好、你和客户的关系、你愿不愿意改期。这些信息不在任何工具的读取范围里。

## 打断是预算，不是免费动作

"别动不动就来问我"不只是一句抱怨，它是可以度量、可以优化的设计指标。

2026 年 10 月的论文《Ask Less, Ask Better》（arXiv:2610.24411）提出了"打断预算"（interruption budget）的评测协议：限制 Agent 最多能问几个问题，同时用"用户注意力成本"给每个问题计费——问题越难读懂、越不值得问，扣分越多。这个协议区分了两件事：**问得多不多，和问得好不好**。只数问题数量的老评法把必要问题和废话问题同等对待；而人类标注者在问题数量相同的对话对里，75% 的情况同意"哪一组更费神"——人对负担轻重的判断稳定存在，问题质量确实可以单独度量。

数据给了一个反直觉的结论：把 Agent 限制到最多问 1～3 个问题，注意力成本下降 36%～73%，但任务收益仍保留 86%～94%。也就是说，**大部分提问是低价值的**，砍掉它们几乎不伤任务完成度。论文还发现，提问前先对照用户此前已回答过的内容（避免重复问），能再省 13% 的注意力成本——这等于给"主动式系统需要记忆"这个直觉补上了数字。

对设计者来说，这组数字的启示是：不要把"能问"当能力，要把用户的注意力当成和 Token、钱一样的预算来管理。每设计一个主动提醒，都在花用户的预算；花得越随意，用户关掉通知越快。

## 主动找什么信息，也是一门学问

前面两节解决"什么时候开口"。还有一半问题没解决：主动的 Agent 该主动去找什么？

同在 2026 年 9 月的论文《Asking for What Was Never Requested》（arXiv:2609.37236）区分了两种主动性内容：**横向主动性**——追问当前上下文已经指明、但用户没说出口的信息（客户邮件里提到"附件里的方案"，就去把附件读了）；**纵向主动性**——追那些只有读完早期材料才会暴露的需求（读到第三封邮件才发现，真正的争议点在两个月前的一份报价单里）。论文用"需求图"把这两类行为和"该停就停"都变成可以从对话记录直接打分的东西，不需要另一个模型当裁判。

它训练出的提问器有个很有说明性的结果：在同等检索开销下，用小模型训练出的提问行为，在三个多跳问答基准中的两个上，胜过同一角色下参数多 15 倍的纯提示模型。**主动性内容是一种可训练的行为，不是堆参数就能自然涌现的能力**——这句话对产品团队的含义是：想让 Agent 主动得体，光换更强的模型不一定有用，得在"找什么"上做专门的设计。

## 主动式的四种典型失败

主动式把控制权从用户手里拿走了一部分，相应地也引入了新的失败方式。

**误触发与"狼来了"。** 触发器太敏感，或者触发后的判断太宽松，系统频繁报告不重要的事。用户的注意力信任被耗尽后，会忽略之后的一切通知——包括真正重要的那条。对主动式系统来说，用户注意力是一次性资源。

**打断焦虑。** 和上一条相反：系统判断过于保守，明明有事却总说"先不打扰"。用户以为它盯着，实际它沉默。这类失败比误触发更隐蔽，因为没有任何错误信息出现。评测上需要专门检查"该报未报"的比例，不能只看误报率。

**沉默失败。** 主动式系统通常无人值守运行。它半夜跑了，失败了，重试也失败了——如果没有失败上报机制，任务就凭空消失，而用户第二天还以为它在干活。长任务的检查点与恢复（见[Agent 如何规划和恢复](./04-Agent如何规划和恢复.md)）在主动式场景里从优化项变成了必需品。

**副作用被触发器放大。** 一个响应式 Agent 的错误操作，只影响用户主动交代的那个任务；主动式 Agent 的错误操作会自己找任务。如果它有权发邮件，一次误判断就可能替你发出一封不该发的邮件。因此主动式系统的权限设计要比交互式更保守：**低风险动作自动做，高风险动作只准备、不执行**——Claude Duet 的"起草回复"而不是"发送回复"，就是这个原则的产品化表达。

## 别把三样东西混在一起

**主动式 ≠ 定时任务。** cron 也能每天八点给你发摘要，但它的"要不要做"是写死的。判断标准不是有没有定时器，而是触发之后有没有一个会根据情况改变行为的决策环节。

**主动式 ≠ 记忆。** 记忆（见 [Agent 的长期记忆是怎样实现的](../12-Memory/02-Agent的长期记忆是怎样实现的.md)）解决"信息怎么存、怎么取回来"，主动式解决"什么时候进入循环"。两者互补：主动判断需要记忆做输入（避免重复打断、了解用户偏好），但有了记忆不等于有了主动性。

**主动式 ≠ 权限更大。** 一个只在你提问时工作的 Agent，可能拥有删除生产数据库的权限；一个主动盯盘的 Agent，可能只有只读权限。自主性描述的是启动方式，权限描述的是能做什么，两者独立配置，也应该独立审计。

## 回到开头的问题

为什么 AI 开始主动找你？因为执行任务对 Agent 已经不再是瓶颈，瓶颈转移到了"值不值得打断你"。Claude Duet 把这个判断包装成了产品（标记事项、起草回复，发送权留在你手里），GPT-6.1 Terra 给这类系统配上了操作界面的手，学术侧则已经把"问用户还是查环境""允许问几个问题""主动找什么"拆成了可以分别度量的问题。

下次遇到一个主动找你的 AI，可以按本文的顺序问三个问题：它的触发器是什么？它怎么决定打断我而不是自己查？它花的每一次打断，有没有对照我的记忆？三个答案的质量，基本决定了这个产品是助手还是噪音。
