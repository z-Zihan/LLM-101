# MCP 和 Skill 有什么区别？

> 所属专题：Skill · 前置：[Tool 和 Skill 有什么区别](./03-Tool和Skill有什么区别.md) · 后续：[Agent 和 Skill 有什么区别](./05-Agent和Skill有什么区别.md)
>
> 最后核验：2026-11-11

MCP 是 Host 连接外部能力的协议；Skill 是保存任务方法、脚本与资料的能力包。MCP 解决“怎样发现并连上”，Skill 解决“怎样把能力用好并完成这类任务”。

## 项目管理场景怎样组合

MCP Server 可以提供查询项目、创建任务和修改状态的 Tools。项目管理 Skill 则规定怎样拆分目标、使用哪些字段、何时先查重、创建后怎样验证。

```text
Skill：任务方法与验收
  ↓ 指导 Agent
MCP Client ↔ MCP Server：发现并调用外部能力
  ↓
后端项目管理系统
```

这张图想说明 Skill 不负责建立协议连接，MCP 也不自动提供组织工作法。读图时注意两者可以独立存在：Skill 可使用内置 Tool，MCP 应用也可不加载 Skill。

## MCP Prompt 为什么仍不是 Skill

MCP Prompt 是 Server 暴露的可复用消息模板；Skill 是带 metadata 和完整说明的目录包，还可能包含脚本、参考与素材。Skill 可以引用 MCP Prompt，平台也能编写转换层，但格式、发现方式和生命周期不同。

MCP Client/Server 需要处理协议版本和能力协商；Skill 维护者要更新业务规则、脚本和资料。协议兼容不保证 Skill 内容仍正确，Skill 更新也不会自动升级 Server。

## 组合时要审查两套边界

检查 Skill 是否要求危险操作、脚本会访问什么；同时检查 Server 来源、凭证权限、Tool 参数和用户确认。标准格式提高互操作性，不建立信任。

有 Skill 不会自动安装 MCP Server，Server 的 Tool 描述也不等于完整 Skill。两者不是父子关系，只是可以在 Agent 运行时协作的不同层。

## 分发与更新走的是两条路

两者各自怎么被安装、信任和废弃，也完全不同。

MCP Server 的分发围绕“连接”展开：Host 需要知道去哪里启动或访问它、用什么凭证，并在每次连接时协商能力。它的更新通常随实现一起发布——协议版本升级、接口调整都要 Server 跟进，否则握手就会失败。Skill 的分发则是普通文件：复制目录、放进约定位置就算安装，跨项目共享靠拷贝或仓库。代价是它没有强制的生命周期信号——说明过时了不会报错，只能等读者发现产出不对；所以 Skill 更需要维护者主动标注适用范围与最后核验时间，正如本章每页顶部所做的那样。

信任来源也不同。装一个 Server 等于把一段会执行的代码接入系统，审查重点在它要了哪些权限；装一个 Skill 是引入一份影响行为的说明书，审查重点在它教 Agent 做什么、脚本会动什么。前者防越权，后者防误导——两种检查都省不得。

## 方法什么时候该沉到协议那一侧

上一节都在讲两层如何协作，但还有一个更少被提起的方向：某些“方法”成熟到一定程度，其实应该离开 Skill，变成 Server 侧的标准动作。

判断信号是这样的：当一段流程不再需要判断，只剩确定步骤——所有人执行起来都一样、错误模式固定、验证方式机械——继续让它以“说明书 + 模型现场发挥”的形式存在，就只是把风险留在概率层。模型每次都可能漏一步，而这类确定性操作本可以在 Server 里一次实现、处处一致。常见的例子是把零散的“查询—比对—写入”三步合并成一个原子 Tool：原来靠说明约束的顺序和校验，现在由代码保证。

反过来，真正依赖上下文取舍的部分——哪些情况适用例外、怎样向用户解释取舍——才值得留在 Skill。一条实用的追问是：“这段指导最后一次被模型改着办是什么时候？”如果答案是好几次都按同一种走法执行，恭喜，你找到了一个该沉底的候选；把它固化之后，说明书变短，行为反而更稳。

## SKILL.md 是终点吗：把说明书固化成软件

前面的对照都默认 Skill 以 Markdown 说明书的形式存在。这个假设在 2026 年 11 月被一篇立场鲜明的论文正面挑战了。Peilivanidis 发表的 Skillware（arXiv:2611.07652）标题就是态度：「不要给 Agent 写提示，给他们装备」。论文主张：把任务能力做成 Markdown 说明书、再指望模型每次现场读懂并做对，是靠概率去执行本该由软件保证的事情；更合理的做法是把能力做成带类型契约、确定性代码和离线测试的软件包，模型只负责判断「何时用」，不碰「怎样执行」。

这个主张不是空想，论文拿出了少见的大规模对照数据：23 个模型、368 组基准条件。更有说服力的是三臂实验的设计——它把「给了代码」和「给了完整能力包」拆成了两件事。让模型裸写代码的基线（Arm 1）通过率只有 58.2%；换成预编译代码加朴素工具调用（Arm 2，有代码但没有类型校验、确认门和防护），通过率升到 71.4%，但仍留下 14.2% 的参数错误率，遇到模棱两可的请求时 54.6% 的运行直接执行了不可逆操作；只有五件套齐全——类型化契约（manifest.yaml）、确定性实现（skill.py）、认知指令（instructions.md）、离线测试（test_skill.py）、展示元数据（card.json）——通过率才到 91.8%，参数错误归零。结论很清晰：把逻辑从概率层挪进代码只是第一步，契约、测试和治理边界各自承担不可替代的部分，拆掉任何一件都会重新暴露对应的失效模式。

数据里最反直觉的一条是所谓「小模型悖论」：能力包带来的提升与模型规模成反比。前沿模型装上后只涨 18 到 20 分，8B 小模型却从 56.0 涨到 88.0 分——一台消费级硬件上的开源 8B 模型，装上能力包后系统性超过了没装备的 Claude Sonnet 5（80.0 分）和 GPT-5（79.0 分），同时 Token 开销最多降 84.8%，推理成本最多降 97.3%。机制值得想清楚：小模型本来就不擅长「读散文、写代码、记住约束」三件事同时干，能力包恰恰把三件事全挪走了，只剩从受限参数集合里做选择——这正是小模型在工具调用微调里反复练过的事。提升的根源不是「包很神奇」，而是剩余任务难度被降到了与模型能力匹配。

那 Markdown Skill 是不是该被淘汰？下结论前先看清两个框架各自站位。Skillware 论文把 SKILL.md 定位为「过程性记忆」：告诉开发者的 Coding Agent 这个仓库怎么跑测试、按什么流程做事；能力包则是「功能性能力」：生产环境里由运行时应用调用的确定性代码。两者的失效面也不同——SKILL.md 的主要风险是说明书误导、脚本越权和触发冲突，这正是本文反复讨论的内容；能力包的主要风险则转移到软件供应链：谁审核这个包、依赖从哪来、包的签名可不可信。前者防误导，后者防投毒。读论文时还有一个折扣要打：它同时是论文和产品宣发，与 MCP、Agent Skills、LangChain 对比的每一节都在论证自己最优，基准也是自建的 Skillware-Bench，评分维度里治理与效率各占 25%，对自家架构天然有利——数字的方向可信，优势的具体幅度要留着审。

真正能带走的是一把判断尺子。上一节结尾问过「方法什么时候该沉到协议那一侧」，Skillware 把这个问题推到了更彻底的形态：一段任务方法离模型越远（说明 → 脚本 → 契约化工具 → 带测试的能力包），执行越确定、成本越低、审计越容易，但能覆盖的场景也越窄——因为它放弃了模型对真实世界的临场判断。为你的任务选形式时，别问「哪种更先进」，问「这段方法里有多少比例其实不需要模型判断」：比例越高，越该沉向代码；需要临场取舍的部分，才值得留在说明书里交给概率层。上下文工程里「没有免费的确定性」的权衡，在这里换了个方向再次出现——确定性的价格是灵活性。

## 回答关键问题

**MCP 和 Skill 哪个负责连接？** MCP。

**哪个负责多步任务方法？** Skill。

**MCP Prompt 是 Skill 吗？** 不是，它只是协议暴露的一类提示模板。

**能只用一个吗？** 可以；是否组合取决于任务和现有工具。

**把 Skill 换成确定性代码包，是不是就万无一失了？** 不是万无一失，而是风险换了个位置：说明书的风险是误导（教错流程），能力包的风险是供应链（包本身谁审核、依赖是否可信）。Skillware 自己的三臂实验也说明，只给预编译代码还不够——没有类型契约时参数错误率仍有 14.2%，没有确认门时过半运行会直接执行不可逆操作。确定性是分层的，每一层都要单独付费。

**为什么 8B 小模型装上能力包后反而胜过没装备的前沿模型？** 因为能力包把「读说明书、写代码、记住约束」三件事从模型身上挪走了，小模型只做受限参数选择这一件它练熟的事。提升与基线规模成反比（前沿模型 +18~20 分，8B 模型 +32 分），这提示能力包主要在补偿「执行层」，而执行层本来就不是靠参数规模解决的。

**我的任务该用 Markdown Skill 还是这类代码化能力包？** 数一数任务方法里有多少比例其实不需要模型判断。步骤完全确定、错误模式固定、验证机械的部分适合沉向代码；需要理解语境、临场取舍的部分才值得留在说明书里。多数真实任务是两者的混合。
